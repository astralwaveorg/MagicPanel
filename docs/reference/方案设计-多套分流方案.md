# 多套分流方案（variants）设计文档

> 状态：已实现并上线（2026-11-13，构建 239）。本文是「多套分流方案」能力的设计
> 事实来源；硬性约束见 `AGENTS.md` 约束 42-44。

## 1. 背景与目标

面板原本只有一套策略组 + 分流规则，所有产物都按这一套渲染。需求：

1. 支持多套「方案」，每套 = 一套完整的策略组 + 分流规则；
2. 门户（首页）下载时可选方案，订阅地址按方案出不同产物；
3. 现有的一套成为「默认」方案，行为一字不变（向后兼容）；
4. 首个自定义方案「自建美日」：只用自建节点（机房 / 家宽），分流按
   「AI、谷歌等 → 美国，低延迟等 → 日本」的原则配置。

## 2. 概念模型

**方案（variant）= 一套完整、独立的策略组 + 分流规则副本。**

备选模型是「作用域子集」（组/规则打方案标签，渲染时按标签过滤，一套共享数据）。
否决理由：`自建美日` 要求同一批组（如 `🇯🇵日本`）在不同方案下有**不同成员**
（默认方案引用机场来源，自建美日只有本地节点），子集模型表达不了
「同名组、不同成员」，只能引入一层「方案级成员覆盖」，语义比完整副本更绕。
完整副本的语义直白：**每个方案就是自己的一个世界**，渲染、校验、引用、排序
都在方案内部闭环，与现有「引擎平台 → 产物」的模型正交叠加。

- 方案与「引擎平台 / 设备」两个既有作用域维度正交：组/规则仍可按平台与设备收窄，
  渲染时三个维度取交集。
- 节点（本地节点、节点来源）、规则来源、基础配置、拓展模块**不分方案**，全部共享；
  「自建美日不用机场节点」由渲染层的「来源按引用过滤」实现（见 §6），不是数据差异。

## 3. 数据模型

### 3.1 variants 表

```sql
CREATE TABLE IF NOT EXISTS variants (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT UNIQUE NOT NULL,        -- 1~32 字；禁 @ / \ 与文件名不安全字符
  note TEXT NOT NULL DEFAULT '',
  enabled INTEGER NOT NULL DEFAULT 1,   -- 停用 = 不进新构建；已有产物照常下发
  is_system INTEGER NOT NULL DEFAULT 0, -- 「默认」方案，禁删禁改名
  sort INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- 迁移播种 `id=0, name='默认', is_system=1`，永久存在。
- `sort` 管方案在界面/门户的展示顺序，默认方案固定第一。

### 3.2 proxy_groups / rules 挂 variant_id

- `proxy_groups.variant_id INTEGER NOT NULL DEFAULT 0`、
  `rules.variant_id INTEGER NOT NULL DEFAULT 0`；`0` = 默认方案。
- **proxy_groups 需要整表重建**：`UNIQUE(name)` → `UNIQUE(variant_id, name)`，
  允许不同方案存在同名组（`🇯🇵日本` 在两个方案里是两个独立实体）。
  重建走迁移（`_migrate_variants`），先补齐全部列再重建，幂等；
  rules 表没有唯一约束，直接补列。
- 组/规则之间的引用（规则目标、组成员）全部**方案内解析**：改名重映射、
  删除解绑、校验都只看同一 `variant_id` 的行。

### 3.3 sort 分段

`sort` 仍是表内全局排序键，但**每个方案占一段**：方案 N 的行 sort =
`N * 10000` 起步（默认方案保持 0 起的原值不动）。这保证：

- 各方案互不干扰，拖拽排序（`reorder_subset` 的重复值消歧）永不跨方案触发；
- 约束 27/28（默认方案组顺序与 sort 值不动）自动满足；
- 新建组/规则时取「本方案内 max(sort)+1」。

## 4. 后端 API

### 4.1 /api/v1/variants

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/variants` | 列表（含每方案组数/规则数），按 sort, id |
| POST | `/variants` | 新建 `{name, note, copy_from?}`；`copy_from` 传方案 id 则整体复制其组与规则（sort 按分段偏移）。同时传 `use_sources_empty=1` 时复制后的组一律清空节点来源引用（给「只用本地节点」类方案用） |
| PUT | `/variants/{id}` | 改名/备注/停用启用；改名有生产产物守卫（409） |
| DELETE | `/variants/{id}` | 删除（连同该方案的组与规则）；系统方案 400；当前生产产物仍有该方案产物时 409（提示先发布新版本） |
| POST | `/variants/reorder` | 拖拽排序 |

守卫口径与约束 35 一致：**停用 ≠ 删除**；删除/改名被当前生产构建引用时拦住。

### 4.2 组 / 规则接口的方案参数

- `GET /groups/page`、`GET /groups`、`GET /rules/page`、`GET /rules`
  增加 `variant` 查询参数（方案 id，缺省 0）。
- `POST/PUT /groups`、`POST/PUT /rules` 的 body 增加 `variant_id`（缺省 0）；
  同名检查、引用校验（目标组、成员组）都在该方案内进行。
- 批量接口按 id 操作，id 自带方案归属；改目标时按每条规则所在方案校验。
- `reorder` 按提交 id 重排（同一方案的行）。

## 5. 构建与产物矩阵

- 快照（`collect_snapshot`）新增 `variants` 与组/规则的 `variant_id`；
  方案数据变化 → 策略指纹变化 → 自动构建触发（约束 40 语义不变）。
- `create_build` 对 **每个启用方案 × 每个引擎平台** 渲染一份产物：
  - 默认方案：`{target}.yaml`、`{device}.yaml`（文件名不变）；
  - 方案 V：`{target}@V.yaml`、`{device}@V.yaml`。
  - 设备专属产物仍只为「出现在 devices 作用域里的设备」渲染。
- 产物文件名冲突（target/device 名 × 方案名组合重复）在构建期报错。
- `results` 键即产物名，value 带 `"variant": V`；构建页、发布门禁、
  `_unchecked_core_targets` 自动兼容。
- 每份产物独立 `validate_rendered` + mihomo `-t`；`validate_policy`
  改为**按方案循环**校验（组引用、规则目标、兜底、顺序不变量、Fake-IP
  规则顺序都在方案内成立）。

## 6. 渲染层的变化（`render.py`）

`render_target(snapshot, target, warnings, device, variant)`：

1. 组与规则按 `variant_id` 过滤（保序）；
2. **来源按引用过滤**：展开每组的 `use`（含 `["*"]`），并集即「本方案用到的来源」。
   顶层 `proxies` 只展开**被引用的 inline 来源**的节点；`proxy-providers`
   只写**被引用的 provider 来源**。默认方案所有组 `use=["*"]` → 行为不变；
   `自建美日` 无组引用来源 → 产物无机场节点、无 proxy-providers；
3. **规则来源按引用过滤**：`rule-providers` 只写「本方案规则引用的集合 ∪
   DNS `nameserver-policy` 的 `rule-set:` 引用」（约束 31 的三个 DNS 集合
   因此永不悬空）。默认方案当前全部集合都被引用 → 行为不变；
4. 其余（兜底归位、成员剔除告警、Fake-IP 顺序等）逻辑逐方案照常。

## 7. 分发（feed）

- `GET /feed/{token}/config.yaml?variant=自建美日`：
  解析方案名 → 取 `{device}@V.yaml`，否则 `{target}@V.yaml`，都没有 → 404。
- 无参数 = 默认方案 = 原有路径，老订阅链接与已装客户端零影响。
- 方案产物是正式下发：`last_config_at`、拉取计数、`#SUBSCRIBED`、
  `profile-update-interval`、ETag 逻辑照旧；`?preview=1` 与 `?variant=`
  可组合（预览三纪律不变：不记拉取、不加 #SUBSCRIBED、inline）。

## 8. 管理界面

- **策略组 / 分流策略页**：页头加「方案」切换器（默认方案 + 自定义方案），
  列表、编辑、批量、排序都在所选方案内进行；新增按钮语义 = 在当前方案新建。
- **方案管理**：弹窗（策略组页与分流策略页共用入口），CRUD + 拖拽排序 +
  「从默认方案复制」。
- **构建发布页**：产物列表自然出现 `@方案` 条目（results 驱动），附方案徽标。

## 9. 门户（首页）

- `portal_data` 返回 `variants`（启用中的方案，默认方案在前）与每设备
  `variants_available`（按当前生产构建 results 计算：该设备的目标或设备专属
  产物存在才算可用，避免给出门会 404 的链接）。
- 设备卡片加方案选择器；复制地址、一键导入、二维码、看配置源码全部联动
  `?variant=`。默认选中「默认方案」= 现有链接不变。

## 10. 「自建美日」方案数据设计

节点池：本地节点中的美国机房 01/02、日本机房 01/02、AWS日本机房、
美国NTT 01-10（香港机房 01/02 不入）。

**精简终态（2026-11-13 向阳定稿：只有日美两类节点，客户端组列表只留三个策略）**，
一般设备 5 个组（3 可见 + 2 隐藏）：

| 组 | 类型 | 成员 |
| --- | --- | --- |
| 🚀 默认代理 | select 可见 | [🇯🇵日本, 🇺🇸美国]——入口组，MATCH 与兜底代理指向它 |
| 🇯🇵日本 | select 可见 | 🇯🇵 日本自动 + 日本机房 01/02 + AWS日本机房 |
| 🇺🇸美国 | select 可见 | 🇺🇸 美国自动 + 美国机房 01/02 + 美国NTT 01-10 |
| 🇯🇵 日本自动 | url-test 隐藏 | 全部日本节点（interval 600 / tolerance 100，约束 11） |
| 🇺🇸 美国自动 | url-test 隐藏 | 全部美国节点 |
| 🏠 路由回家 | select（仅 LVSP 设备可见） | 照抄默认方案，不动 |

**规则三向归位**（113 条服务规则改指向，`scripts/configure_selfbuilt_variant.py`
可重复执行）：

- → 🇺🇸美国（AI、谷歌、开发工具、即时通讯、海外社交、微软、跨境电商、加密货币）；
- → 🇯🇵日本（TikTok、国际影音、游戏、DMM/Pixiv/Niconico/magic-jp/oracle）；
- → DIRECT（apple，国内可达；apple-cn 已在前置直连）；
- 维持 🚀 默认代理（DNS 出口、云服务商、代理兜底集合、QUIC 拦截、MATCH）。

约束 11/13/14 依然成立：地区两层（隐藏自动 + 可见 select）、规则不指向隐藏组、
机房组已并入地区组。

## 12. 实现记录与线上事故（2026-11-13）

- **来源/集合按引用过滤**（§6）上线前先在本地用生产库副本逐字节 diff 验证：
  默认方案产物与旧版一致（rules 段零差异），共享产物里「设备专属规则的集合」
  死重量被剪掉（`apple-push` 等只进对应设备的产物，rules 段本就没有）。
- **线上事故**：`refs.detach_group` 漏传 `variant_id`，删「自建美日」的港台组时
  把默认方案里指向同名组的 8 条规则一并删了（构建 237 发布前发现，规则已按
  快照恢复，修复后有回归测试）。教训：**方案维度的引用函数一律显式传方案**，
  不许依赖调用方记得。
- **配套深度修复**（同日上线，构建 239）：
  1. **指家域名 NAT 回环**：`magichub.top` / `homehub.stream` 路由器分流 DNS
     给内网地址、公网 DoH 给家宽公网 IP——代理接管后从内网访问自己的公网 IP
     会被 NAT 回环挡住（用户实证「homehub 打不开、关代理立刻恢复」）。修复：
     引擎默认配置 `nameserver-policy` 固化这两个域为 `system`，伪键
     `_system_dns_domains` 供追加（AGENTS 约束 43）。
  2. **cn-ip 被误加 no-resolve**（违反约束 23 例外）：未收录国内域名全部落进
     `MATCH → 代理`。修复：数据修正 + 构建期校验强制（AGENTS 约束 44）。
  3. 真实内核验证：容器内起 mihomo 加载生产产物走真实流量，baidu/qq/taobao/
     jd/bilibili/weixin/douyin/zhihu 全部 `RuleSet(cn) → DIRECT`，mi 走 XiaoMi
     直连，google/chatgpt 走谷歌/人工智能组（美国机房），github 走开发工具组
     （日本机房），homehub/magichub 置顶直连——路由语义全部正确。
  4. QUIC 拦截规则（约束 34）位置复核：`cn → cn-ip → direct → private-ip →
     AND(QUIC) → MATCH`，只拦「走代理的 QUIC」，国内直连不受影响，不改动。
