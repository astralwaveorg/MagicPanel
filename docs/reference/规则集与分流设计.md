# 规则集与分流设计

面向"改规则、改分组"这类日常维护：规则集从哪来、哪些该直连、哪些该走哪个组、
以及面板在这套体系里的取舍。本文记录**实测与核对过的结论**，不是上游 README 的转述。

## 一、规则集从哪来

规则集分两层，**都在面板的「规则来源」里配远程地址**，面板抓取后存库，
再由面板自己的 `/res/rule/<name>` 下发给设备（客户端不直接访问 GitHub）：

| 层 | 地址 | 内容 | 格式 |
| --- | --- | --- | --- |
| **自维护** | `https://cdn.jsdelivr.net/gh/astralwaveorg/magic-sets@main/rule/<名称>.yaml` | 只放自己维护的增量与私有部分 | yaml |
| **上游通用** | `https://cdn.jsdelivr.net/gh/MetaCubeX/meta-rules-dat@meta/geo/{geosite\|geoip}/<名称>.mrs` | 规模大、更新频繁的通用集合 | mrs |
| **上游应用集合** | `https://cdn.jsdelivr.net/gh/blackmatrix7/ios_rule_script@master/rule/Clash/<厂商>/<名称>.yaml` | 按应用 / 厂商组织的集合，一条文件里混着多种规则类型 | yaml（行为 `classical`） |
| **第三方成品库** | 各家维护的成品规则库直链，如 `https://cdn.jsdelivr.net/gh/TG-Twilight/AWAvenue-Ads-Rule@main/Filters/<名称>.mrs` | 别人维护好的完整规则集，直接引用 | mrs（行为 `domain`） |

第三层是 blackmatrix7 的 `ios_rule_script`：按应用或厂商维度组织，
一条文件里混着 `DOMAIN-SUFFIX` / `IP-CIDR` / `PROCESS-NAME`，所以行为固定用 `classical`。
**它不进 magic-sets 仓库**——那是自维护层，只放自己维护的增量；上游集合直接引用上游地址，
同样由面板抓取存库、再由面板自己的 `/res/rule/<name>` 下发。

第四层是第三方成品库，目前只有一条 `AWAvenue-Ads`（广告过滤）。它的 mrs 是完整的
MRS 容器（`magic: MRS` + zstd），面板按 `format: mrs` / `behavior: domain` 存储，
产物里下发 `path: ./rules/AWAvenue-Ads.mrs`，与上游通用层的 mrs 处理方式一致。

自维护层是 `astralwaveorg/magic-sets` 仓库（在本项目里以 submodule 挂在 `magic-sets/`），
共 25 个集合：`ads-minimal`、`ai-overrides`、`apple-intelligence`、`apple-push`、
`apple-push-ip`、`claude-extra`、`cn-services`、`connectivity-check`、`dev-extra`、
`direct-ports`、`dns-direct`、`gemini`、`jp`、`kr`、
`lvsp-direct`、`lvsp-ip-check`、`mail-password`、`mirror-accelerate`、`openai-extra`、
`payment-finance`、`proxy`、`proxy-domain`、`search`、`self-hosted`、`social-extra`。

**集合名与仓库文件名一致**，改名时两边一起改；中文展示名写在仓库文件的注释里，
不进文件名（避免 URL 里的百分号编码）。

上游层的 `meta` 分支下 `geo/geosite` 有 1923 个 mrs、`geo/geoip` 有 260 个
（其中 250 个是国家码，10 个是命名集合：`cloudflare`、`cloudfront`、`facebook`、
`fastly`、`google`、`netflix`、`private`、`telegram`、`tor`、`twitter`）。

上游还有一层是 **GEOSITE / GEOIP 规则**（配合客户端本地的 `geosite.dat` / `geoip.dat`）。
面板**不用**这一层，原因见下节。

## 二、上游 README 的示例用法为什么不适合面板

上游 README 的示例配置用的是 `GEOSITE,xxx` / `GEOIP,xxx` 规则 + 客户端本地 Geo 文件。
面板不用，理由是三条：

1. **重复一套机制**。面板的规则集机制（`RULE-SET` + 面板自建 provider）已经能表达
   同样的分类，且内容由面板抓取、存储、去重后再下发。用 `GEOSITE` 就变成两套并存。
2. **给客户端加依赖**。`GEOSITE`/`GEOIP` 要求客户端本地有 `geosite.dat`/`geoip.dat`
   且能下载更新；面板的规则集只需要客户端能访问面板自己的 feed。
3. **面板没法去重**。上游的 `cn` 有 11 万条、`proxy` 与其它分类大量重叠。面板能把
   重复条目在服务端剔掉再下发（`proxy` / `proxy-domain` 就是这么做的），
   `GEOSITE` 则是整包下发，客户端拿到的体积和匹配成本都更高。

**结论：同一个分类，面板统一用 MRS 规则集下发**，不用 GEOSITE/GEOIP 规则。
上游 README 里的 `path-in-bundle` 是给"下载整个 BundleMRS.7z"的用法，与面板自建
provider 的路子无关，不采用。

## 三、兜底方向：代理优先，不是直连优先

上游示例最后一行是 `MATCH,DIRECT`。面板**不**这么做，面板的兜底是：

```
MATCH,🚀 默认代理
```

即"**先分流、未列出的全部走代理**"。原因是国内网络环境下，"忘了配一条规则"
的代价远大于"多代理了一次"：

- 兜底直连 → 任何没配进规则集的境外服务直接打不开（这是"用着用着突然有网站访问不了"
  的最常见原因）；
- 兜底代理 → 没配规则的服务仍能通过代理访问，只是线路可能不是最优。

因此**新增服务规则集是补充，不是兜底**：漏配不会导致打不开，补了只是让线路更对路
（固定地区、走专门的分组）。

## 四、哪些该直连、哪些该代理、走哪个组

判据按优先级：

1. **有地区要求的**（Netflix、TikTok、AI、支付）→ 代理，且分组首成员必须是该地区，
   否则服务端会按出口 IP 拒绝（"不在服务区域"）。现状：
   🌐 谷歌服务 / 🧠 人工智能 / 🎵 TikTok 首成员都是 🇺🇸 美国。
2. **国内服务** → 直连，但要排在"服务分类"规则之后，保证同名冲突时服务优先。
   现状的 CN 专用集合（`cn-services`、`ai-cn`、`apple-cn`、`microsoft-cn`、
   `games-cn`、`steam-cn`…）统一排在服务集合前面，这是有意的：国内 AI（DeepSeek、
   豆包）、国内游戏官网、国内 Apple/Microsoft 服务直连更快。
3. **CDN 类**（`cloudflare` / `cloudfront` / `fastly` / `akamai`）→ **不单独设规则**。
   面板兜底是代理，CDN 走代理不会打不开；反过来加一条"CDN 直连"例外会误伤
   （大量国内站点托管在 Cloudflare），而且 Steam / Apple / 微软的下载都走 CloudFront，
   与"Steam 下载走香港"的决定直接冲突。
4. **tracker** → 直连（避免 tracker 请求暴露代理出口 IP）。面板现在用两条：
   `category-public-tracker`（437 条，上游通用层）→ DIRECT，以及 blackmatrix7 的
   `PrivateTracker`（248 条，上游应用层）→ DIRECT，排在强制代理清单之后。
5. **广告** → REJECT。广告拦截走双轨，都排在第 4 段最前，先于所有分流判定：
   - **Stash 侧（iOS / tvOS / macOS）**：`AWAvenue-Ads`（第三方成品库，mrs）与
     `ads-minimal`（自维护，4 条）→ 目标直接写 `REJECT`，并勾上「提前拒绝」
     （`pre-matching`）与「不记入连接列表」（`no-track`）。命中在连接建立前就拒掉，
     广告请求量大重试快，iOS 上省 CPU 与内存最明显。
   - **其余平台（Stash-Android / Stash-Windows / Mihomo 三端）**：同样两个集合 →
     「🛑 广告过滤」策略组（成员 `REJECT / DIRECT / ⚡️ 自动测速 / 🚀 默认代理`，
     默认 REJECT），保留临时切「默认代理 / 直连」的能力；只勾「不记入连接列表」。

   同一规则集在互斥的引擎平台各挂一条是允许的：面板的「规则重复」判定只看
   适用范围有没有交集，互斥平台不算重复。

### 小米生态为什么直连、排在哪里

`XiaoMi` 集合取自 blackmatrix7 `ios_rule_script` 的 `Clash/XiaoMi/XiaoMi.yaml`：
159 条（`DOMAIN-SUFFIX` 148 / `IP-CIDR` 9 / `PROCESS-NAME` 2），覆盖小米与米家生态
（mi.com、huami、airstar 等）及其国内 CDN 段。目标 `DIRECT`，
适用于所有引擎平台与设备（`targets`/`devices` 都是「包含所有」）。

放置位置：**`cn` 之后、所有服务分类规则之前**。

- `cn` 在前面，同名的国内域名先被直连，结果一致；
- 服务分类（`google`/`apple`/`games`/`social`…）在后面，直连集合压住它们——
  要求是"确保直连"，所以这条要排在服务规则前面；
- `ads-minimal`、`proxy`、`proxy-domain` 排在更前面不影响结果：实测这三个集合与
  Xiaomi 的 159 条**零重叠**（逐条比对过，`cn-services`、`payment-finance`、
  `mail-password`、`search`、`jp` 等自维护集合同样零重叠）。

### 日本出口：🇯🇵 日本服务 组取代 🎏 日韩服务

原来的 `🎏 日韩服务` 组是「按规则集分流」的：成员是 `🇯🇵 日本` / `🇰🇷 韩国` / `🇯🇵 日本机房`
三个组，规则集 `jp-kr-services`、`jp-kr-services-ip` 和一条 `linux.do` 单独规则都指向它。
它只能按"日韩"这个标签分流，选不了具体节点——而实际需求是"日本线路里挑一个"。

现在改成 **`🇯🇵 日本服务`**（同一个组改名、成员重排）：

| 位置 | 成员 | 来源 |
| --- | --- | --- |
| 1 | `🇯🇵 日本` | 自动测速的日本组（url-test，不变） |
| 2 | `🇯🇵 日本机房` | 两个日本机房节点（url-test） |
| 3 | 其余日本节点 | `use_sources` 取全部来源 + 日本正则过滤，按名称排序 |

前两项是组，展开后是节点；客户端里可以直接从这一组里挑具体节点。

配套改动：

- **所有引用 `🇯🇵 日本` 的策略组改成引用 `🇯🇵 日本服务`**（12 个：🚀 默认代理、⚡️ 自动测速、
  🌐 谷歌服务、🧠 人工智能、💻 开发工具、🎬 国际影音、🎮 海外游戏、🎵 TikTok、💬 社交通讯、
  💳 支付理财、🔐 邮箱密码——后两个组后来已撤掉，见下）。`🇯🇵 日本` 组本身保留不动，
  仍是自动测速的日本组。
- **日韩拆成两个集合，但走同一条线路**：`jp-kr-services`（8 条域名）→ 集合 **`jp`**
  （行为 `domain`），`jp-kr-services-ip`（1 条 IP 段）→ 集合 **`kr`**（行为 `ipcidr`）。
  两条规则都指向 🇯🇵 日本服务：
  - `RULE-SET,jp` → 🇯🇵 日本服务，适用 8 台 Astral 设备（沿用原 `jp-kr-services` 的范围）
  - `RULE-SET,kr` → 🇯🇵 日本服务，**全部平台、全部设备**

  这样做的用意是**淡化对韩国节点的依赖**：韩国的 IP 段不再单独走默认代理，
  而是并入日本线路，用哪条日本出口由 `🇯🇵 日本服务` 组里的成员顺序决定。
  集合名也不带聚合含义——`jp-kr` 这种把两个国家捆在一起的名字，随着拆分就该消失。
- **删掉 `linux.do` 单独规则**：`proxy-domain` 里已有 `+.linux.do`（强制代理），
  再单列一条是重复覆盖。
- **规则 `oapi.dnscli.top`（Lvsp 专属）改指 🇯🇵 日本服务**：原来指向 `🇯🇵 日本`（自动测速组），
  现在日本出口统一由 `🇯🇵 日本服务` 承担。

### 自维护集合改完内容，面板抓到的还是旧的：jsDelivr 缓存

jsDelivr 对**已存在路径**的内容有 12 小时缓存，改完 `magic-sets` 里的文件再抓，
拿到的还是旧版本。实测：`?v=983c705` 这种查询参数**不起作用**（缓存键不含 query），

`https://cdn.jsdelivr.net/gh/astralwaveorg/magic-sets@<commit>/rule/<名称>.yaml`，
再抓一次**。新集合用 `@main` 没问题（路径是新的，没有旧缓存）。

### 账户类域名：为什么不单列分组

账户相关的域名先后经历过三版：

1. 一个 `accounts` 集合塞了 19 个域名（PayPal、Stripe、Wise、IBKR、Schwab、Fidelity、
   Proton、Tuta、1Password、Bitwarden）。
2. 拆成两个组：`💳 支付理财`（支付、汇款、证券）与 `🔐 邮箱密码`（邮箱、密码管理器），
   理由是"出口地区与支付地不一致会被风控""登录地与常用地不一致容易被判异常"。
3. **现在两个组都撤掉了**，这些域名的出口统一由 `🧠 人工智能` 组承担（首成员 🇺🇸 美国）。

撤掉的理由不是分组理由错了，而是**这两个组实际上没有起到分流作用**：

- 组是 select 型，首成员固定 🇺🇸 美国，等于把所有账户域名锁死在美国出口；
- 而这些服务对出口的要求本来就分成两派：证券三家（IBKR、Schwab、Fidelity）
  **必须**美国 IP，否则登录被拒；PayPal、Wise 这类支付汇款反而要跟随账户归属地，
  固定美国 IP 正是文档里担心的"不一致被风控"；Proton（瑞士）、Tuta（德国）跨洲登录
  会触发异常登录提醒；1Password、Bitwarden 在北美，用美国 IP 正常。
- 拆成两个组也不能解决——首成员一样，账户归属地那一派仍然被拖去美国。

现在的规则集划分：

| 规则集 | 内容 | 目标 |
| --- | --- | --- |
| `PayPal`（上游 blackmatrix7，classical，247 条） | PayPal 全站域名，含 `DOMAIN-KEYWORD,paypal` | 🧠 人工智能 |
| `payment-finance`（自维护，8 条） | Stripe、Wise、IBKR、Schwab、Fidelity | 🧠 人工智能 |
| `mail-password`（自维护，4 条） | 1Password、Bitwarden | 🧠 人工智能 |
| —— | Proton、Tuta | 落到 `proxy-domain` 与兜底，走默认代理 |

`payment-finance` 与 `mail-password` 的 URL 用的是 magic-sets 的 commit 引用
（`@c1b707e`）：jsDelivr 对已存在路径有 12 小时缓存，改完集合内容必须换 commit
才抓得到新的。

### 「手动节点」为什么并进「默认代理」

原先另有一个 `🖐 手动节点` 组，装着「自动测速 + 各地区组 + 全部机场节点」，
作用是让人手动挑某一个节点用。它与 `🚀 默认代理` 的差别只有一条：
后者不含机场节点、不能逐个挑。

既然默认代理本身就能逐个挑节点，两个组就没有存在必要了。现在：

- `🚀 默认代理` = ⚡️ 自动测速 → 6 个地区组 → 🌍 欧洲 → 2 个机房组 → 6 个本地机房节点
  → 全部机场节点（205 个，按名称排序）；
- 原本引用「手动节点」的服务组（人工智能、开发工具、社交通讯、国际影音、TikTok、
  海外游戏、支付理财、邮箱密码）改为引用「🚀 默认代理」，位置不变
  （其中支付理财与邮箱密码两个组后来已撤掉，出口由 🧠 人工智能 组承担）；
- `🖐 手动节点` 这个组已删除。

组数从 24 降到 23，客户端里少一层菜单，手动挑节点的路径没丢。


### Steam 下载为什么要单独钉香港

`geosite/steam@cn` 只有 19 条，收的是 Steam 中国（完美世界运营那套）的域名：
`+.steamserver.net`、`+.steamusercontent.com`、`+.alibaba.cdn.steampipe.steamcontent.com` 等。
**全球下载 CDN 不在里面**——`cache.steamcontent.com` / `*.steamstatic.com` 不在任何
直连集合里，原本落"未列出 → 默认代理"。

现在三条都指向 🇭🇰 香港，且排在 `cn → DIRECT` 之前：

```
DOMAIN-SUFFIX,steamcontent.com,🇭🇰 香港
DOMAIN-SUFFIX,steamstatic.com,🇭🇰 香港
RULE-SET,steam-cn,🇭🇰 香港
```

顺序有讲究：域名精确规则比规则集优先，规则集比 `cn` 优先，三者都在直连集合之前，
所以 Steam 的下载流量不会又被 `cn` 直连掉。

### 规则顺序：七段结构

规则从上往下**第一条命中即生效**，所以顺序本身就是分流逻辑。现在 97 条规则按七段排：

| 段 | 条数 | 内容 | 为什么在这个位置 |
| --- | --- | --- | --- |
| 1 网络层直连 | 12 | `private` / `private-ip` / `dns-direct` / `self-hosted` / `mirror-accelerate` / 组播与本地 IP / `direct-ports` / `connectivity-check` | 最基础的免代理项，放最前保证不被别的规则截胡 |
| 2 设备专属 | 6 | Lvsp 那 5 台设备专用的直连与代理 | 只对特定设备生效，与其它段不重叠 |
| 3 本地进程直连 | 15 | qBittorrent / Transmission / deluge / syncthing / Tailscale / UURemote | 按进程匹配，与域名规则互不冲突 |
| 4 强制代理与地区敏感 | 17 | 广告过滤 ×2、SteamCN 直连、账户域名、AI、强制代理清单、Steam 香港、PrivateTracker | 优先级最高的一段 |
| 5 国内与日本线路 | 13 | `cn-services` / `ai-cn` / `apple-cn` / `cn.bing.com` / `microsoft-cn` / `games-cn` / `pt` / `trackers` / `cn` / `XiaoMi` / `cn-ip` / `jp` / `kr` | 国内直连集合必须排在服务集合之前 |
| 6 服务分类 | 31 | AI / 谷歌 / 开发工具 / 社交通讯 / 国际影音 / 海外游戏 / 苹果 / 微软 / Docker / WhatsApp | 按服务类型分流 |
| 7 尾例与兜底 | 3 | `jianpian.tv` / `xgplay1.com` / `MATCH` | 兜底永远最后 |

**三条硬约束**，改顺序前先看这三条：

1. **`MATCH` 永远最后**。
2. **国内直连大集合必须排在服务集合之前**。上游 geosite 里 `apple@cn` ⊂ `apple`、
   `microsoft@cn` ⊂ `microsoft`、`games-cn` ⊂ `games`、`ai-cn` ⊂ `ai`，
   反过来排这四个国内集合会整体失效，国内 Apple / 微软 / AI / 游戏站点改走海外出口。
3. **强制代理清单（`proxy` / `proxy-domain`）排在普通直连集合之前**，但排在
   `PrivateTracker` 之前——见下面的落位说明。

### 本轮新增的 5 个集合

| 规则集 | 条数 | 目标 | 落位 | 理由 |
| --- | --- | --- | --- | --- |
| `AWAvenue-Ads` | 第三方成品库（mrs） | REJECT / 🛑 广告过滤 | 第 4 段**最前** | 广告拦截要先于所有分流判定 |
| `ads-minimal` | 4 | REJECT / 🛑 广告过滤 | 第 4 段第 2 位 | 最小广告集，兜底 |
| `PrivateTracker` | 248 | DIRECT | 第 4 段**末尾** | 私有 tracker 直连，避免 tracker 请求暴露代理出口 IP |
| `SteamCN` | 17 | DIRECT | 第 4 段**段首**（广告两条之后） | Steam 中国区资源直连 |
| `Docker` | 7 | 🚀 默认代理 | 第 6 段开发工具区（`devtools` 之后） | `docker.io` / `docker.com` 国内访问要走代理 |
| `Whatsapp` | 17 | 💬 社交通讯 | 第 6 段社交区（`social` 之后） | WhatsApp 归社交类 |

前两个集合各有两条规则：**Stash 三平台用 `REJECT` + 提前拒绝**，其余平台用
「🛑 广告过滤」策略组，详见上文「广告 → REJECT」的双轨说明。

`AWAvenue-Ads` 取自 `TG-Twilight/AWAvenue-Ads-Rule`，用的是
`Filters/AWAvenue-Ads-Rule-Clash-No.Unwelcome.mrs`（不含 Unwelcome 类，只留纯广告）。
面板抓取后校验 sha256 与源文件一致（`7a14912b…`），mrs 原字节入库、原样下发。

其余四个取自 blackmatrix7 `ios_rule_script`（上游应用集合层），行为 `classical`。

两个落位不是随手排的，是实测出来的：

- **`PrivateTracker` 必须排在 `proxy-domain` 之后**。它含 `DOMAIN-KEYWORD,torrent`，
  而 `proxy-domain` 里有 11 个含 torrent 的域名（`bittorrent.com`、`qbittorrent.org`、
  `torrentz.eu`、`torrentprivacy.com`…）。排到前面的话，这 11 个域名会从"强制代理"
  掉成"直连"，这些站在国内是打不开的。
- **`SteamCN` 必须排在 `steam-cn` 与 `steamcontent.com` / `steamstatic.com` 之前**。
  blackmatrix7 的 `SteamCN` 与上游 `geosite/steam@cn` 重叠 13/17 条，
  排后面的话只有 4 条能真正直连。

第 4 段内部的顺序约束（从前往后）：广告过滤两条 → `SteamCN` → 账户域名类
（`apple-intelligence` / `payment-finance` / `PayPal` / `mail-password`）→ `tiktok` →
地区敏感与强制代理（`biliintl` / `onedrive` / `proxy` / `proxy-domain`）→ Steam 香港三连 →
`youtube-dubbing.com` → `PrivateTracker`。`tiktok` 排在账户域名之后、广告之前，
这样 TikTok 相关的广告域名不会被 `tiktok` 集合抢先。

### SteamCN 上线后，Steam 香港三连退化成半死规则

`SteamCN` 排在第 4 段最前，它的 17 条全部直连，后面的香港三连只剩零头：

- `RULE-SET,steam-cn` 只剩 6 条独有域名还走香港（`csgo.com.cn`、`dota2.com.cn`、
  `client-update.queniuqe.com`、`alibaba.cdn.steampipe.steamcontent.com`、
  `lv.queniujq.cn`、`gstore.val.manlaxy.com`）；
- `DOMAIN-SUFFIX,steamcontent.com` 与 `DOMAIN-SUFFIX,steamstatic.com` 被
  `SteamCN` 里的同名后缀完全覆盖，这两条不再生效。

如果后面想让 Steam 全球下载 CDN 回到香港，把 `SteamCN` 挪到这两条之后即可。

## 五、规则与规则集的规范核对

规则与规则集按下面四份官方文档逐项核对过（核对脚本按官方表格重建白名单，不靠记忆）：

- Stash：<https://stash.wiki/rules/rule-types>、<https://stash.wiki/rules/rule-set>
- Mihomo：<https://wiki.metacubex.one/config/rules/>、<https://wiki.metacubex.one/config/rule-providers/>

| 检查项 | 依据 | 结论 |
| --- | --- | --- |
| 规则类型在引擎白名单内 | 两份 rule-types 列表 | 97 条全部在 Stash 与 Mihomo 双方白名单内 |
| `MATCH` 只有一条且在最后 | 客户端「从上往下第一条命中」 | 是 |
| 规则的 `target` 都存在 | 客户端加载时校验组名 | 23 个组全部存在，无悬空引用 |
| `RULE-SET` 引用的来源都存在 | rule-providers | 全部命中，无悬空引用 |
| 来源的 `behavior` × `format` 组合合法 | Stash rule-set 的格式表 | 全部合法（`mrs` 只配 `domain` / `ipcidr`） |
| 来源内容格式与声明一致 | — | 逐个取内容核对，`mrs` 用 sha256 与源文件比对 |
| `behavior` 与内容里的规则类型匹配 | 同上 | 匹配（`domain` 里无 IP，`ipcidr` 里无域名） |
| `no-resolve` 只挂在 IP 类规则上 | rule-types「规则选项」 | 是 |
| **`ipcidr` 行为规则集都加了 `no-resolve`** | Stash：「ipcidr 类规则集支持 no-resolve 参数」 | **原 `kr` 漏加，已修** |
| 产物里 `path` 后缀与 `format` 一致 | 客户端按扩展名推断格式 | 一致 |
| 组名 / 规则值 / 来源名不含逗号等字符 | 规则行是逗号分隔文本 | 均无 |
| 未被引用的来源、已停用的来源 | — | 均无 |

**`kr` 漏加 no-resolve**：这个来源是 `ipcidr` 行为（1 条韩国 IP 段），不加 `no-resolve` 时
客户端遇到域名请求会先为它做一次 DNS 解析再判断 IP 是否命中，纯属无谓解析。
另外三个 `ipcidr` 来源（`private-ip`、`cn-ip`、`telegram-ip`、`apple-push-ip`）本来就加了。

### Stash 独有能力：no-track 与 pre-matching

Stash 有两个 Mihomo 不认的规则选项，面板已支持：

- `no-track`：命中的连接不记入客户端连接列表，流量统计照常。适合心跳、探测、广告这类
  高频而无需查看的请求。
- `pre-matching`：让 REJECT 在连接建立之前生效（DNS 阶段就空应答、SYN 包直接回 RST）。
  官方原话是「广告、统计类域名的请求量大、重试快，这是 iOS 下减少内存和 CPU 占用最直接的手段」。

**产物里只有 Stash 平台带这两个修饰符**。Mihomo 的规则参数只有 `no-resolve` 与 `src`，
所以 `compiler/render.py` 的 `_rule_line()` 按引擎分支输出。

顺带一个实测结论：**Mihomo 遇到未知的规则参数不会失败**。用容器里的
mihomo v1.19.32 跑 `mihomo -t`，带 `no-track`、带 `pre-matching`、连乱写的
`bogus-param-xyz` 都通过校验、退出码 0。既然如此，产物里干脆不写这两个参数，
语义更清楚，也不依赖 Mihomo 的宽容行为。

**pre-matching 的两个硬门槛**（面板在接口层与构建层都拦住了）：

1. 目标必须是 `REJECT` / `REJECT-DROP` 字面量，用策略组会让客户端配置加载失败；
2. 只能用在"连接建立前就能判断"的规则类型上（域名类、GEOSITE、IP-CIDR、GEOIP、
   IP-ASN、DST-PORT、SRC-IP、SRC-PORT、NETWORK、RULE-SET、AND / OR / NOT）；
   `PROCESS-NAME` / `PROCESS-PATH` / `USER-AGENT` / `URL-REGEX` / `PROTOCOL` / `SCRIPT`
   依赖建连后才有的信息，带它会报错。

**版本要求**：pre-matching 官方标注 `iOS/tvOS 3.7+ / macOS 4.4+`。
版本太旧的客户端遇到这个参数可能直接加载失败（客户端起不来），所以这个开关**默认不开**，
由使用者在确认自己设备的版本后再勾。

**兜底规则（MATCH）不能加 no-track**：它命中的是所有未列出的流量，勾上等于让客户端
不记录任何连接。接口层直接拒绝，批量修改时自动跳过。

**广告过滤怎么用上 pre-matching**：官方要求目标只能是 `REJECT` 字面量，
而面板的广告规则原本指向「🛑 广告过滤」策略组（成员里第一个是 REJECT，但目标是组）。
办法是**按引擎平台分两条规则**：

| 适用引擎平台 | 目标 | 修饰符 |
| --- | --- | --- |
| Stash-iOS / Stash-tvOS / Stash-macOS | `REJECT` | `pre-matching` + `no-track` |
| Stash-Android / Stash-Windows / Mihomo 三端 | 🛑 广告过滤（策略组） | `no-track` |

`pre-matching` 只对版本达标的客户端有意义（官方标注 iOS/tvOS 3.7+、macOS 4.4+），
Stash-Android 与 Stash-Windows 的版本线不同，暂不纳入，留在策略组那条上。
策略组本身也限定到同样的 5 个平台，Stash 三个平台的客户端里就不会出现闲置菜单项。

同一个规则集在互斥平台各挂一条不算「规则重复」：面板的重复判定只看适用范围
有没有交集（`"*"` 是包含全部的哨兵，按通配处理）。

## 六、Geo 数据：面板用不上，但客户端还在下

产物里**没有任何 GEOSITE / GEOIP 规则**（规则类型分布：RULE-SET 59 条、PROCESS-NAME 15、
DOMAIN-SUFFIX 13、IP-CIDR 6、IP-CIDR6 1、DOMAIN 1、MATCH 1），`dns.fake-ip-filter` 34 条里也没有 geosite 引用。
也就是说客户端那套 `geosite.dat` / `geoip.dat`（合计 30 MB 量级）**当前完全用不上**，
但引擎默认配置里 `geo-auto-update: true` + `geodata-mode: true` 仍然开着，客户端会照旧
去更新它（实测 Mihomo 启动时就会去查 Geo 文件的更新时间）。

官方 Mihomo 示例给的是 `geo-auto-update: false`。**面板目前保持 true**，理由：

- 改 false 的收益只是一次性省下每台设备几十 MB 流量（此后只查不下载）；
- 代价是日后有人在界面里加一条 GEOIP / GEOSITE 规则时，客户端可能没有 Geo 数据，
  规则**静默不命中**——这类"平时没事、加了规则才炸"的坑比省流量难查得多。

要省这份流量，把「引擎默认配置」层的 `geo-auto-update` 改成 false 即可，
但改之前先确认自己不会加 GEOIP / GEOSITE 规则。

## 七、空组保护：实测结论是"必须保留"

在 NAS 上用 Mihomo 核心直接实测（`mihomo -t`）：

| 组的形态 | 结果 |
| --- | --- |
| 没有任何成员的 `select` | ❌ `proxy group[0]: xxx: \`use\` or \`proxies\` missing` |
| 没有任何成员的 `url-test` | ❌ 同上 |
| 没有任何成员的 `fallback` / `load-balance` | ❌ 同上 |
| `proxies: []`（空数组） | ❌ 同上 |

也就是说：**空的策略组不是"这个组失效"，而是整份配置加载失败**，客户端直接起不来。
面板在 `url-test` / `fallback` / `load-balance` 组末尾追加的占位节点
（`空组保护`，指向 `127.0.0.1:1`，永远连不通）是唯一能保证组非空的手段。

因此占位节点**保留**。另外补了一道产物级校验：产物里任何没有 `proxies` 也没有
`use` 的策略组，构建时直接报错——内联模式下来源节点被过滤光时组会变空，
这类问题必须在构建期挡住，不能等到设备上才发现。

## 八、相关约定

- 规则集一律 `format: mrs`（二进制），产物里的 `path` 后缀跟格式一致
  （`./rules/cn.mrs`），避免客户端按文本格式解析。
- 新增远程规则集的地址固定为
  `https://cdn.jsdelivr.net/gh/MetaCubeX/meta-rules-dat@meta/geo/{geosite|geoip}/<名称>.mrs`。
- 规则集内容由面板抓取后下发，设备不直接访问上游；上游不可达只影响面板抓取。
