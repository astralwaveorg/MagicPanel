# MagicPanel 接入审计与优化方案（节点测速 / 解锁探测 / 重命名分类）

> 2026-11-19 · 面向「全自动、周期性、高准确率」的节点质量流水线：
> 三级漏斗（连通延迟 → 下载吞吐 → 解锁矩阵）→ 结构化能力分类 → 规范化重命名
> → 直接可用的 Mihomo 节点列表与分类文件，供 MagicPanel 构建流程消费。

---

## 1. 项目结构与构建链路审计

### 1.1 节点输入源

| 来源 | 存储 | 抓取 | 说明 |
| --- | --- | --- | --- |
| 机场订阅 | `sources.snapshot_enc`（Fernet 密文） | `services/updater.py::refresh_source` | 解密后是 Clash YAML（`proxies:`）或 base64 URI 列表；`source_nodes.extract(bytes)` 解析 |
| 本地节点 | `local_nodes` 表（`params_enc`/`extra_yaml_enc`） | 手工录入 | `local_nodes.render_proxy(node, engine)` 直接产出 Mihomo 节点字典 |
| 节点目录 | `node_catalog` 表 | 构建时从快照同步 | 规范化后的稳定身份（`node_uid` / `emit_name`） |

**关键事实（本次审计确认）**：`sources.snapshot_enc` 解密后是**文本**，而
`services/source_nodes.extract()` 的入参是 **bytes**——传文本会抛
`AttributeError: 'str' object has no attribute 'decode'`。该异常此前被
`except: continue` 吞掉，导致「机场节点在候选列表里整体消失」。
2026-11-18 已修（`unlock_check.py` 两处调用点 + 回归测试）。

### 1.2 构建 / 发布链路

```
POST /api/v1/builds  →  builds.create_build()
   ├─ collect_snapshot(conn)            # 收集全库策略快照 + 策略指纹
   ├─ validate.validate_policy(snapshot) # 逐方案校验（引用/顺序/作用域）
   ├─ render.render_target(...)          # ★ 节点名在此规范化 + 加能力徽章
   ├─ tester.validate_config(text)        # Mihomo 目标跑 mihomo -t
   └─ 产物落盘 data/builds/<id>/<target>.yaml
          ↓
   releases.publish_to_testing / publish_to_production
          ↓
   GET /feed/<token>/config.yaml          # 设备拉取（叠加设备独立配置）
```

**节点名在构建链路里的位置**：`render.py` 481-510 行做「节点名规范化 + 徽章」，
节点本体名与组成员引用共用同一张 `rename_map`，所以客户端里看到的组员名与
节点名永远一致。**这是接入解锁/测速结果的天然挂载点**——不需要另建一条
「先测再改名再构建」的旁路。

### 1.3 下游消费

- `data/builds/<id>/*.yaml`：构建产物（客户端订阅源）
- `data/unlock_cache.json`：解锁检测缓存（按**原始节点名**索引）
- `sources.test_results`（`{name: delay_ms}`）：测速延迟缓存

### 1.4 结论（对规格的回应）

> 「重命名后的节点列表在构建时如何被引用」——**已经是这样做的**：
> 检测结果 → 分类 → `rename_map` → 产物里的节点名与组成员引用。
> 本次要做的是把「测速 + 精细化解锁」的结果也接进同一个 `rename_map`，
> 并把漏斗门禁接在探测之前。

## 2. 运行环境与网络环境适配分析

### 2.1 运行环境

- **NAS（10.0.1.2）**，容器 `magicpanel`，Python 3.12 + Mihomo 核心（`data/bin/mihomo`）
- 容器内直连出网；NAS 宿主 `~/.docker/config.json` 曾把构建代理指向已停用的
  `10.0.1.8:7890`（2026-11-18 已由 `deploy.sh` 用临时 `DOCKER_CONFIG` 绕开）

### 2.2 关键网络约束（必须区分的两条流量路径）

| 路径 | 发起方 | 出口 | 风险 |
| --- | --- | --- | --- |
| **A. 面板自身**（拉订阅、更新规则集、写产物） | 容器进程 | NAS 直连（路由器 OpenClash 透明代理） | 订阅源本身可能需要代理；`tester.direct_env()` 刻意清空代理变量，避免测速绕代理 |
| **B. 被测节点**（访问流媒体/AI 目标） | 临时 Mihomo 核心的本地入站 | **被测节点自己的出口** | 代理套娃、DNS 污染、分流规则劫持 |

**实现约束**（写代码时必须守住）：

1. 探测请求**只能**经被测节点转发：本地 `mixed-port` → 节点 → 目标站。
   面板自身访问目标站（如测出口 IP）走直连，不能混淆两者。
2. 核心进程必须 `direct_env()`（清空 HTTP_PROXY 等），否则节点的 CONNECT
   请求会先被宿主代理截走 → 测出的是代理的延迟，不是节点的。
3. DNS：核心配置里 `dns.enable=false` 或显式交给系统解析，避免 Fake-IP/
   污染 DNS 影响「能否访问真实站点」的判定。
4. 端口：每次探测用 `_free_port()` 取空闲端口；多批次并行时端口不冲突。

### 2.3 现存实现的最大性能缺陷

**每检测一个节点就起一次 Mihomo 核心**（`unlock_check._exit_proxy` 为每个
节点生成临时目录、起核心、等端口就绪、跑完再杀）。实测 **约 7 秒/节点**
（起核心 ~4s + 19 项请求 ~3s）。199 个节点 → 约 23 分钟，且 199 次核心启动
对磁盘与 CPU 都是无谓消耗。

**优化**：一个核心实例 + `select` 组切换节点。Mihomo 的
`PUT /proxies/<group>` 可切换组内选中节点，之后所有本地入站请求都走新节点。
单节点切换成本 ≈ 0.1s，整批 199 节点可压到 **2-4 分钟**。

## 3. 性能、并发与防风控：三漏斗

### 3.1 漏斗设计

```
候选节点（快照 + 本地节点，去重）
   │
   ├─【一级·连通与延迟】Mihomo delay API，超时 5s（QUIC 类 8s），重试 1 次
   │    门槛：delay < 600ms 且可连通                      → 不达标直接淘汰
   │
   ├─【二级·下载吞吐】对达标节点各取一次固定大小文件，测平均速度
   │    门槛：>= 2 MB/s（16 Mbps）                        → 不达标归入「备用池」
   │
   └─【三级·解锁矩阵】只对同时达标的节点跑 20+ 平台探测
        门槛：产出结构化能力标签                          → 用于分类与命名
```

**为什么先测速后探测**：解锁探测要打 20+ 个真实站点（Netflix、Disney+、
ChatGPT…），单 IP 触发频率高会被风控（实测 Claude/Perplexity 对无头请求
直接 403 人机校验）。先用测速淘汰掉 60-80% 的慢节点/坏节点，能显著降低
目标站点侧的触发量，也缩短总时长。

### 3.2 并发与防风控

| 参数 | 默认 | 配置键 | 说明 |
| --- | --- | --- | --- |
| 测速并发 | 16 | `probe_concurrency` | 沿用现有 `tester.CONCURRENCY`；单实例内切节点，**不**多实例并行 |
| 探测并发 | 4 | `unlock_concurrency` | 每个节点 20+ 请求并发 4，避免瞬时打满 |
| 单请求超时 | 8s | `probe_timeout_ms` | 现 `CHECK_TIMEOUT=8.0` |
| 重试 | 1 | `probe_retry` | 仅对「超时/5xx」重试；**403/地区特征不重试**（重试只会加深风控） |
| 测速文件大小 | 5MB | `speed_test_bytes` | 够算平均速度，又不至于太慢 |
| 每轮节点上限 | 200 | `probe_round_limit` | 防止一次跑太久 |

### 3.3 误判控制

| 现象 | 判定 | 处置 |
| --- | --- | --- |
| 超时 / 连接失败 | `unreachable` | 重试 1 次，仍失败则淘汰 |
| 429 / 5xx | `error`（限流或抖动） | 重试 1 次；仍失败标 `error`，**不算封锁** |
| 403 + Cloudflare 特征 | `blocked?`（人机校验） | 标 `unknown`，**不算区域拒绝**（2026-11-18 线上实证：Claude/Perplexity 全部如此） |
| 403 + 正文含地区词 | `blocked`（区域限制） | 确认为封锁 |
| 200 + 正文含地区码 | `unlocked` + 提取地区码 | 记录地区码（如 `US`/`HK`） |

## 4. 多协议兼容性

由 **Mihomo 内核**统一承接，现有 `tester.py` 已验证支持
SS / SSR / VMess / VLESS / Trojan / Hysteria2 / TUIC / anytls 等
（`_start_failure` 会解析 `unsupport proxy type` 并给出明确原因）。

**要求**：

- 不支持/解析失败的节点**记录原因**（`unsupported: <type>` / `parse_error: ...`），
  **不静默丢弃**——面板上要能看到「这批节点里哪些是内核不认的」。
- QUIC 类协议（hysteria/hysteria2/tuic）握手慢，延迟预算放宽到 8s。
- 单个节点配置错误不能拖垮整批：核心启动失败时按 `proxy (N):` 定位并剔除
  该节点后重试（`_start_failure` 已实现该路径）。

## 5. 重命名、分类与输出契约

### 5.1 命名格式（扩展现有格式）

```
🇺🇸 [神龙机场] 美国 🔓🎬 01          # 现有：地区 + 机场 + 国名 + 能力徽章 + 序号
🇺🇸 [神龙机场] 美国 🔓🎬 01 120M/45ms # 追加：吞吐(MB/s) / 延迟(ms)
```

- 吞吐取整（`120M`），延迟取整（`45ms`）；未测到速度的节点不追加该段。
- 命名合法性：不含 `,`（Mihomo 规则语法分隔符）、`#`、`=`；长度上限 80 字符，
  超长截断原始标识部分；同名冲突追加 `-02`、`-03`（在序号段解决）。

### 5.2 分类标签体系

| 标签 | 含义 | 来源 |
| --- | --- | --- |
| 🔓 | AI 类（≥4/6 项确认解锁，无明确区域拒绝） | 三级探测 |
| 🎬 | 流媒体核心项（≥5/8 项确认解锁） | 三级探测 |
| 📺 | Netflix 高级版目录可达 | 三级探测 |
| 🌍 | 识别出的地区码（如 `US`/`HK`） | 各探测器 |
| ⚡ | 吞吐 ≥ 2MB/s（达标池） | 二级门禁 |
| 🐌 | 吞吐 < 2MB/s（备用池） | 二级门禁 |

### 5.3 输出契约

| 产物 | 路径 | 内容 | 写入方式 |
| --- | --- | --- | --- |
| 分类文件 | `data/node-classes/<tag>.yaml` | 达标池 / 各能力组的 Mihomo `proxies` | `tmp → 校验 → mv` 原子替换 |
| 快照 | `data/node-classes/snapshot-<ts>.json` | 本轮全量结果（对比变化用） | 追加写，保留最近 N 份 |
| 构建消费 | `sources.test_results` / `unlock_cache.json` | 现有缓存继续用 | 事务写 |

**Mihomo 输出校验**：`yaml.safe_load` 后逐节点检查必需字段
（`name`/`server`/`port`/`type`），重名检查，非法字符检查——校验不过就**保留旧文件**
（不写坏产物）。

6. **调度器周期任务** + 构建流程消费

## 8. 假设与需人工确认项

- **假设**：解锁探测的目标站仍以「状态码 + 正文特征」判定，不引入浏览器
  指纹（无头环境下 Cloudflare 挑战无法稳定通过，引入只会增加误判率）。
- **需确认**：Netflix「自制剧 / 全库」判定依赖正文里的 `isOriginal`/`isAvailable`
  字段，Stash/Netflix 未登录页面的字段可能随时间变化——若判定失效，降级为
  「可访问 + 地区码」，并在日志里标注降级原因。
- **需确认**：吞吐测试的固定文件源（建议用 Cloudflare 的 `speed.cloudflare.com`
  或机场自己的 CDN）；源不可用时应改用「连接建立时间 + 小文件下载」近似。
- **需确认**：199 节点的完整一轮探测在 NAS 上的实际耗时与对家宽带宽的影响
  （每节点一次 5MB 下载 = 约 1GB 流量/轮）。
