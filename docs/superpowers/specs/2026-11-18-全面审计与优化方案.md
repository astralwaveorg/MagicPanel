# MagicPanel 全面审计与优化方案（2026-11-18）

> 审计范围：全仓库只读审计 + 测试基线实测。审计对象：前端 18 个视图 / 14 个组件、
> 后端 18 个路由文件（179 个路由操作）/ 47 个 services、构建发布链路、调度自动化、测试与 CI、文档一致性。
> 本文只做方案，不含任何已执行的改动。问题定位格式 `文件:行号` 以 HEAD=73eed34 工作区为准。

## 0. 基线实测（审计起点）

| 项 | 结果 |
| --- | --- |
| 代码版本 | `main` @ 73eed34，工作区干净 |
| 后端测试 | `pytest tests -q`：**844 passed / 9 skipped**（1 分 57 秒） |
| 前端测试 | `vitest run`：**9 文件 68 tests 全绿**（1.9 秒） |
| 前端构建 | 3.0 秒；**主包 1,077.90 kB（gzip 354.48 kB）**，超 500 kB 警告 —— Element Plus 全量引入且无分包 |
| 数据风险 | 未发现 P0 级「已在线上造成数据损坏」的问题；发现的 P0 全部是**失败路径下的链路风暴与卡死** |

**总体判断**：这套代码的底子很好——发布状态机有数据库部分唯一索引兜底、发布 CAS+幂等票据齐备、
凭据全链路密文、事务纪律在 updater/scheduler 是铁律、备份恢复测试是全仓库最强项。
短板高度集中在三处：**自动化失败路径没有退避与持久化**（两条 P0 风暴都源于此）、
**失败对用户不可见**（无通知、空态与错误态混用、配置保存≠配置生效无提示）、
**约定没有被同一把尺子量到所有角落**（错误契约四种形态、界面约定在后改的页面失守）。

## 2. P0 — 数据与链路风险（6 项，先于一切优化）

### 2.1 链路与调度（3 项）

**P0-1 自维护仓库同步：写事务包网络操作 + 失败重试风暴**
- 位置：`server/app/services/scheduler.py:225-226`、`server/app/services/repo_sync.py:170-197`、`server/app/routers/deps.py:131-141 / 234-248 / 251-264`
- 机制：`repo_sync.run_sync`（含 git pull/commit/push，单条 git 超时 120s）整体运行在 `db.tx(immediate=True)` 里。WAL 下读不受阻，但**所有 API 写请求排队**。更糟的是失败路径先 `_record`（写 `deps_last_sync_at`）再 `raise`，异常传播导致外层事务回滚——时间戳永远不推进，调度器每 30 秒都判定「到期」，网络故障期间变成每 30 秒一次的持锁 git pull 无限重试。`updater.py`/`builds.py` 注释里明确写着「网络请求不得进事务」的项目纪律，deps 路由违反了它。
- 改法：run_sync 拆三段；deps 路由的 clone/commit/sync 同样把 git 移出 `db.tx()`。

**P0-2 自动发布失败无退避：每 30 秒重建一个完整构建**
- 位置：`server/app/services/scheduler.py:416-422`
- 机制：发布异常时把 `auto_build_last_attempt` 清空以「下轮立即重试」，但发布持续失败时（典型：被 P0-1 的写锁挤爆 `database is locked`），每个 tick 都完整跑 create_build（含每个 Mihomo 产物一次 `mihomo -t`）+ 产物落盘 + 构建记录膨胀（retention 截 30 条等于持续互相驱逐）。
- 改法：指数退避 + 复用最近同 policy_sha 构建。

**P0-3 门禁默认值组合陷阱：自动发布可被永久卡死**
- 位置：`server/app/services/scheduler.py:540`（全局 `auto_test_sources` 默认 "0"）vs `:237-287`（`_publish_tests_ready` 只认来源级开关）
- 机制：`updater.refresh_source` 成功后清空 `test_results` 并注释「调度器会在同一轮立即补测」，但补测被全局开关（默认关）挡住。任何开启「只分发可用节点」的来源，每次抓取成功后门禁条件「测速新于抓取」永不成立 → 自动发布静默卡死，唯一痕迹是 automation_runs 里循环 build_error。这正是 2026-11-04 线上事故（空来源卡门禁）的同族问题，那次修了「没有节点的来源」，没修这个默认值组合。
- 改法：全局测速关闭的来源并入门禁 skipped；UI 在开启 filter_unavailable 时提示依赖。

### 2.2 前端数据风险（2 项）

**P0-4 基础配置页切换作用域丢未保存改动** — `src/views/ArtifactConfig.vue:739`
- `select()` 切换左侧层级列表（含移动端下拉）时不检查未保存改动，直接用新层数据覆盖 `doc/raw`。基础配置是整个产物的基线，误触一次丢掉整层编辑。
- 改法：切换前对比 `changedCount`，有改动弹 confirm。

**P0-5 设备/平台层「保存并构建发布」直接发生产** — `src/views/ArtifactConfig.vue:846`
- 仅 builtin 层有确认；设备/平台层点击后直接构建并发布到所选环境（默认生产），无「将发布到生产，影响所有设备」二次确认。与 Builds.vue 的发布确认文案不一致。

### 2.3 配置健壮性（1 项）

**P0-6 settings 数值键无校验，可打挂登录** — `server/app/routers/misc.py:245-290`（校验缺口）、`server/app/routers/deps.py:25`（爆炸点）
- `session_ttl_hours` / `profile_update_interval` 是可编辑键但只校验布尔与个别枚举；写成非数字后 `create_session`、`config_stale` 全部 ValueError → 登录接口 500。一条合法请求把面板登录打挂。
- 改法：put_settings 对数值键做类型+范围校验。

## 8. 验收标准

- **功能不回退**：844 后端用例 + 68 前端用例全绿；阶段一/四涉及的发布与门禁改动各配新回归用例。
- **链路韧性**：断网 10 分钟 → 无写锁 500、无重试风暴、恢复后一轮追平；发布持续失败 → 退避间隔递增且横幅可见。
- **可观测**：任何自动化失败在概览页 5 秒内可见（不点子页面）；「配置已保存」与「产物已生效」两个状态不再混淆。
- **交互一致性**：交接文档界面约定逐条核对通过（列宽/op-grid/配色/用词）；桌面 + 手机宽度实测主要页面。
- **包体**：主包 gzip 从 354 kB 降到 200 kB 以下。
- **文档**：接口清单由脚本生成且与实际一致；README 与代码无冲突数字。
