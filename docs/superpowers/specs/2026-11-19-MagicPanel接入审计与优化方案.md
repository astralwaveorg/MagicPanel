# MagicPanel 接入审计与优化方案

审计基线：2026-11-19，Git `95f42e3`。旧版《节点质量流水线》是设计记录；以下结论以实现和生产只读查询为准。

## 结论

当前有三段测速、33 项左右的平台探测、Mihomo 单实例切换和名称摘要，但**没有实现用户要求的周期复测、可信解锁分类和可直接交付的达标节点池**。线上漏斗和两种旧自动任务均关闭；目录有 218 条记录，质量文件仅 64 条（38 延迟未通过、1 吞吐未通过、25 跑完平台探测），含历史记录，不能当作当前覆盖率。名称和质量缓存按展示名关联，凭据或节点线路变动后可能沿用旧结果。

## 输入、构建和发布

订阅抓取后存入加密的 `sources.snapshot_enc`，解析器将 Clash YAML 或节点 URI 转为代理字典。本地节点从 `local_nodes` 渲染，节点目录保存稳定标识、版本和产物名称。构建收集数据库快照，按方案、引擎和设备解析引用；内联节点进入 `proxies`，动态节点通过 `proxy-providers` 引用分发端点。静态检查和 Mihomo 校验后，测试与生产各自移动发布指针。不能用另一份未经同样校验的 YAML 替换生产订阅。

现状：构建读取质量文件来拼速度摘要，徽章取另一份解锁缓存；动态 provider 对照原名取徽章，缺少同等摘要，且其 ETag 未覆盖实际变化后的输出。原有「只分发可用节点」基于旧延迟结果，和新门禁不是同一套规则。适合先在现有构建旁接入同一份质量快照，显式出达标池和能力分组，保留原分流与固定引用；任何自动删节点或改变现有规则目标都要先验证空池及引用。

## 运行与流量

NAS 为 Debian 12、Linux 6.18.18.c1186-trim x86_64，应用在 Docker 内以受限身份运行，Python 3.12.16，已找到可执行的 Mihomo。容器 DNS 走 Docker 内部解析，所列上游是路由器；宿主默认路由也指向该路由器。家宽下行约 1 Gbps、上行通常 60–80 Mbps 为既有环境记录，本次未跑满带宽验证。

面板抓取订阅、规则和浏览站点走宿主路由；经探测核心访问目标服务走回环代理端口，由选中的节点转发。关闭进程级代理变量只排除显式代理，**不能**排除 OpenClash 对节点服务器连接的再次代理，也不能证明节点服务器域名按预期解析。上线验收应抽查不同协议的节点端点及网关实际出站；未核对前，延迟/速度只能注明「从 NAS 当前网络测得」。不改路由、DNS、宿主防火墙或客户端分流。

## 执行和防误判

- 一级严格小于 600 ms；二级按完整文件有效字节计算，默认门槛 2 MB/s（2,000,000 B/s，即 16 Mbps）。达标和失效由实际测试阶段记录，不用默认值翻译自定义结论。
- 单核心、单节点、单下载；同节点的平台请求可有限并发，切节点前收完所有结果。对连接异常、超时和 5xx 做有限重试；地区拒绝、人机校验与 429 不追加压力。任务按日期重新检查，优先未测及最旧结果，保持每轮节点上限、互斥和错误冷却。
- 身份变化要让旧结果失效。先适配当前构建和动态 provider 的共同命名口径，并把证据时间、分类和性能明确区分。不能把旧成功徽章当新能力，也不因一次故障把旧生产订阅清空。
- SS/SSR、VMess、VLESS、Trojan、Hysteria2、TUIC 等协议由安装的 Mihomo 版本承接。只声称已通过真实核心和样本验证的协议；带外部节点依赖或内核不支持的条目需单独报告，避免阻塞整轮。
- 区分主页有响应、明确区域限制、风控、网络失败与有能力证据。Netflix 目录测试不能替代播放；Disney+、Max、Prime Video、TikTok、Spotify、YouTube Premium 的实际播放、登录账号权益、免广告、直播/创作者资格要依赖账户或客户端验证，证据不足则留空或标未确认。不能用访问主页或返回 HTTP 200 发解锁徽章。AI 平台同样区分网页访问和账号可以使用。

## 交付与验证

用同一份已验证质量结果生成管理端列表和构建可选分组。候选输出须校验 YAML 与引用，私有文件使用 0600 权限，从同目录临时文件原子替换；快照仅存判定数据，不带代理凭据。空池与过期数据不能覆盖已有生产分流。通过面板已有调度器运行，避免再建一套 cron 与容器计划冲突。

全站按「来源 → 策略组与规则 → 基础/设备配置 → 构建、测试、生产 → 订阅」核对文案和关键操作。机械部分由 Claude Code 只读提出文案建议，当前 Codex 审查业务含义并实施。整批修改安排一次统一前后端验证，部署后抽查真实页面、接口、核心及运行开关；未完成真实播放和长期周期验收时如实说明。


## 实施与运行

1. 「网络体检 → 节点质量」可手动测一批或开启自动检测。生产初始设置为每批最多 3 个节点；建议先观察几个周期，再按 NAS 负载调整。失败节点约 6 小时后复测，其他结果默认 24 小时复测。
2. 导出依赖面板「系统设置」安装的 Mihomo。验证可用 `mihomo -t -f node-pools.yaml`；速度门禁用 `cd server && ../.venv/bin/python -m pytest tests/test_quality_funnel.py tests/test_probes.py tests/test_route_evidence.py -q` 验证。使用内置定时器，无需额外 systemd timer 或 cron。
3. 服务器网络优先展示与本次请求的主机名、源 IP、源端口吻合的 Mihomo 连接记录。可在容器环境设置 `MAGICPANEL_ROUTE_CONTROLLER` 为允许读取 `GET /connections` 的私网地址；Docker 经 NAT 时配置 `MAGICPANEL_ROUTE_SOURCE_IP` 为控制器实际看到的 NAS 源地址。需要认证时可挂载专用只读代理的令牌文件，并以 `MAGICPANEL_ROUTE_TOKEN_FILE` 指向它。无连接证据时尝试同域公开诊断，找不到就显示未获取；不把通用出口 IP 复制到每行。
4. 动态 provider 的质量命名单独由 `probe_quality_provider_names` 控制，默认关闭。该设置立即影响设备下次拉取，需生产发布权限。Mihomo 构建里的质量分组单独开关，默认关闭，和动态 provider 实时更新互不影响。
