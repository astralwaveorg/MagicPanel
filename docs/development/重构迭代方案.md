## 零、迭代概览

本轮是四块改动合在一起的一次迭代。

| 块 | 内容 | 性质 | 详细设计 |
| --- | --- | --- | --- |
| 一 | **菜单重排 + 页面改名**：侧边栏 13 项 → 12 项并重排；「产物配置 → 基础配置」「功能模块 → 拓展模块」「设置 → 系统设置」；「引擎平台」并入「基础配置」页 | 信息架构重构 | §一 |
| 二 | **拓展模块加来源类型**：内联内容 / 远程 URL，与「添加规则来源」同款 | 功能增强 | §三 |
| 三 | **构建发布与自动发布合并**：一个页面两个 tab；详情抽屉改成「发布测试」+「一键发布」 | 功能合并 | §二 |
| 四 | **自主维护**：magic-sets 从 submodule 变成运行时可配置、可替换的数据层 | 新功能 | [自主维护-设计方案](自主维护-设计方案.md) |

耦合点：块一的菜单里含块四的入口；块三的 tab 合并要改路由，与块一的路由重定向一起做。

> **首页交互已在本轮之前定稿**（平台筛选标签、分组折叠、规则来源详情预览），规范写在 §1.5。重构过程中的任何改动都不得把首页改回旧形态。

### 1.2 「引擎平台」并入「基础配置」

引擎平台不再有独立菜单项，改为「基础配置」页的**第一个 tab**：

```
基础配置
├── tab1  引擎平台    （原 Targets.vue：Stash/Mihomo × 各平台的目标清单与排序）
└── tab2  产物配置    （原 ArtifactConfig.vue：引擎默认/平台/设备三层配置）
```

理由：引擎平台是产物配置的骨架——每个目标对应一类客户端，产物按目标编译；没有目标就没有产物（构建会直接报「尚未配置任何引擎平台」）。放同一页比拆两页更符合认知。

tab 用 query 参数切换（`?tab=targets` / `?tab=artifact`），两个 tab 各自可直达。

## 二、构建发布与自动构建发布合并

### 2.1 页面结构

```
构建发布
├── tab「构建发布」      原 Builds.vue：构建列表 + 详情抽屉 + 发布历史 + 手动构建
└── tab「自动构建发布」  原 Automation.vue：定时任务配置 + 运行记录 + 最近自动发布
```

实现：`Automation.vue` 的内容整体搬进 `components/AutoBuildPanel.vue`（去掉页面标题那一行），`Builds.vue` 外层加 `el-tabs`，两个面板用 `v-if` 懒挂载。

tab 值走 query：`/admin/builds`（默认构建发布）、`/admin/builds?tab=auto`。

### 2.2 「立即发布」提升为页面级主操作

现在的「立即手动发布」按钮在自动发布页（`Automation.vue`），它触发一轮完整的自动任务（抓取 → 测速 → 构建检查 → 发布）。这是个**常用操作**，但它既不属于「手动构建发布」也不属于「自动构建发布」——它跨两者。

所以把它提升为**整个构建发布页面的独立主操作**，放在页面标题行右侧（与两个 tab 平级，两个 tab 都能点到）：

```
构建发布                                    [ tab: 构建发布 | 自动构建发布 ]   [ ⚡ 立即发布 ]
```

移动后的分工：

| 位置 | 放什么 |
| --- | --- |
| **页面标题行右侧** | **「立即发布」**（触发一轮自动任务：抓取 → 测速 → 构建 → 发布） |
| tab1「构建发布」 | 构建列表 + 「创建构建」按钮 + 详情抽屉（「发布测试」/「一键发布」）+ 发布历史 |
| tab2「自动构建发布」 | 纯配置：定时开关、抓取间隔、测速间隔、自动构建间隔、目标环境 + 运行记录 + 最近自动发布记录 |

「自动构建发布」tab 因此变成**纯配置页**，所有执行类动作都在别处，职责清楚。

**命名上要避开混淆**：页面级「立即发布」触发的是「自动跑一轮」，而抽屉里的「一键发布」是「把**已有的这个构建**发到测试和生产」——两者动作对象不同，名字相近容易误触。

| 按钮 | 位置 | 动作 |
| --- | --- | --- |
| 立即发布 | 页面标题行 | 触发自动流程，产出**新**构建并发布 |
| 一键发布 | 详情抽屉 | 把**当前这个**构建发到测试 + 生产两个通道 |

建议给「立即发布」加一个 tooltip 说明它会先构建再发布（`立即发布` / `一键发布` 名字相近，这是唯一需要提示的地方）。


### 2.3 详情抽屉的两个发布按钮

抽屉右上角（构建信息下方、目标卡片上方）放两个按钮：

| 按钮 | 行为 | 适用状态 |
| --- | --- | --- |
| **发布测试** | 只发布到测试通道。已构建/已下线 → 测试中 | 已构建、已下线 |
| **一键发布** | 同时发布到测试与生产两个通道，一步到位。已构建/已下线 → 生产中（测试通道同时指向它） | 已构建、已下线 |

按钮本身不加 tooltip 说明文案。

**保留二次确认框**（操作警示，不是按钮解释）：

- 发布测试：「确定将构建 #N 发布至测试环境吗？当前测试版本（#M）将被转为已下线。」
- 一键发布：「⚠️ 确定将构建 #N 同时发布至测试与生产吗？这会影响所有线上设备，当前生产版本（#M）将被转为已下线。」

已在测试通道（TESTING）或已下线（OFFLINE）且只回滚生产的场景，保留原有的「发布至生产」「重新测试」「回滚至生产」按钮。

### 2.4 后端：一键发布端点

**核心逻辑已经存在。**

`releases.publish_build(conn, build, operator, reason, env=PRODUCTION)`（`server/app/services/releases.py:245`）：

> 规格要求"发布至生产"的来源状态必须是 TESTING 或 OFFLINE，
> 而自动任务与"保存并构建发布"要在同一轮里把新构建推上线，
> 因此这里先置 TESTING、再置 PRODUCTION，两步同处一个事务，状态原子切换。
> 两步算**一次**发布：发布历史只记最终那一条。

这正是「一键发布」的语义，且已满足：

- 同一事务内完成，状态原子切换 ✓
- 发布历史只记一条，不会一轮吃掉两条额度 ✓
- 来源状态 BUILT / OFFLINE 都允许（先置 TESTING 再置 PRODUCTION）✓

**只需新增一个端点**：

```python
@router.post("/builds/{bid}/publish-both")
def publish_both(bid: int, body: PublishBody, user=CurrentUser):
    """一键发布：已构建 / 已下线 → 测试中 + 生产中，一步到位。"""
    return _publish("both", bid, body.reason, user["username"])
```

`_publish` 加一个分支：

```python
elif action == "both":
    result = releases.publish_build(conn, build, operator, reason,
                                    releases.Env.PRODUCTION)
```

前端调用 `POST /api/v1/builds/{id}/publish-both`。

**为什么不用现有两个端点串起来**：`publish-to-prod` 走 `publish_to_production`，要求来源状态已经是 TESTING，从「已构建」直接调会被状态机拒绝；前端串行调还会跨两个事务，中间态可被其它请求看到，且发布历史会记两条。

### 2.5 列表操作列统一

| 状态 | 现在的按钮 | 改成 |
| --- | --- | --- |
| 已构建 | 详情 / 发布至测试 / 删除 | 详情 / **发布测试** / **一键发布** / 删除 |
| 测试中 | 详情 / 发布至生产 / 下线 | 不变 |
| 已下线 | 详情 / 重新测试 / 回滚至生产 | 不变 |

「已构建」变成 4 个按钮，操作列宽度 `190 → 240`（移动端 `150 → 190`）。

### 2.6 与自动任务的关系

服务端 scheduler 不动：自动构建发布走的是 `releases.publish_build(..., Env.PRODUCTION)`，与新的「一键发布」是同一套语义、同一套事务逻辑，行为一致。

界面区分：自动任务在后台按间隔执行；「一键发布」与「立即手动发布」是人工即时触发。

## 三、拓展模块：加来源类型

### 3.1 现状与目标

「添加模块」弹窗现在只能**手动编写** YAML 内容，面板里 17 个条目全是内联。

目标：**只加一个来源类型**，变成「内联内容 / 远程 URL」二选一，交互与「添加规则来源」弹窗完全同款：

```
来源类型   ○ 内联内容   ● 远程 URL
URL        [ https://.../ruleset.yaml            ]
格式       [ yaml ▾ ]
抓取间隔   [ 86400 ▾ ] 秒
客户端更新间隔 [ 0 ▾ ] 秒（0 = 跟随抓取间隔）
☑ 启用
☐ 抓取走代理（服务端直连抓不到时经指定代理中转）
```

远程来源由服务端定时抓取，内容进缓存；抓取失败保留上一次可用内容。

### 3.2 数据模型

`snippets` 表新增 6 列：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source` | TEXT NOT NULL DEFAULT 'inline' | `inline`（面板内建）/ `remote`（远程 URL） |
| `url` | TEXT NOT NULL DEFAULT '' | 远程地址 |
| `format` | TEXT NOT NULL DEFAULT 'yaml' | `yaml` / `text` |
| `interval` | INTEGER NOT NULL DEFAULT 86400 | 抓取间隔（秒） |
| `client_interval` | INTEGER NOT NULL DEFAULT 0 | 客户端更新间隔（秒），0 = 跟随抓取间隔 |
| `proxy_url_enc` | TEXT NOT NULL DEFAULT '' | 抓取走代理（Fernet 密文） |

`content` 一列两用：`inline` 时是用户写的内容；`remote` 时是抓取缓存。

现有字段（`name` / `category` / `engine` / `enabled` / `sort` / `note`）语义不变。

### 3.3 抓取实现

**规则来源的抓取机制可以直接复用**：`updater.refresh_provider`（`server/app/services/updater.py:215`）的结构是

```
加锁 → 校验 kind == remote → 取 url/proxy → fetcher.fetch(url, proxy=proxy)
     → 写 last_status/last_error/last_attempt_at/content → 记审计
```

拓展模块新增一个同构的 `updater.refresh_snippet(snid, operator, automatic=False)`：

- 复用 `fetcher.fetch(url, proxy=proxy)`（该函数是通用的：逐跳校验重定向、限体积、显式代理）
- 片段不需要 `count_rules`（那统计的是规则集条目，片段是 YAML 映射）
- 抓到的内容**仍要过现有校验**（`_check`）：合法 YAML、非空映射、不含 `proxies`/`proxy-providers`/`proxy-groups`/`rule-providers`/`rules` 这些受保护键
- 校验失败 → 记 `last_error`，**保留上一次可用内容**（与规则来源的行为一致）

### 3.4 定时抓取

`services/scheduler.py` 现有 `_run_rule_fetch`（抓远程规则来源）在旁边加一个 `_run_snippet_fetch`（抓远程拓展模块），复用同样的到期判断（`last_attempt_at` + `interval`）与重试逻辑（`FETCH_RETRY_TIMES` / `FETCH_RETRY_DELAY`）。

调度器开关：沿用 `auto_fetch_rules`；拓展模块单独加一个 `auto_fetch_snippets`（默认 1），在「自动构建发布」tab 里配置。

### 3.5 内容进产物与触发重建

`collect_snapshot` 里的 snippets 已经带 `content`（`builds.py:113`），所以：

- 远程片段抓取成功 → content 更新 → 快照变化 → `policy_sha` 变 → **自动构建照常触发** ✓
- 这条链路现状就对（内联片段改了也会触发），加远程来源不需要额外改动

### 3.6 与自主维护（仓库）的关系：**无关联**

**拓展模块不与仓库做任何自动关联**：

- 不列仓库文件、不自动建条目、不自动引用
- 用户自己在「远程 URL」里填地址（jsDelivr / raw.githubusercontent / 任意可抓的地址）
- 仓库里的分类目录（通用 / 脚本 / 覆写 / 面板 / DNS）是用户自己仓库的组织方式，面板不管、不消费

换句话说：仓库提供**文件**，用户自己决定把哪个文件的地址填进拓展模块。面板两边都不做「关联」。

### 3.7 界面改动

「添加 / 编辑拓展模块」弹窗：

- 来源类型单选：`内联内容` / `远程 URL`（放在名称、分类、引擎之后）
- 选「内联内容」：现有文本域 + 内置预设下拉（不变）
- 选「远程 URL」：URL、格式、抓取间隔、客户端更新间隔、抓取走代理
- 列表新增「来源」列：`内联` / `远程`（远程的悬浮提示显示完整 URL）
- 远程条目加一个「立即抓取」按钮（与规则来源页的「抓取」同款）

来源列的中文标签与首页规则来源区块的「远程 / 内联」标签口径一致（同一套枚举中文口语标签，见 §1.5）。

### 3.8 分类枚举

现有分类保持不变：`general`（通用）、`script`（脚本）、`rewrite`（覆写）、`panel`（面板）、`dns`（DNS）。界面显示中文，内部枚举值不动。

## 四、自主维护

完整设计见 [自主维护-设计方案](自主维护-设计方案.md)，要点：

- magic-sets 从 submodule 变成运行时可配置、可替换的数据层（单仓库）

- 仓库托管实体的内容只读，改动只在自主维护页；启用状态归面板

## 五、策略组顺序：本次重构不得触碰

策略组的先后顺序是向阳精心配置过的基线，**本次重构的任何一步都不得改动它**（含 `sort` 值）——菜单重排、页面合并、构建流程改动、数据层切换都不例外。

基线见 `AGENTS.md` 约束 27（31 个策略组的顺序与 `sort` 值）。

执行要求：

- 动手前拉一次线上当前顺序（`GET /api/v1/groups`），与基线逐项比对，确认起始状态一致
- 重构过程中**不调用** `POST /api/v1/groups/reorder`——该接口会按提交的 id 数组重新分配 `sort` 值，即使相对顺序不变也会改动 `sort` 数值
- 若确实需要新增策略组（例如自主维护引入的分组），只能追加到向阳指定的位置
- 重构完成后再次拉取线上顺序，与基线逐项比对（名称 + `sort` 值），确认完全一致

## 九、实施记录与偏差（2026-10-25）

六步全部实施并上线，线上生产版本随之更新。实施中与本方案不一致的地方，以下列为准：

| # | 方案原文 | 实际做法 | 原因 |
| --- | --- | --- | --- |
| 1 | §2.3「一键发布 …（测试通道同时指向它）」 | 发布后**测试通道空置**，只有生产通道指向它 | `publish_build` 是同一事务里「先置测试、再置生产」，构建状态最终是生产中，`current(TESTING)` 按状态查自然查不到。与自动构建发布同一套语义 |
| 2 | §3.2 拓展模块新增 6 列 | 实际是 **10 列**：6 列来源相关 + `last_status` / `last_error` / `last_fetched_at` / `last_attempt_at` 四个抓取状态列 | 远程来源要有「抓取失败保留上一次可用内容」的状态位，否则界面无从提示 |
| 3 | §1.2 tab 名沿用「产物配置」 | 保留 | 改名映射只覆盖**页面名**（菜单、页面标题、描述、文档、审计动作）；tab 名指的是"三层配置本身"，与旧页面名不冲突 |
| 4 | §1.4 改名清单里的「依赖管理 → 自主维护」 | 新页面直接叫「自主维护」，没有旧页面可改 | 「依赖管理」从未存在为页面，只是方案稿里的旧称 |
| 5 | 自主维护文档未提容器用户 | 镜像里给运行身份（uid 1000 / gid 1001）补了 passwd / group 记录 | 没有这条记录，`ssh` 会因 `No user exists for uid 1000` 直接拒绝连接，Git 操作做不了 |
| 6 | 自主维护文档未提 known_hosts | 显式指到 `/app/data/deps/known_hosts` | 容器没有可写的 HOME，`~/.ssh/known_hosts` 写不进去 |
