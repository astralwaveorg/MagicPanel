# 构建发布系统状态机重构 · 影响面分析报告

> 编写日期：2026-10-21
> 目标：废弃「稳定通道 / 候选通道」双轨模型，改为**单一版本生命周期状态机**（一个构建在任意时刻只有一种状态）。
> 依据：《构建发布系统状态机重构规格说明书（Tech Spec）》

---

## 一、现状盘点（重构前）

### 1.1 数据模型

| 表 | 现状 | 问题 |
| :--- | :--- | :--- |
| `builds` | `status` 列存**校验结果**（`building` / `success` / `failed`） | 没有生命周期状态；「是否发布过/在哪」只能靠外部指针表推断 |
| `pointers` | `channel`(PK: stable/candidate) → `build_id` + `released_at/operator/action/reason` | 双指针允许**同一构建同时处于两个通道**（线上现存：构建 #30 同时在 stable 与 candidate） |
| `releases` | `build_id` + `channel` + `action` + 操作人 + 说明 | 发布历史与通道耦合 |
| `devices` | `channel`（stable/candidate） | 设备订阅目标建立在「通道」概念上 |
| `settings` | `auto_publish_channel` = stable/candidate | 自动发布目标同样建立在通道概念上 |

| 层 | 文件 | 职责 |

### 1.3 线上数据实况（迁移输入）

- `pointers`：stable → #30、candidate → #30（**同一构建占两个通道**，正是本次要消除的病态）。
- `releases`：最近 10 条均为 `promote` 动作，stable/candidate 混用。
- `settings.auto_publish_channel = stable`，8 台设备全部 `channel = stable`。
- 构建记录共 4 条（#26/#27/#28/#30），均 `status = success`。

## 二、重构设计（目标模型）

### 2.1 状态枚举（严格四态）

```python
class BuildStatus(str, Enum):
    BUILT = "BUILT"        # 已构建：产物已生成，从未发布过
    TESTING = "TESTING"    # 测试中：当前测试环境生效的唯一版本
    PRODUCTION = "PRODUCTION"  # 生产中：当前生产环境生效的唯一版本（受保护）
    OFFLINE = "OFFLINE"    # 已下线：曾发布过，被新版本替换或手动撤销（归档，不可彻底删除）
```

**校验结果另立字段** `verify_status`（`building` / `success` / `failed`）：规格要求「状态枚举严格限制为四种」，而校验结果不是生命周期状态，两者必须分离，否则一个构建会同时拥有两种「状态」。

### 2.2 状态流转矩阵（含副作用）

| 动作 | 允许的源状态 | 目标状态 | 副作用 |
| :--- | :--- | :--- | :--- |
| 发布至测试 | `BUILT` / `OFFLINE` | `TESTING` | 原 `TESTING` 构建 → `OFFLINE` |
| 发布至生产 | `TESTING` / `OFFLINE` | `PRODUCTION` | 原 `PRODUCTION` 构建 → `OFFLINE` |
| 手动下线 | `TESTING` | `OFFLINE` | 测试环境空置（弹窗二次确认） |
| 彻底删除 | `BUILT` | 物理删除 | 其余状态一律拒绝 |

约束（数据库级 + 代码级双保险）：

- 部分唯一索引 `idx_builds_production` / `idx_builds_testing`：`status IN ('PRODUCTION','TESTING')` 的构建**全局至多各一条**，DB 层杜绝双活。
- 切换顺序固定：先把旧版本置 `OFFLINE`，再把目标置为新状态（避免唯一索引冲突）。
- 全部发布/下线/回滚在**单个 `BEGIN IMMEDIATE` 写事务**内完成，状态原子切换。

### 2.3 「环境」取代「通道」

设备订阅目标与自动发布目标不再叫「通道」，改叫**环境**（`env`）：

| 旧 | 新 | 值 |
| :--- | :--- | :--- |
| `devices.channel = stable` | `devices.env = production` | `production` / `testing` |
| `pointers.channel` | `builds.status` | — |
| `settings.auto_publish_channel` | `settings.auto_publish_env` | `production` / `testing` |

设备拉取链路由 `devices.channel → pointers.channel → builds.id` 变为
`devices.env → builds.status（PRODUCTION / TESTING）→ builds.id`。

## 三、影响面清单（逐文件）

### 3.1 后端 · 数据层

| 文件 | 改动 | 类型 |
| :--- | :--- | :--- |
| `server/app/db.py` | `builds` 增列 `verify_status/published_at/published_by/publish_reason/status_updated_at`；`status` 语义改为生命周期；`releases` 重建为 `env`；`devices.channel → env`；删除 `pointers` 表；新增两条部分唯一索引 | 迁移 |
| `server/app/config.py` | `SETTINGS_DEFAULTS`：`auto_publish_channel` → `auto_publish_env`（默认 `production`） | 改名 |

**迁移算法（一次性，`schema_version = release_state_v1`）**

1. `builds.verify_status ← builds.status`（旧校验结果），`builds.status` 置为初始生命周期值。
2. 读 `pointers`：`stable → PRODUCTION`，`candidate → TESTING`；同一构建同时命中两指针时**生产优先**（候选指针作废，测试环境置空）。
3. 曾在 `releases` 出现但当前未生效的构建 → `OFFLINE`；从未发布过的 → `BUILT`。
4. 从 `pointers` 搬运发布元数据到 `builds.published_at/published_by/publish_reason`。
5. `releases` 表重建：`channel` → `env`（stable→production、candidate→testing），`action` 归一为 `publish/rollback/offline`。
6. `devices.channel` → `devices.env`（stable→production、candidate→testing）。
7. `settings.auto_publish_channel` → `auto_publish_env`。
8. 删除 `pointers` 表，建唯一索引，写 `schema_version` 标记。

## 四、关键决策与理由

| # | 决策 | 理由 |
| :--- | :--- | :--- |
| 1 | 校验结果另立 `verify_status` 字段 | 规格要求状态枚举严格四态；校验通过与否不是生命周期 |
| 2 | `pointers` 表整体废弃，元数据上移到 `builds` | 状态机下「当前生效版本」= `status` 唯一确定，指针表成为冗余的第二真相源 |
| 3 | 生产唯一性用**部分唯一索引**兜底 | 应用层校验可被并发绕过，DB 约束才是最后一道防线 |
| 4 | 写事务改为 `BEGIN IMMEDIATE` | 状态切换必须串行，避免并发发布时出现「双 PRODUCTION」或半切换 |
| 5 | `BUILT → PRODUCTION` 禁止 | 规格矩阵明确只允许 `TESTING/OFFLINE → PRODUCTION`，未过测试不得上线 |
| 6 | 自动发布到生产采用「同一事务内 TESTING → PRODUCTION」 | 既满足流转合法性，又保留「定时自动上线」的既有运维能力（线上 `auto_publish_env=production`） |
| 7 | 设备的 stable/candidate 改为 env=production/testing | 通道概念整体废弃，设备侧同步改名才能自洽 |
| 8 | 手动删除只放行 `BUILT`；已发布过的构建由**留存任务**按窗口自动清理（保留最近 20 个，更早的连记录、产物、发布历史一起删） | 归档语义与回滚能力的前提；同时避免历史构建无限堆积 |

### 4.1 实施补充（落地后确认的三点）

1. **自动发布到生产后，测试环境为空**：自动发布走「同一事务内 BUILT → TESTING → PRODUCTION」，
   构建最终停在 `PRODUCTION`，因此测试环境在被下一次手动发布前没有生效版本。
   这与「一个构建只有一种状态」的前提一致，线上 8 台设备均为生产环境订阅，不受影响。
2. **手动「发布至生产」同样会消费掉测试版本**：把 `TESTING` 的构建提升为生产版本后，
   它离开测试环境，测试环境随之空置（需要时重新发布一个构建到测试环境即可）。
3. **被自动清理的历史版本不可回滚**：留存任务保留最近 20 个已发布过的构建，
   更早的会连记录、产物与发布历史一起彻底删除（404「构建不存在」）。
   回滚窗口因此是"最近 20 个"，而不是无限长。

## 五、边界情况与预期行为

| 场景 | 预期 |
| :--- | :--- |
| 并发发布同一个构建 | 写事务串行；第二个请求读到状态已变更 → `400 该构建已是生产版本`，不产生双活 |
| 没有测试版本时直接发布到生产 | `BUILT → PRODUCTION` 被拒 → `400 请先发布至测试环境` |
| 回滚到很旧的 `OFFLINE` 构建 | 旧 `PRODUCTION` → `OFFLINE`，目标 → `PRODUCTION`，唯一索引保证不破坏唯一性；超出留存窗口的构建已被自动清理 → `404 构建不存在` |
| 发布测试时原测试版本 | 原测试版本自动 `OFFLINE`（归档保留，可回滚） |
| 删除 `TESTING/PRODUCTION/OFFLINE` 构建 | `400 只有未发布过的构建可以删除` |
| 设备订阅的生产版本被下线 | 生产版本不可手动下线（仅能被新版本替换），生产设备不会出现 503 |
| 迁移时同一构建占两个通道 | 生产优先；候选指针作废，测试环境迁移后为空（线上 8 台设备均为生产环境，无影响） |

1. 备份生产库（已有 WebDAV 备份机制）。

5. 全量回归：`pytest`（103 + 新增用例）、前端构建、线上接口冒烟。

## 七、上线记录（2026-10-21）

### 7.1 迁移结果

线上库迁移前后对照：

| 构建 | 迁移前 | 迁移后 |
| :--- | :--- | :--- |
| #30 | stable + candidate 双指针 | `PRODUCTION`（生产优先，候选指针作废） |

| 测试环境 | candidate → #30 | 空（#30 已占生产；发布新的构建即恢复） |

* `pointers` 表已删除；`releases` 重建为 `env` 列；8 台设备 `channel` → `env=production`；
  `auto_publish_channel` → `auto_publish_env=production`。
* 迁移幂等：`schema_version` 记录 `release_state_v1` / `release_state_v2`，重复启动不改变数据。

### 7.2 上线中发现并修复的两个真实缺陷

1. **`releases` 旧列残留**：只给 `releases` 加 `env` 列不够——旧的 `channel` 列是
   `NOT NULL` 且无默认值，之后写发布历史会整条 INSERT 失败。改为整表重建
   （`release_state_v2`），并补 `test_migration.py` 回归用例。
2. **产物检查只做在生产侧**：产物已被留存清理的构建，发布到测试环境会被放行，
   随后测试环境设备拉取拿到 503。现在两个环境都做产物检查。

### 7.3 节点来源改名后的重建

生产库把节点来源「🐉 神龙机场」改名为「神龙机场」后，已发布产物里仍写着旧名，
客户端按旧名请求 provider 子资源会 404。因此重建并发布了构建 #31，
现网配置已全部改用新名（设备拉取 200，provider 子资源 200）。
