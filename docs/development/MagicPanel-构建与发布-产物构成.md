# MagicPanel 构建与发布：产物构成与可变边界分析

> 面向维护者。目的：说清楚「一次构建到底固化了什么」「发布到底动了什么」「谁能改什么、什么时候生效」。
> 结论以代码为准，对应实现位置写在每节末尾，便于核对。

---

## 0. 一句话结论

- **构建 = 把当前策略固化成不可变快照 + 逐目标渲染成静态产物文件**。构建完成那一刻，产物内容不再变化；改任何配置都必须新建一次构建。
- **发布 = 把构建的生命周期状态切到 `TESTING`（测试环境）或 `PRODUCTION`（生产环境）**。发布本身不生成内容，只切状态，并留一条发布记录。
- **客户端拉到的配置 = 构建期固定内容 + 分发期按设备替换的少量占位 + 完全实时的子资源**。三者生命周期不同，是最容易混淆的地方。
- **能改配置的是登录后台的维护者**；持有订阅地址（token）的人只能拉取、不能修改；客户端本地还能改「当前选中哪个节点」这类客户端自己的状态。

实现位置：`server/app/services/releases.py`（状态机唯一实现）、`server/app/routers/builds.py`、`server/app/compiler/render.py`、`server/app/compiler/validate.py`、`server/app/routers/feed.py`、`server/app/services/scheduler.py`。

## 1. 全链路数据流

```
┌──────────────── 配置层（数据库，可编辑）─────────────────┐
│ sources 节点来源 / rule_providers 规则来源 / local_nodes 本地节点 │
│ proxy_groups 策略组 / rules 分流规则 / targets 引擎平台 / snippets 功能模块 │
└───────────────────────────┬───────────────────────────────┘
                            │ collect_snapshot()  ← 只读快照，不含运行期状态
                            ▼
                 snapshot(JSON) ──sha256──► policy_sha（策略指纹）
                            │
                            │ validate_policy() 静态校验（引用/环路/空组/兜底/正则）
                            ▼
        ┌──────── render_target(snapshot, target) 逐目标渲染 ────────┐
        │ 代理组 / 规则 / provider 引用 / 本地节点 → Clash YAML 文本 │
        └───────────────────────────┬───────────────────────────────┘
                                    │ validate_rendered() YAML 往返
                                    │ mihomo -t（仅 Mihomo 目标，核心可用时）
                                    ▼
              data/builds/<build_id>/<target>.yaml   ← 静态产物文件（不可变）
              builds 表：snapshot / policy_sha / results / verify_status / status
                                    │
                     发布（校验通过才允许，状态流转）
                                    ▼
              builds.status（BUILT / TESTING / PRODUCTION / OFFLINE）+ releases 表（最近 10 条）
                                    │
                       客户端拉取 /feed/<token>/config.yaml
                                    ▼
        {FEED} 替换成设备专属地址、{FEED_HOST} 替换成面板域名；浏览器下载时加 #SUBSCRIBED 首行（Stash 客户端自己会补，服务端不重复补）；rules 段内完全重复的条目只保留一条
                                    │
        客户端再去拉 /feed/<token>/res/provider/<来源>  ← 实时快照，不是构建产物
                  /feed/<token>/res/rule/<规则来源>    ← 实时规则内容
```

关键分界：**上图上半段全部发生在构建瞬间；下半段的子资源完全在请求时现取。**

## 2. 产物里哪些内容是「固定不变」的

构建产物 = `data/builds/<build_id>/<target>.yaml`。以下内容在文件写下的瞬间固化，此后**任何配置改动都不会改这个文件**，只能通过新建构建产生新文件。

| 产物顶层键 | 内容 | 来源 | 用户可改 | 何时生效 |
| --- | --- | --- | --- | --- |
| `mixed-port` / `allow-lan` / `mode` / `log-level` / `ipv6` / `profile` | 7890 / false / rule / warning / false / store-selected、store-fake-ip | **产物基础配置**（系统默认 → 通用配置（引擎+平台）→ 设备配置，三层联动） | ✅ 可改 | 下次构建（设备级在下一次拉取即生效） |
| `proxies` | ①「空组保护」占位节点（127.0.0.1:1）② **本地节点**（`名称 (类型)`，含地址、端口、协议、凭据；键名按引擎渲染） | 常量 + `local_nodes` 表 | ⚠️ 可改本地节点本身 | 下次构建 |
| `proxy-providers` | 每个启用来源的 HTTP provider 条目：url=`{FEED}/res/provider/<名称>`、path、interval、UA、filter；Stash 用 `benchmark-url`/`benchmark-timeout`，Mihomo 用 `health-check` | `sources` 表 | ✅ 可改名称/UA/间隔/客户端间隔/过滤/启用 | 下次构建（条目参数） |
| `proxy-groups` | 组名、类型、成员（组名 / DIRECT / REJECT / `xxx (类型)`）、`use` 来源、filter、interval/tolerance/lazy/hidden；`url`/`timeout` 与 `strategy` 按引擎输出 | `proxy_groups` 表 | ✅ 可改 | 下次构建 |
| `rule-providers` | 每个启用规则来源的条目：url=`{FEED}/res/rule/<名称>`、path、behavior、interval、format | `rule_providers` 表 | ✅ 可改 | 下次构建（条目参数） |
| `rules` | ①**置顶** `DOMAIN-SUFFIX,{FEED_HOST},DIRECT`（面板域名强制直连，防 VPN 运行中更新配置失败）②**个人直连域名** `DOMAIN-SUFFIX,<域名>,DIRECT`（`_direct_domains`）③用户规则按顺序 | 规则表 + 基础配置伪键 | ✅ 规则可改 / ⚠️ 置顶两条可在「产物配置」里开关与维护 | 下次构建 |
| `dns` | Mihomo 目标：fake-ip、DNS 服务器、nameserver-policy、fake-ip-filter；Stash 目标仅在配置了 `_fake_ip_filter` 时下发 dns 段 | 基础配置优先，未配置时用内置默认值 | ✅ 可改 | 下次构建 |
| 合并后的功能模块 | 启用的 snippets 按 engine 匹配后合并：字典递归、列表追加、标量覆盖 | `snippets` 表 | ✅ 可改 | 下次构建 |
| 目标扩展覆盖 | 目标级 `extra_yaml` 合并，**优先级最高** | `targets` 表 | ✅ 可改 | 下次构建 |

### 2.1 快照（snapshot）里固化了什么

`collect_snapshot()` 只取「影响产物的配置」，刻意**不取运行期状态**（上次抓取时间、节点数量、测速结果），因此上游波动不会让策略指纹漂移：

- 来源：名称、启用、filter、UA、抓取间隔
- 规则来源：名称、behavior、format、kind（remote/inline）、间隔、启用
- 本地节点：名称、协议、地址、端口、**解密后的参数**、启用
- 策略组 / 规则 / 引擎平台 / 启用的功能模块：全部字段

`policy_sha = sha256(json.dumps(snapshot, sort_keys=True))`，用于两件事：
1. 判断「策略是否变化」——自动构建据此跳过无意义的重复构建；
2. 标记每个构建对应的是哪一版策略。

### 2.2 特别容易被误解的「不变」

| 内容 | 是否进构建产物 | 实际生效时机 |
| --- | --- | --- |
| **上游节点列表**（机场订阅里的节点） | ❌ 不进（只写 provider 引用） | 客户端拉子资源时**实时**取最新快照 |
| **上游规则内容** | ❌ 不进（只写 rule-provider 引用） | 客户端拉子资源时**实时**取最新内容 |
| **测速结果 / 不可用节点过滤** | ❌ 不进 | 分发子资源时按当前 `test_results` 过滤 |
| **本地单节点凭据** | ✅ 进，且是明文 | 构建时固化，换凭据必须重新构建 |
| **设备令牌 / 设备专属订阅地址** | ❌ 不进（用 `{FEED}` 占位） | 分发时按请求 URL 替换 |

> 推论：**改机场订阅的节点内容不需要重新构建**（子资源直读）；**改本地单节点的密码必须重新构建**。
> 推论：**上游节点变了而策略没变，自动构建会判定「策略未变化」而跳过**——这是设计意图，不是 bug。

实现位置：`server/app/routers/builds.py:collect_snapshot`、`server/app/compiler/render.py:render_target`。

## 3. 分发期（客户端拉取时）才确定的内容

客户端拿到的不再是磁盘上的原文件，而是**按请求现场拼装**的响应。

| 位置 | 内容 | 变化原因 |
| --- | --- | --- |
| 首行 `#SUBSCRIBED <设备专属订阅地址>` | 每个设备不同 | 按 token 拼接；仅浏览器下载时输出（Stash 客户端自己会写这一行） |
| 全文中的 `{FEED}` | 替换为 `https://面板域名/feed/<token>` | 每个设备不同（**产物里不含设备令牌**） |
| 全文中的 `{FEED_HOST}` | 替换为面板域名（供置顶 DIRECT 规则用） | 部署域名决定 |
| `Content-Disposition` 文件名 | 设备名（中文按 RFC 5987 编码） | 每台设备不同 |
| 响应头 `profile-update-interval` | 来自设置 `profile_update_interval`（默认 1 小时） | 改设置立即生效，**不需要重新构建** |
| 响应头 `ETag` | `sha256(build_id:target:token 前 10 位)` | 生效版本切到新构建后 ETag 变化，客户端才重新下载 |
| 子资源 `/res/provider/<名称>` | 当前快照；开了「只分发可用节点」时按最新测速结果过滤失败节点 | **每次请求实时** |
| 子资源 `/res/rule/<名称>` | 规则来源当前内容（inline 或抓取结果） | **每次请求实时** |
| 当前生效版本 | 客户端下次拉取时拿到的是**该订阅环境当前生效的构建**（`builds.status` = `PRODUCTION` / `TESTING`） | 发布 / 回滚后立即改变 |

分发链路上的两条硬约束：
- **HTTP 200 只代表文件下载成功**，不代表客户端已加载或策略已生效。
- 生效版本切换后，**已经拿到旧文件的客户端仍会继续用旧配置**，直到它下次按自己的节奏拉取（受 `profile-update-interval` 影响，默认 1 小时）。

实现位置：`server/app/routers/feed.py`。

## 4. 谁可以改什么

### 4.1 角色划分

| 角色 | 凭据 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| **维护者**（登录后台） | 用户名 + 密码 + 会话 + CSRF | 增删改所有配置、触发构建、发布/回滚/删除构建、改设置、导设备、管核心、看审计与产物 | — |
| **订阅持有者**（客户端 / 第三方） | 完整 feed URL（含 token） | GET/HEAD 拉完整配置与子资源 | 不能改任何配置；不能看别的设备；token 撤销只影响**之后**的下载，已拿到的文件仍然有效 |
| **门户访客** | 4 位 PIN（可选） | 只读查看规则/分流信息 | 不能改任何东西；PIN 与后台登录是两套凭据 |
| **系统（自动任务）** | 进程内调度器 | 抓取、测速、自动构建、以「系统」身份发布 | 只能走同一套校验与门禁；自动发布记录以 `operator='系统'` 区分，不混进手动发布列表 |
| **客户端本身** | 自己的本地配置 | 选中的节点、策略组选择等客户端本地状态 | 与服务端无关；服务端不感知 |

### 4.2 可编辑项清单（维护者）

| 配置域 | 可改字段 | 受控约束 |
| --- | --- | --- |
| 节点来源 | 名称、订阅地址、启用、过滤正则、UA、抓取间隔、测速间隔、自动抓取/自动测速开关、允许私网地址、只分发可用节点 | 名称唯一；订阅地址加密存储；删除时校验策略组引用 |
| 规则来源 | 名称、类型（remote/inline）、URL 或内联内容、behavior、format、间隔、启用 | 名称唯一；内联内容 ≤ 2MB；删除时校验规则引用 |
| 本地单节点 | 名称、协议、地址、端口、协议参数、高级 YAML、启用 | 名称唯一；参数加密存储；删除时校验策略组引用；停用则不进产物 |
| 策略组 | 名称、类型、隐藏、成员、节点来源、本地节点、过滤正则、测速地址/间隔/超时/容差、惰性测速、分配策略 | 类型白名单；relay 必须 ≥2 个固定成员且不能用来源/过滤；空组报错 |
| 分流规则 | 类型、匹配值、目标策略组、启用、no-resolve | 目标必须是存在的策略组或内置目标；必须有 MATCH 兜底 |
| 引擎平台 | 名称、引擎（Stash/Mihomo）、平台、扩展 YAML | 名称限 ASCII 字母数字下划线横线；扩展 YAML 必须是映射。客户端更新提示是全局设置 `profile_update_interval`（默认 1 小时），不再有平台级覆盖 |
| 功能模块 | 名称、分类、引擎、内容、启用、排序 | 引擎为 all/stash/mihomo |
| 设备 | 文件名、设备名、平台、目标、订阅环境、备注 | 令牌不可读，只能轮换 |
| 设置 | 对外基础地址、会话有效期、客户端更新间隔、核心下载代理、定时任务各开关与间隔、自动发布环境 | 白名单项；布尔值只接受 0/1；自动构建间隔 1–168 小时；发布环境只允许 production / testing |

### 4.3 不可修改项（硬边界）

| 不可改动的东西 | 原因 / 实现位置 |
| --- | --- |
| 已生成的构建产物文件 | 构建即固化；没有「编辑产物」接口。改配置 = 新建构建（`builds.py:create_build`） |
| 已发布构建的内容 | 发布只切换状态；想换内容必须构建新版本 |
| 校验失败的构建 | 状态机拒绝 `verify_status != success` 的构建（`releases._check_publishable`） |
| 发布过的构建（`TESTING` / `PRODUCTION` / `OFFLINE`） | 删除时拦截，提示「只有未发布过的构建可以删除」 |
| 规则首行 `DOMAIN-SUFFIX,{FEED_HOST},DIRECT` | 编译器强制置顶，不在规则表里，用户无法删改 |
| 空组保护节点 | 常量注入（`http://127.0.0.1:1`，永远连不通），防止空策略组被客户端隐式改写成 DIRECT；固定排在自动组成员**末尾**，真实节点优先 |
| 设备令牌 | 只存哈希 + 密文，界面不展示，只能轮换 |
| 订阅来源与规则来源的**上游内容** | 面板不代理上游内容，只在子资源里转发最新快照 |
| 审计日志 | 记录所有维护操作；可手动批量删除/清空，也会按上限（2 万行）自动裁剪最旧记录 |
| 发布历史长度 | 只保留最近 10 条（`RELEASE_HISTORY_LIMIT`），更早的以审计日志为准 |

## 5. 改动 → 生效路径速查

| 你改了什么 | 需要重新构建吗 | 客户端什么时候看到 |
| --- | --- | --- |
| 策略组 / 分流规则 | ✅ 需要 | 发布后 + 客户端下次拉取 |
| 本地单节点（含凭据、启停） | ✅ 需要 | 同上 |
| 引擎平台扩展 YAML、功能模块 | ✅ 需要 | 同上 |
| 来源的**间隔 / UA / 过滤正则 / 启用** | ✅ 需要（写进 provider 条目） | 同上 |
| 来源的**订阅地址** | ❌ 不需要重建（provider 条目里只有 `{FEED}/res/provider/<名称>`，不含真实地址） | 换地址后重新抓取，节点内容在子资源里立刻生效 |
| 规则来源的 **URL / 内容** | ❌ 不需要（内容在子资源里） | 抓取后立即生效 |
| 规则来源的 **behavior / format / 间隔** | ✅ 需要（写进 rule-provider 条目） | 发布后生效 |
| 上游机场的节点内容 | ❌ 不需要 | 客户端拉子资源时实时生效 |
| 设置里的客户端更新间隔 | ❌ 不需要 | 下一次响应头即生效（已统一为 1 小时） |
| 设备绑定的目标 / 订阅环境 | ❌ 不需要 | 下次拉取即生效 |
| 测速结果（可用节点过滤） | ❌ 不需要 | 子资源实时过滤（ETag 已纳入测速摘要，结果变化会真正下发） |
| 产物基础配置（端口/模式/DNS 等） | ✅ 需要 | 下次构建 |

> 记住这一条就够了：**凡是写进产物 YAML 的东西（组、规则、本地节点、provider 条目参数、基础配置、扩展 YAML）都要重建；凡是走子资源实时读取的东西（上游节点、上游规则、测速过滤）都不用重建。**
> 产物由四层叠加：**① 基础配置（按「引擎 + 平台」，可在「产物配置」页改）→ ② 结构化内容（节点/策略组/规则，恒由服务端生成）→ ③ 功能模块 → ④ 引擎平台扩展**。基础配置与扩展都不得写入 `rules` 等结构键。

## 6. 校验与护栏

### 6.1 构建期校验

| 校验 | 触发条件 | 结果 |
| --- | --- | --- |
| 策略组引用存在、环路检测、空组、本地节点引用、relay 成员数 | 每次构建 | error → 构建失败，不可发布 |
| 规则类型白名单、RULE-SET 引用存在、目标存在、必须有 MATCH 兜底 | 每次构建 | error → 构建失败 |
| 过滤正则可编译 | 每次构建 | error → 构建失败 |
| 未被引用的策略组/规则来源 | 每次构建 | warning → 仍可发布，界面提示 |
| 产物 YAML 往返（可解析、是映射、含 mode/rules、mode 合法） | 每个目标 | error → 该目标失败 |
| `mihomo -t -f`（仅 Mihomo 目标，核心已安装时） | 每个 Mihomo 目标 | 通过则标记「核心校验通过」，否则失败 |

**失败构建同样入库**（`verify_status=failed`，含每个目标的 errors/warnings），便于排查；但**不能发布**，也不会生成产物文件。

### 6.2 发布期护栏（版本生命周期状态机）

发布系统没有「通道指针」，只有一个构建在任意时刻只有一种**生命周期状态**：

| 状态 | 含义 | 说明 |
| --- | --- | --- |
| `BUILT` 已构建 | 产物已生成，从未发布过 | 只在列表中存在 |
| `TESTING` 测试中 | 当前测试环境生效的唯一版本 | 全局唯一 |
| `PRODUCTION` 生产中 | 当前生产环境生效的唯一版本 | 全局唯一，受保护 |
| `OFFLINE` 已下线 | 曾发布过，被新版本替换或手动撤销 | 归档状态，不可彻底删除 |

流转矩阵（**全部在单个写事务内完成**，切换顺序固定为「先下线旧版本、再置新状态」）：

| 动作 | 允许的源状态 | 目标状态 | 副作用 |
| --- | --- | --- | --- |
| 发布至测试 | `BUILT` / `OFFLINE` | `TESTING` | 原 `TESTING` 构建自动变 `OFFLINE` |
| 发布至生产 | `TESTING` / `OFFLINE` | `PRODUCTION` | 原 `PRODUCTION` 构建自动变 `OFFLINE` |
| 手动下线 | `TESTING` | `OFFLINE` | 测试环境空置 |
| 彻底删除 | `BUILT` | 物理删除 | 其余状态一律拒绝 |

配套约束：

- 校验结果（success / failed / building）单独存 `builds.verify_status`；`builds.status` 只存上表四种生命周期状态——一个构建不会同时有两种「状态」。
- **没有指针表**：「当前生效版本」= `builds.status` 为 `PRODUCTION` / `TESTING` 的那一条，数据库用两条部分唯一索引（`idx_builds_production` / `idx_builds_testing`）保证各至多一条，应用层校验只是第一道防线。
- 只有 `verify_status=success` 的构建可以发布 / 回滚。
- 未经过测试的构建（`BUILT`）不允许直接发布到生产环境，接口返回 400「请先发布至测试环境，再发布至生产环境」。
- 发布写 `builds.status`（当前生效版本）+ `releases` 流水（`env` / `action` / 操作人 / 说明），并把发布历史裁剪到最近 10 条。
- 删除构建时会连带删除该构建的发布历史与产物目录；**只有 `BUILT` 状态的构建允许删除**，其余状态返回 400「只有未发布过的构建可以删除」。
- 回滚 = 把一个历史构建重新置为 `PRODUCTION`（源状态 `TESTING` / `OFFLINE`），原生产版本自动变 `OFFLINE`；若该构建的产物已被留存清理，发布会被拒绝并提示「该构建的产物已被清理，无法发布」。

实现位置：`server/app/services/releases.py`、`server/app/routers/builds.py:_publish`。

### 6.3 自动发布的额外门禁

自动任务（内置调度器，30 秒一 tick）执行顺序：抓取到期来源 → 抓取到期规则来源 → 测速到期来源 → 自动构建 → 自动发布。

自动发布比手动发布多一道**测速门禁**：凡是开启「只分发可用节点」的来源，必须有**晚于最近一次抓取**的测速结果，且至少有一个节点可用，否则本轮跳过发布（并保留检查时间，等测速完成后下一轮立即重试）。另外策略指纹与**目标环境当前生效的构建**一致时，直接跳过构建（记为「策略未变化，跳过」）——不能用「最近一次成功构建」做比较，否则「构建成功但没发布出去」的新产物永远无法上线。

自动发布到**生产环境**时，调度器会在**同一个数据库事务内先置 `TESTING` 再置 `PRODUCTION`**：既满足「`BUILT` 不能直接上生产」的流转约束，又保留「定时自动上线」的既有能力，且状态切换是原子的。

实现位置：`server/app/services/scheduler.py:_publish_tests_ready`、`_run_auto_build`。

## 7. 安全边界（与本项目既有规格一致）

| 事实 | 含义 |
| --- | --- |
| 产物里**不含设备令牌** | 订阅地址用 `{FEED}` 占位，分发时按请求替换，泄漏一个产物不会泄漏其他设备 |
| 产物里**不含上游订阅凭据** | 上游内容走 provider / rule 子资源，需 token 才能取 |
| 产物里**含本地单节点凭据** | 本地节点是明文写入 YAML 的；因此 `builds.snapshot` 与产物文件都含凭据，**只能管理端预览，不要公开分发产物目录** |
| feed token 即凭据 | 任何拿到完整订阅地址的人都能下载；撤销只影响之后的下载 |
| 子资源同样校验 token | provider / rule 子资源走同一套 token 校验 |
| 本地节点参数加密落盘 | 数据库里是密文（`params_enc`），界面只对维护者解密回显 |
| 审计日志可清理 | 增删改、发布、抓取都留痕；支持批量删除与清空，也按上限自动裁剪 |
| 门户 PIN 与后台登录独立 | 门户只读，且不是管理凭据 |

## 8. 现状观察与改进建议（供讨论，非必做）

1. **本地节点不参与自动测速**：目前测速只针对节点来源的快照；本地单节点既没有测速入口，也不会被「只分发可用节点」过滤。若自建节点较多，建议后续给本地节点加测速能力与独立开关。
2. ~~**`builds.snapshot` 含本地节点明文凭据**~~：已修复 —— 快照改为 `enc:v1:` 密文落盘（启动时迁移历史明文行），密文与 `data/secret.key` 绑定。
3. **生效版本切换到客户端生效有窗口**：已把全局 `profile-update-interval` 与服务端 `auto_build_interval_hours` 统一为 **1 小时**（含存量数据迁移），端到端 ≤2 小时；也可用「产物配置 → 保存并构建发布」立即生效。
4. **自动构建对「上游内容变化」不敏感**：这是有意的（避免无意义构建），但意味着「上游节点全部失效」不会触发重建；依赖的是 provider 层面的实时替换 + 客户端自带测速切换。
5. **发布历史 10 条 ≈ 5 天**：每日两次自动发布时刚好覆盖；手动发布频繁时会挤掉自动发布记录，完整追溯请查审计日志。
6. **目标级「更新提示(小时)」已废弃**：客户端更新间隔统一取全局设置，目标页不再提供该输入，避免「改了却不生效」。
6. **目标级「更新提示(小时)」目前不生效**：`targets.update_interval` 只入库并在界面展示，分发层的 `profile-update-interval` 取的是全局设置 `profile_update_interval`。二者需要统一（要么目标级生效、要么把该字段从界面移除），否则容易误以为「改目标就能改客户端更新节奏」。

## 9. 如何自查（运维动作）

| 目的 | 操作 |
| --- | --- |
| 看当前生产 / 测试环境用的是哪次构建 | 构建发布页顶部「当前生产版本 / 当前测试版本」；或 `GET /api/v1/release-state` |
| 看两次构建差在哪 | 构建详情页「对比」；或 `GET /api/v1/builds/{id}/diff/{other}` |
| 看某目标的完整产物 | 构建详情页「预览」；或 `GET /api/v1/builds/{id}/artifact/{target}` |
| 看策略指纹是否变化 | 构建详情的 `policy_sha`；连续两次相同即策略未变 |
| 看自动任务做了什么 | 自动任务页「最近运行」；`GET /api/v1/automation/runs` |
| 看谁在什么时候改了什么 | 审计日志页；`GET /api/v1/audit` |
| 看设备实际拉到哪一版 | 设备详情页的最近拉取时间 + 该设备订阅环境当前生效的版本；设备页记录下载次数与 IP |

## 10. 术语对照

| 术语 | 含义 |
| --- | --- |
| 构建 | 一次策略固化 + 逐目标渲染，产出静态 YAML 与校验结果，不可变 |
| 策略快照 snapshot | 构建瞬间抓取的一份配置副本（不含运行期状态） |
| 策略指纹 policy_sha | 快照的 SHA-256，用于判断「策略有没有变」 |
| 产物 artifact | `data/builds/<id>/<target>.yaml`，客户端最终拿到的配置 |
| 发布状态 build status | `builds.status` 的生命周期取值：`BUILT` / `TESTING` / `PRODUCTION` / `OFFLINE` |
| 校验结果 verify_status | `builds.verify_status` 的取值：`building` / `success` / `failed`，与发布状态无关 |
| 订阅环境 env | 设备订阅的目标环境：`production`（生产）/ `testing`（测试）；同一环境只有一条生效版本 |
| 发布 publish | 把构建状态切到 `TESTING` 或 `PRODUCTION`，并写一条 `releases` 记录 |
| 回滚 rollback | 把历史构建重新置为 `PRODUCTION`，原生产版本自动转 `OFFLINE` |
| 下线 offline | 把当前测试版本置为 `OFFLINE`，测试环境空置 |
| 分发 feed | 按设备 token 现场拼装并返回产物 + 子资源 |
| 子资源 | provider（节点快照）/ rule（规则内容），实时读取，不进产物 |
