# 产物差异化与设备配置：全链路分析与升级方案

> 目标：让**每台设备、每个引擎平台**拿到的配置真正符合它的引擎、平台与使用场景，而不是"8 个平台只产出 2 份完全相同的文件"。
>
> ⚠️ 2026-10 更新：本方案里的「发布目标」已更名为「**引擎平台**」（= 引擎 + 平台，对应一类客户端）；
> 基础配置的作用域也从「四级联动」收敛为「**三层联动**」：内置默认 → 通用配置（引擎+平台）→ 设备专属。
> 原则：**不大改现有架构**，在既有四层合并模型（基础配置 → 结构内容 → 功能模块 → 目标扩展）上补齐缺失的差异维度。

## 1. 全面了解：现在的整条链路

### 1.1 数据流

```
数据库（sources / rule_providers / local_nodes / proxy_groups / rules / targets / devices / base_configs / snippets）
   │  collect_snapshot()  ← 构建时冻结成不可变快照（加密落盘）
   ▼
render.render_target(snapshot, target)  ← 逐目标渲染
   │  ① 基础配置（base_configs，按 engine）
   │  ② 结构内容（proxies / proxy-providers / proxy-groups / rule-providers / rules）
   │  ③ 功能模块 snippets（按 engine 过滤）
   │  ④ 目标扩展 target.extra_yaml（最高优先级）
   ▼
validate_policy(snapshot) + validate_rendered(text) + mihomo -t（仅 Mihomo 目标）
   ▼
产物文件 data/builds/<build_id>/<target>.yaml
   ▼
发布 = 移动 pointers（stable / candidate）
   ▼
分发 feed.py：{FEED} → 设备专属地址，{FEED_HOST} → 面板域名，加 #SUBSCRIBED 首行（Stash 请求除外）
```

### 1.3 关键事实：8 个目标只产出 2 份不同的文件

构建 #12 的结果里，6 个 Stash 目标的 `sha256` **完全相同**（`63a0098e…`），2 个 Mihomo 目标也完全相同（`0161e045…`）。也就是说：

- 目标名里的 `ios / macos / macmini / tvos / android / windows` 目前**不产生任何配置差异**；
- `targets.platform` 字段在渲染中**完全没有被使用**，只作展示；
- 目标扩展 `extra_yaml` 8 个目标**全为空**；
- 基础配置只按 **engine** 存两份，`stash-macos` 与 `stash-macmini` 共用同一份 → 顶层键也无法区分。

**这就是"差异化没做好"的根因**：当前模型里，"目标"这个概念只承载了"产物文件名"，没有承载任何差异化语义。

## 2. 逐逻辑分析

### 逻辑 1：引擎差异（Stash vs Mihomo）——已解决，但仍有尾巴

- 已做：provider（`headers`+`benchmark-*` vs `header`+`health-check`）、策略组（无 `url`/`timeout` vs 有）、本地节点（`auth`/`down-speed` vs `password`/`down`）、`udp`、`version`、顶层键（Stash 官方无 `mixed-port`/`allow-lan`/`profile`）。
- 尾巴：① 顶层 `dns` 段在 Mihomo 是必需（客户端不接管），在 Stash 只有显式配置才下发；② Stash 的 `dns` 段只输出 `fake-ip-filter`，没有 `nameserver`，依赖客户端"内置 DNS 服务"兜底——**需要确认各平台 Stash 都支持**；③ `strategy` 在 Stash 只支持两种取值，其余被静默改写（应在 UI 提示）。

### 逻辑 2：平台差异——**完全缺失**

- `platform` 字段从未参与渲染。
- 平台能力差异是客观存在的（进程名规则只在桌面端有意义、tvOS 的组交互受限、Linux/OpenWrt 还没有对应平台枚举）。
- 当前所有设备拿到的规则集完全一样，包括 6 条 `PROCESS-NAME` 规则（qbittorrent / transmission / deluge / rtorrent…）——这些在 iOS / Android / tvOS 上**永远不会命中**，纯属噪音，还让配置变大。

### 逻辑 3：场景差异（日常客户端 vs 常驻服务）——**完全缺失**

MacBook（日常上网、看流媒体）与 Mac mini（常驻服务、给家里其他设备做出口）都是 macOS，但期望的产物明显不同：

| 维度 | MacBook | Mac mini |
| --- | --- | --- |
| 顶层键 | 常规端口 / 日志 / DNS | 独立端口、独立 DNS、可能更严的日志 |
| 规则集 | 全量（含桌面进程名） | 精简（服务流量直连或固定出口） |
| 策略组 | 全部（含手动选择） | 只要必要的自动组 |
| 本地节点 | 参与选择 | 可不参与（常驻服务固定走某组） |

当前模型**没有任何表达手段**——策略组和规则都是全局的，任何目标都拿到同一份。

### 逻辑 4：目标扩展 `extra_yaml`——能力够用但入口粗糙

- 能改顶层键（含 `dns`）、能追加列表；但**不能改结构键**（`rules`/`proxy-groups`/… 被保护，因为列表是追加语义，写在兜底规则之后永不生效）。
- 没有 schema 化的表单，只能手写 YAML；也没有"哪些键在 Stash 无效"的提示。

### 逻辑 5：设备个性化——**不可用**

- 设备 = 目标 + 通道。要个性化只能"为这台设备单独建一个目标"，而目标之间的差异仅限顶层键（且无 UI），**规则与组无法差异化**。
- 设备层没有任何自己的配置入口（没有 `extra_yaml`），也没有"这台设备不要某些组/规则"的能力。

### 逻辑 6：命名与信息架构——不整齐

- 目标命名混杂：`stash-macos`（其实是 MacBook 日常机）与 `stash-macmini`（其实是常驻服务器），语义不在命名里。
- 设备命名客户端前缀不统一：`Clash-Windows` 实际用的是 Mihomo 内核，`Flclash-Android` 又是第三种叫法；大小写也不统一（`Stash-Macmini` / `Stash-MacBook`）。
- 平台枚举缺 `linux`（Mihomo 在 OpenWrt / Linux 上极常见）。
- 页面标题与菜单名此前不统一（已修）。

### 逻辑 7：构建与发布——健康

- 快照不可变、策略指纹（`policy_sha`）驱动"策略未变化则跳过"、双通道指针、发布历史、失败不覆盖旧发布 ✓。
- 构建期不再长持写锁 ✓。
- 唯一缺口：快照里的 `base` 只有 engine 两份，扩展到目标维度后需要一并纳入指纹（自动满足：快照进指纹）✓。

## 3. 确认：多少类型、多少设备、应该产出多少配置

| 问题 | 答案 |
| --- | --- |
| 引擎有几种 | 2（Stash / Mihomo） |
| 平台有几种 | 5（+ 建议补 linux = 6） |
| 发布目标有几个 | 8（生产现状） |
| 设备有几台 | 8（生产现状） |
| 设备与目标是否一对一 | 设备数 = 目标数 = 8，但**一对一只是巧合**：一台设备只能指向一个目标，一个目标可被多台设备共用 |
| 现在实际产出几份不同的配置 | **2 份**（6 个 Stash 目标相同 + 2 个 Mihomo 目标相同） |
| 应该产出几份不同的配置 | **最多 8 份**（每个目标一份，允许目标间配置相同，但应当**可以不同**） |
| 每台设备能否拿到专属配置 | 现在**不能**；方案落地后**可以**（设备级叠加 + 专属目标两种方式） |

**结论**：配置的多样性上限 = 发布目标数（8），而不是设备数（8）——因为多台设备共用一个目标时理应拿到相同配置。个性化需求应通过"**为目标建立差异**"或"**为设备建立专属覆盖**"来满足，而不是无节制地增加目标数量。

## 4. 方案（在既有架构上增量升级）

### D1. 基础配置支持"作用范围"（引擎默认 → 具体目标）

- `base_configs` 增加 `target` 列（`''` = 引擎默认），逻辑主键变为 `(engine, target)`。
- 渲染顺序：`引擎默认 base` → `目标级 base`（字典递归、列表整体替换）→ 结构内容 → 功能模块 → 目标扩展。
- 「产物配置」页增加**作用范围选择器**（引擎默认 / 指定目标），表单与预设不变。
- 兼容：存量数据 `target=''`，行为与现在完全一致 ✓。

### D2. 策略组 / 分流规则支持"适用目标"

- `proxy_groups` 与 `rules` 各增加 `targets` 列（JSON 数组，空 = 适用全部目标）。
- 渲染时按目标名过滤组与规则。
- **安全约束（必须）**：
  1. 兜底规则（`MATCH`/`FINAL`）永远保留，其指向的策略组**强制保留**——否则产物缺少兜底，客户端加载即失败；
  2. 过滤后指向"不存在组"的规则自动丢弃（并在构建结果里记 warning），杜绝"规则指向不存在的组"导致客户端报错；
  3. 组的成员里若引用了被过滤掉的其它组，同样剔除该成员。
- 收益：Mac mini 可以只保留必要组与规则；tvOS 可以精简掉用不上的组。

### D3. 平台能力裁剪

- 新增**平台能力表**（依据官方文档，见 §6）：哪些规则类型在哪些平台有意义（如进程名/进程路径只在 macOS / Windows 有效）。
- 目标级开关：**剔除当前平台不支持的规则**（默认开启），构建结果里报告剔除了多少条，UI 可见。
- 只剔除"必然无效"的规则类型，不做任何语义改写。

### D4. 设备级个性化

- `devices` 增加 `extra_yaml` 列：分发时在目标产物之上叠加（结构键保护，字典递归、列表追加），仅对这台设备生效。
- ETag 纳入设备覆盖内容的哈希，保证不同设备的缓存互不串味。
- 于是有两条个性化路径：
  1. **专属目标**（适合"这台机器就是另一种角色"）：建目标 → 设目标级 base / 适用目标 → 设备指向它；
  2. **设备级覆盖**（适合"这台机器要额外加一条规则/改一个端口"）：直接在该设备上写扩展 YAML。

### D5. 命名与枚举规范化

- 目标命名建议 `<引擎>-<平台>[-<场景>]`：`stash-macos-desktop`、`stash-macos-server`。
- 设备命名建议 `<客户端>-<设备名>`，客户端名统一为 `Stash` / `Mihomo` / `FlClash`。
- 平台枚举补 `linux`（Mihomo 常见），并统一大小写展示。

### D6. 兼容性红线

- 所有新增列都有默认值，存量数据不迁移也不报错 ✓。
- 渲染结果在"无任何差异化配置"时与改动前**逐字节一致**（用回归测试锁定）。
- 不改变四层合并模型，不改变发布/通道/指纹机制。

## 9. 实施结果（已落地）

### 9.1 数据模型（全部为增量列，存量无需迁移）

| 表 | 新增列 | 含义 |
| --- | --- | --- |
| `base_configs` | `target` | 作用范围：`''` = 引擎默认；目标名 = 该目标专属。旧表 engine 单列主键无法存放同引擎多份配置，已做一次性重建迁移 |
| `proxy_groups` | `targets` | 适用引擎平台（JSON 数组，空 = 全部） |
| `rules` | `targets` | 适用引擎平台（JSON 数组，空 = 全部） |
| `devices` | `extra_yaml` | 设备级个性化覆盖 |

### 9.2 基础配置的三层联动与合并语义

层级：**内置默认**（程序内置，只读可见）→ **通用配置**（按「引擎 + 平台」，与引擎平台一一对应）→ **设备专属**（按设备）。

合并语义为**键级并集**：同一键以更靠下的层为准；字典逐层递归合并；列表整体替换（不拼接）；标量与类型冲突均为后者覆盖。实现采用开源库 [`deepmerge`](https://github.com/toumorokoshi/deepmerge)（MIT），策略显式声明：

```python
Merger([(list, ListStrategies.strategy_override),
        (dict, DictStrategies.strategy_merge)],
       FallbackStrategies.strategy_override,
       TypeConflictStrategies.strategy_override)
```

每层只保存"与上层不同"的差异（`diff_overlay`），因此上层默认值变化时，未显式改过的键会自动跟随；「恢复本层」= 清空本层差异。界面把「生效值」与「来源层级」逐键展示，级联关系一目了然。

### 9.3 渲染层

合并顺序变为：**引擎默认 base → 目标级 base（字典递归、列表整体替换）→ 结构内容（按目标过滤 + 平台裁剪）→ 功能模块 → 目标扩展**；分发层再叠加**设备级覆盖**（字典递归、列表追加、标量覆盖）。

安全约束（全部有单测覆盖）：
1. 兜底规则 `MATCH`/`FINAL` 永远保留，其目标组被限定到其它目标时**强制保留**；
2. 指向不存在策略组的规则**自动剔除**并记入构建告警（否则客户端加载即失败）；
3. 策略组成员里指向不存在策略组的引用一并剔除；
4. 设备级覆盖与目标扩展一样**禁止写结构键**；
5. 设备级覆盖的哈希进入 ETag，不同设备的缓存不会串味。

### 9.4 平台能力裁剪

`PLATFORM_UNSUPPORTED_RULES`：iOS / Android / tvOS 剔除 `PROCESS-NAME`、`PROCESS-PATH`（这些平台不提供进程信息，规则必然不命中）。裁剪条数写入构建告警，界面可见。

### 9.5 界面

- 「产物配置」页的作用范围选择器改为**三层联动**（内置默认 / 通用配置（引擎+平台）/ 设备专属），并逐键显示生效值来自哪一层。
- 「策略组」「分流规则」页新增**适用目标**多选（表格列 + 编辑表单），不选 = 全部目标。
- 「设备管理」页新增**设备专属扩展**（YAML），仅该设备生效。
- 平台枚举补 `linux`（Mihomo 常见于 OpenWrt / Linux）。

### 9.6 审计日志

新增「删除选中」「清空全部」两个动作（`POST /api/v1/audit/delete`，支持按 id 批量或 `all=true` 清空）；删除动作本身不写审计日志，避免每次清理又产生一条记录。

### 9.7 生产数据落地

`scripts/apply_target_differentiation.py`（幂等）：

- 目标改名：`stash-macos → stash-macos-desktop`（MacBook 日常机）、`stash-macmini → stash-macos-server`（Mac mini 常驻服务）；
