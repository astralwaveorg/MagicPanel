# 自主维护：设计方案

> 状态：**设计讨论稿**，尚未开发。确认后作为开发依据。
> 起草：2026-10-25（v3：单仓库、拓展模块解耦为引用式）
> 关联：`AGENTS.md` 约束 19/20/22、`docs/reference/规则集与分流设计.md`

## 一、定位与目标

把「当前系统依赖的文件库」的管理能力做进 MagicPanel 后台，菜单叫 **自主维护**。

达成后应当成立：

1. **MagicPanel 独立**：仓库里不再含任何规则内容，不再有 submodule 引用，克隆 MagicPanel 即可运行。
2. **依赖内容外置且可替换**：依赖文件库的地址、分支、鉴权凭据都在后台配置，用户可以指向自己的任何仓库，MagicPanel 不绑定 `astralwaveorg/magic-sets`。
3. **仓库即文件库**：自主维护页是一个**文件管理系统**，能浏览仓库里**全部文件**（除 `.git` 等排除项外），不只是 `rule/` 里的规则集合。
4. **编辑即入库**：在页面上改文件、保存、提交、推送，走的是标准 Git 流程；远端有更新时自动拉取并提示处理合并冲突。
5. **内容即时生效**：自维护集合不再经 jsDelivr 中转，改完推上去面板就能拿到，没有 12 小时缓存。

### 非目标

- 不做 Git 托管服务，不代替 GitHub，只做**客户端**。
- **只支持一个依赖文件库**。多仓库没有实际场景，不做。
- 不做行级三方自动合并；冲突以**手工编辑**为主路径。
- 不改变客户端拉配置的协议（`/res/rule/<name>` 与 `/res/provider/<name>` 保持不变）。

## 二、关键决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 容器内装**系统 git**（`git` + `openssh-client`） | 需要真 merge/rebase、冲突标记、三方 blob 读取。dulwich 冲突能力残缺；GitHub API 做不了真合并 |
| D2 | 运行时把仓库 clone 到 `/app/data/deps/rule-repo` | `/app/data` 是持久卷，重启不丢；镜像里没有 submodule |
| D3 | 仓库配置存 `settings` 表，私钥 Fernet 加密 | 单仓库用不着单独建表；沿用 `security.encrypt_text` |
| D4 | **单仓库** | 一个 MagicPanel 对应一个文件库，没有多仓库场景 |
| D5 | 规则来源与拓展模块**各加一个「来源」标记** | 统一表达"内容从哪来"，两处用同一套模型 |
| D6 | **仓库是内容的事实来源** | 面板侧只额外持有"启用状态"这类运行态字段 |
| D7 | 定时任务**只 pull 不 push**；push 只在用户点「保存并提交」时发生 | 避免定时自动提交产生意料之外的提交 |
| D8 | 构建快照纳入规则内容的 sha256 | 现状 `collect_snapshot` 不含 content，规则内容变了不触发自动构建——这是现存缺陷，顺手修 |
| D9 | 冲突解决以**手工编辑**为主 | 规则文件通常整体重写而非逐行改，整文件覆盖反而容易丢改动 |
| D10 | 迁移**分批**执行，每批有核对清单 | 数据不能丢 |
| D11 | 移除 submodule 与第 2 步合并为一个提交 | 提交粒度无意义，数据安全有意义 |
| D12 | **脚本/重写片段不自动引入**，需在「拓展模块」页手动引用 | 片段是可选增强，仓库里堆了文件不等于面板就该用；解耦后由用户显式选择 |
| D13 | 排除清单可配置，**默认排除所有点开头路径** | `.git` 是 Git 元数据永远不可碰；点开头路径（`.github`、`.editorconfig` 等）默认不纳管，用户可按需放开 |
| D14 | 规则集合**自动**引入来源（默认开，可关） | 规则集合是分流的必需输入——不建来源就没法挂规则，28 个手动配不现实 |
| D15 | 仓库托管实体的内容**只读**，改动只发生在自主维护页 | 否则拓展模块页改了 content，下次同步被仓库覆盖，用户的编辑静默丢失 |

## 三、架构总览

```
        ┌────────── 依赖文件库（magic-sets 或用户自己的仓库）──────────┐
        │  rule/   script/   rewrite/   README.md   ...（全部文件）     │
        └────────────┬───────────────────────────┬───────────────────┘
                     │ git pull（默认 12 小时）    │ git push（保存并提交时）
                     ▼                           ▲
┌────────────────────────────────────────────────────────────┐
│ MagicPanel 容器                                             │
│                                                            │
│  /app/data/deps/rule-repo          ← Git 工作树副本（持久卷）│
│        │                                                   │
│        │ 同步：文件 → 面板实体                              │
│        ▼                                                   │
│  rule_providers（kind=repo）   snippets（source=repo）       │
│        │                                                   │
│        │ 构建                                               │
│        ▼                                                   │
│  产物 rule-providers / script-providers 段                  │
│        │  url = {FEED}/res/rule/<name>                     │
└────────┼───────────────────────────────────────────────────┘
         │ 客户端从面板拉（协议不变）
         ▼
    Stash / Mihomo
```

**关键事实（已实测）**：`/res/rule/<name>` 端点只读 `rule_providers.content`，**完全不看 URL**（`server/app/routers/feed.py:198`）。内容从哪来是面板内部的事，客户端零感知——这是「依赖内容可替换」成立的根本依据。

## 四、数据模型

### 4.1 `settings` 新增键

单仓库不需要单独建表，全部走 `settings`。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `deps_enabled` | `0` | 总开关，未配置时「自主维护」页显示引导 |
| `deps_url` | `git@github.com:astralwaveorg/magic-sets.git` | 仓库地址 |
| `deps_branch` | `main` | 分支 |
| `deps_auth` | `ssh` | `ssh` / `https` / `none` |
| `deps_private_key_enc` | '' | Fernet 密文；只写不读，接口永不回显 |
| `deps_token_enc` | '' | HTTPS 方式用；同样加密 |
| `deps_commit_name` | `MagicPanel` | 提交身份 name |
| `deps_commit_email` | `magicpanel@localhost` | 提交身份 email |
| `deps_sync_hours` | `12` | 拉取间隔（小时） |
| `deps_auto_push` | `1` | 保存并提交后是否自动 push |
| `deps_auto_create_rule_sources` | `1` | 仓库新增 `rule/*.yaml` 时是否自动建规则来源（见 §六） |
| `deps_exclude_paths` | `.git,.github,.env,*.bak,.*` | 排除的路径 glob，逗号分隔，可配（见 §5.2） |
| `deps_max_file_bytes` | `2097152` | 单文件编辑上限（2 MB） |
| `deps_last_sync_at` | '' | 上次成功同步时间（内部） |
| `deps_last_commit` | '' | 上次同步到的 commit（内部） |
| `deps_last_error` | '' | 上次失败原因（内部） |

工作树路径固定为 `/app/data/deps/rule-repo`，不作为配置项（只有一个仓库，改了也没意义）。

### 4.2 `rule_providers` 增列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `repo_path` | TEXT NOT NULL DEFAULT '' | 仓库内相对路径，如 `rule/chat-extra.yaml`。`kind='repo'` 时必填 |

`kind` 取值扩展：新增 `repo`；`remote`（抓 URL）/ `inline`（面板内建）语义不变。

### 4.3 `snippets` 增列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source` | TEXT NOT NULL DEFAULT 'local' | `local`（面板内建）/ `repo`（引用仓库文件） |
| `repo_path` | TEXT NOT NULL DEFAULT '' | `source='repo'` 时必填，仓库内相对路径 |

### 4.4 新表 `repo_migrations`

存档迁移前的原始配置，供回退与核对（详见 §九）。

## 五、仓库契约

### 5.1 目录约定

仓库里**任何文件**都能在自主维护页浏览与管理，但只有两类路径会被面板**消费**：

```
<仓库根>/
  rule/<name>.yaml       → 规则集合（rule-providers）—— 会被自动引入
  script/<name>.yaml     → 脚本片段素材 —— 需手动在「拓展模块」页引用
  rewrite/<name>.yaml    → 重写片段素材 —— 需手动在「拓展模块」页引用
  其它任意路径/文件       → 仅文件管理，不被消费
```

### 5.2 排除清单

排除清单存 `deps_exclude_paths`，逗号分隔的 **glob 模式**，逐项与仓库内路径做 `fnmatch` 匹配（`.*` 匹配任意点开头路径）。

默认值：

```
.git,.github,.env,*.bak,*
```

| 模式 | 含义 |
| --- | --- |
| `.git` | Git 元数据目录，永远不可碰、不可管理、不可编辑 |
| `.github` | CI 配置 |
| `.env` | 环境文件（可能含凭据） |
| `*.bak` | 备份文件 |
| `.*` | **所有点开头的路径**（`.editorconfig`、`.gitignore`、`.gitattributes` 等） |

用户在设置里可增删条目；删掉 `.*` 即放开所有点开头文件（`.git` 仍不可放开）。

被排除的路径在自主维护页完全不显示（不树、不计数、不候选）。

> 排除只影响**面板的管理范围**，不影响 Git 自身：仓库里的 `.gitattributes`、`.gitignore` 照常对 Git 生效，只是不在面板里出现。

### 5.3 文件头注释

沿用仓库既有格式（28 个集合文件已经是这个格式，不新造元数据）：

```yaml
# 名称: chat-extra
# behavior: domain
# 条目: 43
# 说明: 即时通讯补充域名——blackmatrix7 与 geosite 都没有收录的小众聊天应用。
payload:
  - +.discord.com
```

| 头字段 | 必需 | 作用 |
| --- | --- | --- |
| `# 名称:` | 是 | 展示名。**规则集合以文件名为准**（文件名是引用键），片段以名称为准 |
| `# behavior:` | rule 必需 | `domain` / `ipcidr` / `classical` |
| `# 适用引擎:` | 片段可选 | `stash` / `mihomo` / `all`，用于填 snippet 的 engine |
| `# 条目:` | 否 | 仅展示；同步时重算并提示不一致 |
| `# 说明:` | 否 | 展示用；同步时写入 snippet 的 note |

### 5.4 面板实体映射

| 仓库路径 | 面板实体 | 引入方式 | 映射键 |
| --- | --- | --- | --- |
| `rule/chat-extra.yaml` | 规则来源 `chat-extra` | **自动**（可关） | 文件名去扩展名 |
| `script/ua-apple.yaml` | 拓展模块（category=script） | **手动引用** | 用户在「拓展模块」页选文件时指定 |
| `rewrite/ad-block.yaml` | 拓展模块（category=rewrite） | **手动引用** | 同上 |
| 其它路径 | 无 | — | 仅文件管理 |

**字段归属**：

| 字段 | 归属 | 同步时的处理 |
| --- | --- | --- |
| content | 仓库 | 仓库 → 面板覆盖；面板**不允许**直接编辑仓库托管实体的 content |
| behavior / format | 仓库（rule） | 以文件头为准，冲突时纠正面板值并记审计 |
| engine | 仓库（片段） | 以文件头「适用引擎」为准，缺省沿用现值 |
| category | 仓库（片段） | 由引用时选择的目录决定 |
| note | 仓库（片段） | 以文件头「说明」为准 |
| **enabled** | **面板** | **仓库不覆盖**——是否启用是面板的能力，与文件库无关 |
| name / sort | 面板 | 仓库不覆盖 |
| 规则引用关系 | 面板 | 仓库不感知 |

## 六、拓展模块与文件库的解耦

### 6.1 为什么要解耦

现状面板的 `snippets` 表与仓库的 `script/`、`rewrite/` **各存一份相同内容**（已实测 6 条逐字完全一致）：

| 面板拓展模块 | 仓库文件 | 内容 | 启用状态 |
| --- | --- | --- | --- |
| 请求 UA 伪装为移动版 Safari | `script/ua-mobile.yaml` | 完全一致 | 否 |
| Apple 服务 UA（音乐/视频） | `script/ua-apple.yaml` | 完全一致 | 否 |
| 请求头去跟踪 | `script/strip-headers.yaml` | 完全一致 | **是** |
| 常见广告域名拦截 | `rewrite/ad-block.yaml` | 完全一致 | 否 |
| 隐私请求头（DNT） | `rewrite/do-not-track.yaml` | 完全一致 | 否 |
| 强制 HTTP 引擎（80 端口） | `rewrite/force-http-engine.yaml` | 完全一致 | 否 |

这是「同一件事两份清单」的又一例：改一边就要改另一边，迟早漂移。

**解耦后的模型**：

- **自主维护页** = 文件库的文件管理（浏览、编辑、提交、推送）
- **「拓展模块」页** = 面板的功能开关（决定用哪个片段、是否启用、什么引擎）

两者不再是"自动同步"，而是**显式引用**。

### 6.2 引入流程

```
① 自主维护页：新建 script/foo.yaml（或仓库里本来就有）→ 提交推送
② 同步：面板拉到该文件，文件树里能看到
③ 「拓展模块」页 → 添加 → 来源选「仓库文件」→ 选 script/foo.yaml
   → 自动带出：名称（文件头）、分类（目录）、引擎（文件头「适用引擎」）、内容（文件全文）
   → 校验通过（YAML 合法、非空映射、不含受保护键）→ 保存
④ 之后该片段的 content 由仓库管理；「拓展模块」页只管启用与否
```

**不自动引入**（D12）：仓库里放了 `script/foo.yaml` 不会自己变成拓展模块。理由：

- 拓展模块是**可选增强**（不引入只是少个功能），而规则集合是**分流的必需输入**（不建来源就没法挂规则）——两者的引入成本与必要性不同，不该用同一套自动化策略
- 仓库里堆文件不等于面板就该用，用不用由用户显式决定

因此**规则集合仍然自动引入**（`rule/*.yaml` → 规则来源），并提供设置项 `deps_auto_create_rule_sources` 允许关掉。

### 6.3 「拓展模块」页新增的「来源」维度

| 来源 | 表单表现 | content 存哪 | 能否编辑内容 |
| --- | --- | --- | --- |
| 面板内建 | 文本域（可用内置预设填充） | `snippets.content` | 可以 |
| 仓库文件 | 下拉选文件（候选见下） | `snippets.content`（由同步填充） | **不可以**，只读 + 「在自主维护中编辑」跳转 |

**内容改动只允许发生在自主维护页**（D15）：拓展模块页与规则来源页对仓库托管实体一律只读。
否则会出现"拓展模块页改了 content → 下次同步被仓库内容覆盖 → 用户的编辑静默丢失"。

**候选文件的范围**：`rule/` 下的文件**永远排除**——规则集合的格式是

```yaml
payload:
  - +.example.com
```

`payload` 是合法的 YAML 键但不是客户端认识的产物顶层键，当片段合并进产物会多出一个无效键。

`rule/` 之外的范围有三种取法（见 §十七 待确认 1）：

| 取法 | 候选 | 特点 |
| --- | --- | --- |
| A 窄 | 只有 `script/` 与 `rewrite/` 下的 `.yaml` | 最保守，与仓库目录约定完全一致；将来加 `dns/` 之类目录要改代码 |
| B 宽 | 除 `rule/` 外所有 `.yaml`（含未来新目录） | 最灵活，但用户可能误选非片段文件 |
| C 折中 | 默认列 `script/` 与 `rewrite/`，提供「显示全部文件」开关切到宽 | 两种都能用，代价是多一个开关 |

被排除清单命中的文件不进候选。

### 6.4 内置预设的定位

`src/snippetPresets.js` 里的 17 个预设**只是"填入表单"的模板，不是已存在的条目**（实测 `applyPreset()` 只把内容填进表单，用户保存才成条目）。保留它，但调整分工：

- `general` / `dns` / `panel` 类预设（IPv6、嗅探、Fake-IP 过滤、首页磁贴…）是**面板自己的配置**，留在前端
- `script` / `rewrite` 类预设中与仓库文件重复的 6 个**从预设列表移除**——那 6 个改为"从仓库文件选"，避免两处维护同一份内容

### 6.5 引用关系的约束

- **一个仓库文件最多被一个拓展模块引用**（唯一约束）。否则产物里会合并两段相同内容，后写的覆盖先写的，纯属冗余
- snippet 引用仓库文件后，**仓库文件改名 = 引用失效**（`repo_path` 对不上）→ 标记「源文件缺失」并停用，不自动删
- snippet 引用仓库文件后，**仓库文件被删** → 同上

## 七、Git 操作层

新文件 `server/app/services/repo_manager.py`，只负责 Git，不含业务判断。

### 7.1 命令封装

统一用 `subprocess` 调 git，**禁止 `shell=True`**。每次调用注入：

```
git -c user.name=<name> -c user.email=<email>
    -c core.hooksPath=/dev/null
    -c commit.gpgsign=false
    -c pull.rebase=false
    -c safe.directory=/app/data/deps/rule-repo
    -C /app/data/deps/rule-repo ...
```

SSH 方式额外注入 `GIT_SSH_COMMAND="ssh -i <临时私钥> -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new"`。
临时私钥写在 `<workdir>/.git/.mp_key`，权限 600，用完立即删除（`try/finally` 保证异常路径也删）。

> 这套命令序列已人工验证可用（2026-10-25 用真实密钥跑通 clone → commit → push）。

### 7.2 状态机

```
                 ┌─────────────┐
   clone ───────▶│  未初始化    │
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐   git fetch
                 │   已克隆    │◀──────────────┐
                 └──────┬──────┘               │
        ┌───────────────┼───────────────┐       │
        ▼               ▼               ▼       │
   ┌─────────┐   ┌──────────┐   ┌──────────┐  │
   │ 工作区干净│   │ 有本地改动│   │ 有冲突    │◀─┘
   └────┬────┘   └────┬─────┘   └────┬─────┘
        │             │  commit      │ 手工解决
        │             ▼              ▼
        │        ┌──────────┐   ┌──────────┐
        │        │ 待推送    │   │  待推送   │
        │        └────┬─────┘   └────┬─────┘
        │             │  pull --rebase（先拉最新）
        │             └──────┬──────┘
        │                    │ 冲突则回到「有冲突」
        ▼                    ▼

```

### 7.3 关键命令序列

**首次克隆**

```
git clone --branch <branch> --single-branch <url> /app/data/deps/rule-repo
```

失败分类（要给用户看得懂的提示，不能只回传 stderr）：

| 现象 | 提示 |
| --- | --- |
| `Permission denied (publickey)` | 私钥与 GitHub 上的公钥不匹配 |
| `Permission to <repo>.git denied to deploy key` | 部署密钥是只读的，需在 GitHub 上勾 "Allow write access"（**已实测遇到过**） |
| `Repository not found` | 地址错，或部署密钥没加到这个仓库 |
| `Could not resolve hostname` | 容器出网问题 |

**拉取**（定时同步 / 推送前）

```
git fetch origin <branch>
git status --porcelain
# 有本地改动 → 先 commit（信息前缀「面板自动提交：」）
git pull --rebase origin <branch>
```

`pull --rebase` 失败且 `git diff --name-only --diff-filter=U` 非空 → 冲突态。

**提交与推送**

```
git add -A <白名单目录>
git commit -m "<message>"
git push origin <branch>
```

push 被拒（`non-fast-forward`）→ 自动 `pull --rebase` 后重试一次，仍失败按冲突处理。

**冲突三方内容**

```
git show :1:<path>    # 共同祖先 base
git show :2:<path>    # 本地 ours
git show :3:<path>    # 远端 theirs
```

**解决冲突**（手工编辑为主）

```
# 页面把三方内容 + 冲突标记写入工作树文件 → 用户编辑 → 校验无残留标记
git add <path>
git commit -m "解决冲突：<path>"
```

「整体用远端」「整体保留本地」是快捷按钮，等价于 `git checkout --theirs/--ours -- <path>` + `git add`，供"不打算手工合并"时快速收场。

### 7.4 并发

模块级 `threading.Lock` 串行化所有 Git 操作。定时同步与用户操作抢锁时：用户优先，定时同步跳过并记「已延后」；定时同步持锁时用户请求排队（前端显示等待）。

## 八、现状冲突与解法

| # | 冲突 | 解法 |
| --- | --- | --- |
| 1 | 主仓库有 submodule 引用 | 目标态删除 `.gitmodules` 与 `magic-sets/` 目录。主仓库**没有任何代码引用 magic-sets**（已实测：除 `.gitmodules` 外零引用），移除成本极低 |
| 2 | 规则来源 28 个指向 jsDelivr | 改成 `kind='repo'` + `repo_path`。**客户端零影响**（`/res/rule/<name>` 只读 content）。切换后 jsDelivr 环节消失 |
| 3 | 改 jsDelivr 缓存那一大段文档与约定 | 目标态删除「改完必须换 commit 号 URL」的约定；`AGENTS.md` 约束 19 改写为"自维护层由依赖文件库托管" |
| 4 | 面板 6 个拓展模块与仓库文件内容重复 | 按 §六 迁移为 `source='repo'`，`src/snippetPresets.js` 里重复的 6 个预设移除。**已逐字核对内容完全一致，切换零行为变化** |
| 5 | 仓库托管实体的 `enabled` 被谁控制 | **归面板**（D6）。仓库不覆盖，文件库只管内容 |
| 6 | 文件头 `behavior` 与面板 `behavior` 不一致 | **文件头是事实来源**：同步时以文件头为准纠正面板值，记审计 + 界面提示 |
| 7 | 规则内容变更不触发自动构建 | 现状 `collect_snapshot` 的 rule_providers 不含 content，policy_sha 不变。**本期修**：把 content 的 sha256 纳入快照，仓库同步后自然触发自动构建 |
| 8 | 可追溯性 | 原来 submodule pin 天然知道用的哪版规则。目标态在构建记录里写明**依赖库 commit**，产物与构建详情都可追溯 |
| 9 | 仓库新增 `rule/*.yaml` | **自动建**规则来源（`kind='repo'`、behavior 取自文件头、默认启用），可用 `deps_auto_create_rule_sources` 关掉。**不自动建规则**——规则仍在「分流规则」页手工挂，避免规则表被自动污染 |
| 10 | 仓库新增 `script|rewrite/*.yaml` | **不自动建**拓展模块（D12）。状态条提示"N 个候选片段未被引用"，可跳转到「拓展模块」页 |
| 11 | 仓库删除文件 | 若对应实体被引用（`refs.rules_targeting`）→ 拒绝删除并列出引用；无引用 → 删除实体与文件 |
| 12 | 换仓库地址 | 原仓库的实体按 `repo_path` 找不到对应文件 → 标记「源文件缺失」并停用（不自动删） |
| 13 | 仓库里 CRLF/LF 混用 | 仓库加 `.gitattributes`（`*.yaml text eol=lf`），否则每次 diff 都是全文件 |
| 14 | 仓库为空（无 commit） | 本地建分支首次提交，`git push -u origin <branch>` |
| 15 | 提交身份与钩子 | `user.name`/`user.email` 走设置项；`core.hooksPath=/dev/null` 防止仓库自带钩子干扰 |
| 16 | 二进制文件 | 只读展示 + 下载，不提供编辑；同步时跳过 |

## 九、数据安全与回滚

> 迁移阶段的第一优先级。原则：**任何时候都不丢数据，任何一步都能退回去。**

### 9.1 五条原则

1. **迁移全程不删除任何 `content`**：切换只是改 `kind`/`source`/`repo_path`，内容原地保留
2. **原始配置留档**：切换前把每个实体的 `kind`/`source`/`url`/`repo_path`/`behavior`/`content_sha256`/`rule_count` 存档
3. **逐批核对**：一批核对通过才做下一批，不通过就停
4. **回退是一键操作**：不需要重建，只需还原存档字段
5. **Git 历史不丢**：冲突解决产生新 commit，不改写历史；不用 force push

### 9.2 存档表

```sql
CREATE TABLE IF NOT EXISTS repo_migrations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  batch INTEGER NOT NULL DEFAULT 1,
  object_type TEXT NOT NULL,     -- rule_provider / snippet
  object_id INTEGER NOT NULL,
  origin_kind TEXT NOT NULL,     -- remote / inline / local
  origin_url TEXT NOT NULL DEFAULT '',
  origin_repo_path TEXT NOT NULL DEFAULT '',
  origin_behavior TEXT NOT NULL DEFAULT '',
  origin_engine TEXT NOT NULL DEFAULT '',
  origin_category TEXT NOT NULL DEFAULT '',
  origin_enabled INTEGER NOT NULL DEFAULT 1,
  origin_content_sha TEXT NOT NULL DEFAULT '',
  origin_rule_count INTEGER,
  switched_at TEXT NOT NULL,
  reverted_at TEXT
);
```

### 9.3 分批切换

**规则来源 28 个：4 批 × 7。** 每批流程：

1. **批前快照**：把该批的原始字段写入 `repo_migrations`
2. **切换**：`kind='repo'`、`repo_path='rule/<name>.yaml'`
3. **同步**：从仓库读文件覆盖 content
4. **核对清单**（逐项比对，任何一项不过就不进入下一批）：

| 核对项 | 判据 |
| --- | --- |
| 来源名一致 | 仓库文件名去扩展名 == 规则来源名 |
| behavior 一致 | 面板 behavior == 文件头 `# behavior:` |
| 内容一致 | 面板 content 的 sha256 == 仓库文件 sha256 |
| 条目数一致 | 面板 rule_count == 文件头 `# 条目:` == 实际 payload 条数 |
| 分发路径不变 | 产物里该 rule-provider 的 url 仍为 `{FEED}/res/rule/<name>` |
| 产物一致 | 切换前后对同一策略快照构建，产物 rule-providers 段字节一致 |

5. **回退**：核对不过 → 用 `repo_migrations` 还原该批，不进入下一批

**拓展模块 6 个：1 批。** 额外核对项：

| 核对项 | 判据 |
| --- | --- |
| 内容一致 | 面板 content == 仓库文件去头注释后（**已预核对：6 条全部逐字一致**） |
| 启用状态保留 | `enabled` 与切换前完全相同（`请求头去跟踪` 原本是启用的） |
| 引擎与分类保留 | `engine` / `category` 与切换前相同 |

### 9.4 移除 submodule

随第 2 步合并为一个提交。要点：

- 删 `.gitmodules` 与 `magic-sets/` 目录
- **依赖库仓库必须保持可访问**（公开或至少部署密钥有读权限），否则规则无从获取
- 迁移前在面板侧做一次内容快照留档：`repo_migrations` 存 sha256，**内容本体**建议另存一份到 `data/backup/`（面板已有备份机制）

### 9.5 仓库历史

Git 自身保证。面板不做 `reset --hard` / `push --force` / `filter-branch`；只做 `fetch`/`pull --rebase`/`commit`/`push`。误操作回退用「回滚到指定提交」（生成一个 revert 提交，不改写历史）。

## 十、同步与构建联动

### 10.1 同步流程（定时 12 小时 / 手动立即同步）

```
取锁 → git fetch → 判断工作区状态
  ├─ 干净 → pull --rebase
  ├─ 有本地改动 → 提交（信息前缀「面板自动提交：」）→ pull --rebase
  └─ 冲突 → 记录冲突列表，停在冲突态，同步结束（不推）
  ↓
遍历仓库文件（排除清单内的路径跳过）：
  rule/*.yaml         → 校验 → 找/建规则来源 → 覆盖 content
  script|rewrite/*.yaml → 校验 → 若已被拓展模块引用 → 覆盖该 snippet 的 content
                          若未被引用 → 不动（只统计"未引用候选数"）
  其它文件 → 不消费，只更新文件树状态
  ↓
写 last_sync_at / last_commit
```

同步**只 pull 不 push**（D7）。冲突解决后需要用户显式触发一次推送。

### 10.2 内容 → 构建

- `collect_snapshot` 的 rule_providers 项增加 `"content_sha": sha256(content)`。内容变了 → policy_sha 变 → 定时自动构建照常触发（现状 content 不进快照，规则改了不会自动重建，是现存缺陷）
- snippet 的 content **本来就**在快照里（`builds.py:113`），片段改了会自动触发重建

同步完成后把 `last_commit` 写进构建 note，让构建详情能回答"这次构建用的是哪版依赖"。

### 10.3 与「规则来源」「拓展模块」页的关系

| 页 | 仓库托管实体的表现 |
| --- | --- |
| 规则来源 | URL 列显示仓库路径而不是 URL；「抓取」按钮改为「从仓库同步」（只更新该文件内容，不做 Git 操作）；启用/停用仍在这里做 |
| 拓展模块 | 新增「来源」列（面板内建 / 仓库：<路径>）；仓库托管的条目内容只读 + 「在自主维护中编辑」跳转；启用/停用仍在这里做 |

## 十四、特殊场景清单

| 场景 | 处理 |
| --- | --- |
| 首次配置，目录为空 | 引导流程：填地址 → 配密钥 → clone |
| 公钥没贴到 GitHub | clone 报 `Permission denied (publickey)`，页面给可执行提示 |
| **部署密钥是只读的** | push 报 `denied to deploy key`，页面提示"需在 GitHub 勾 Allow write access"（**已实测遇到过**） |
| 仓库地址错 | `Repository not found`，提示检查地址与密钥所属仓库 |
| 容器出网不通 | `Could not resolve host`，提示检查网络 |
| 远端更新 + 本地干净 | fast-forward，无冲突 |
| 远端更新 + 本地有改动 | 先自动 commit 再 pull --rebase，成功则 push |
| 同一文件两边都改 | 冲突 → 手工编辑为主，三方对照 + 两个快捷按钮 |
| push 被拒（非 fast-forward） | 自动 pull --rebase 重试一次，仍失败转冲突 |
| 本地有未提交改动时点同步 | 自动 commit（带「面板自动提交：」前缀）后继续 |
| 定时同步撞上用户编辑 | 锁串行；编辑期间定时同步延后并在状态条提示 |
| 二进制文件 | 只读展示 + 下载，不提供编辑 |
| 文件名含空格/中文 | 允许，URL 编码要正确 |
| 路径穿越 / 符号链接 / 绝对路径 | 白名单校验拒绝 |
| 非 UTF-8 文件 | 拒绝并提示编码问题 |
| 单文件超 2 MB | 拒绝 |
| CRLF/LF 混用 | 仓库 `.gitattributes` 统一 |
| 面板重启 / 崩溃 | 工作树与冲突中间态在持久卷，可恢复 |
| 换仓库地址 | 原实体标记「源文件缺失」并停用，不自动删 |
| 仓库被删除/改名 | 同上，页面明确提示 |
| 定时同步失败 | 记 `automation_runs` + 审计，状态条显示失败原因，不刷屏 |
| 误操作要回滚 | 提交历史页可看 diff，支持生成 revert 提交（不改写历史） |
| 私钥写错 | 设置页重新填；旧私钥从 DB 覆盖 |
| 排除清单把某目录排掉 | 该目录文件完全不显示；已引用它的实体标「源文件缺失」 |

## 十六、风险与取舍

| 风险 | 应对 |
| --- | --- |
| 镜像 +60 MB（装 git） | 可接受；若不接受，退到 dulwich，冲突处理降级为"提示后人工下载 diff 合并" |
| 自动 push 是对外可见变更 | 提交前预览 diff + 明确显示目标仓库地址 + 二次确认；定时任务不 push |
| 部署密钥只读导致 push 失败 | 已在实测中发现并在引导页写明要勾 Allow write access |
| 私钥落 DB | Fernet 加密 + 只写不读 + 临时文件用完删；与设备令牌同等级保护 |
| 依赖库成为单点 | 库不可用时，实体表里已有 content 仍可继续构建分发（**不阻断**）；迁移存档里还留有 content sha256 |
| 自动提交产生噪音提交 | 只在冲突态或同步前有本地改动时提交，提交信息统一前缀可识别 |
| 仓库托管实体的 content 在两个页面都不好看 | 规则来源页/拓展模块页都改成只读 + 跳转自主维护页编辑 |
| 行级自动合并未实现 | 手工编辑为主路径 + 两个整文件快捷按钮，覆盖绝大多数场景 |

## 十七、待确认

**1. 候选片段范围取 A / B / C？**

背景：仓库里除了规则集合（`rule/`）和现成的两类片段（`script/`、`rewrite/`），将来还可能有别的目录。拓展模块页「添加 → 仓库文件」时，下拉里应该出现哪些文件？

假设依赖库里有这些文件：

```
rule/chat-extra.yaml     ← 规则集合（payload 格式，永远不能当片段）
script/ua-apple.yaml      ← 脚本片段
rewrite/ad-block.yaml     ← 重写片段
dns/force-ipv6.yaml       ← 假设以后新建的目录
README.md                 ← 文档
```

| 取法 | 下拉里出现 | 适用 |
| --- | --- | --- |
| **A 窄** | `script/ua-apple.yaml`、`rewrite/ad-block.yaml` | 最保守，完全对齐现有仓库目录约定；将来要支持新目录得改代码 |
| **B 宽** | 上面三个 yaml（含 `dns/force-ipv6.yaml`） | 最灵活，未来加目录不用改；但用户可能误选非片段文件 |
| **C 折中（推荐）** | 默认只列 `script/` 与 `rewrite/`，旁边一个「显示全部文件」开关可切到宽 | 两种都能用，代价是多一个开关 |

`rule/` 在三种取法下都排除——`payload:` 不是合法的产物顶层键，合并进去会多出客户端不认的键。

**2. 仓库托管实体的「内容只读」边界已确认（D15）**

- 拓展模块页、规则来源页对仓库托管实体一律只读
- 改内容只能去自主维护页改文件
- 仓库托管实体的 `enabled` / `name` / `sort` 仍在原页面改（面板能力，与文件库无关）
