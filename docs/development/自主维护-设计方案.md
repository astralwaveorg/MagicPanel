# 自主维护：设计方案

> 状态：**设计讨论稿**，尚未开发。确认后作为开发依据。
> 起草：2026-10-25（v5：补 `kind='repo'` 对产物渲染与门户展示的影响，修正来源分布口径）
> 关联：[重构迭代方案](重构迭代方案.md)（菜单重排、拓展模块加来源类型、构建发布合并、首页交互规范 §1.5）
> 参考：`AGENTS.md` 约束 19/20/22、`docs/reference/规则集与分流设计.md`

## 一、定位与目标

把「当前系统依赖的文件库」的管理能力做进 MagicPanel 后台，菜单叫 **自主维护**。

达成后应当成立：

1. **MagicPanel 独立**：仓库里不再含任何规则内容，不再有 submodule 引用，克隆 MagicPanel 即可运行。
2. **依赖内容外置且可替换**：依赖文件库的地址、分支、鉴权凭据都在后台配置，用户可以指向自己的任何仓库，MagicPanel 不绑定 `astralwaveorg/magic-sets`。
3. **仓库即文件库**：自主维护页是一个**文件管理系统**，能浏览仓库里**全部文件**（除排除项外），不只是 `rule/` 里的规则集合。
4. **编辑即入库**：在页面上改文件、保存、提交、推送，走的是标准 Git 流程；远端有更新时自动拉取并提示处理合并冲突。
5. **规则内容即时生效**：自维护规则集合不再经 jsDelivr 中转，改完推上去面板就能拿到，没有 12 小时缓存。
6. **三种来源一视同仁**：远程抓取、面板内联、仓库托管三类规则来源在后台与门户的展示口径一致，切换来源不改变它在分流里的地位。

### 非目标

- 不做 Git 托管服务，不代替 GitHub，只做**客户端**。
- **只支持一个依赖文件库**。多仓库没有实际场景，不做。
- 不做行级三方自动合并；冲突以**手工编辑**为主路径。
- **不与「拓展模块」做任何关联**（见 §五、六）。
- 不改变客户端拉配置的协议（`/res/rule/<name>` 与 `/res/provider/<name>` 保持不变）。

## 二、关键决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 容器内装**系统 git**（`git` + `openssh-client`） | 需要真 merge/rebase、冲突标记、三方 blob 读取。dulwich 冲突能力残缺；GitHub API 做不了真合并 |
| D2 | 运行时把仓库 clone 到 `/app/data/deps/rule-repo` | `/app/data` 是持久卷，重启不丢；镜像里没有 submodule |
| D3 | 仓库配置存 `settings` 表，私钥 Fernet 加密 | 单仓库用不着单独建表；沿用 `security.encrypt_text` |
| D4 | **单仓库** | 一个 MagicPanel 对应一个文件库，没有多仓库场景 |
| D5 | 规则来源新增第三种 `kind='repo'`（仓库托管） | 与 `remote`（抓 URL）并列：用户不用自己填 jsDelivr 地址，也没有 12 小时缓存 |
| D6 | **仓库是内容的事实来源** | 面板侧只额外持有"启用状态"这类运行态字段 |
| D7 | 定时任务**只 pull 不 push**；push 只在用户点「保存并提交」时发生 | 避免定时自动提交产生意料之外的提交 |
| D8 | 构建快照纳入规则内容的 sha256 | 现状 `collect_snapshot` 不含 content，规则内容变了不触发自动构建——这是现存缺陷，顺手修 |
| D9 | 冲突解决以**手工编辑**为主 | 规则文件通常整体重写而非逐行改，整文件覆盖反而容易丢改动 |
| D10 | 迁移**分批**执行，每批有核对清单 | 数据不能丢 |
| D11 | 移除 submodule 与第 2 步合并为一个提交 | 提交粒度无意义，数据安全有意义 |
| D12 | 规则集合**自动**引入来源（默认开，可关） | 规则集合是分流的必需输入——不建来源就没法挂规则，28 个手动配不现实 |
| D13 | 排除清单可配置，**默认排除所有点开头路径** | `.git` 是 Git 元数据永远不可碰；点开头路径（`.github`、`.editorconfig` 等）默认不纳管，用户可按需放开 |
| D14 | 仓库托管实体的内容**只读**，改动只发生在自主维护页 | 否则用户改了 content，下次同步被仓库覆盖，改动静默丢失 |
| D15 | **拓展模块不与仓库关联** | 拓展模块自己支持「内联内容 / 远程 URL」两种来源（见重构方案 §三），用户自己填地址即可，不需要面板做关联 |
| D16 | 门户与后台对三种来源用**同一套中文标签**：`远程` / `内联` / `仓库` | 首页规则来源区块已经有「远程 / 内联」两态标签（见重构方案 §1.5）。`kind='repo'` 落地后必须补第三态，否则这类来源在首页会被误标成「内联」或空标签 |

## 三、架构总览

```
        ┌────────── 依赖文件库（magic-sets 或用户自己的仓库）──────────┐
        │  rule/            ← 被面板消费：自动引入为规则来源             │
        │  script/ rewrite/ … ← 素材区：面板只管理文件，不消费            │
        └────────────┬───────────────────────────┬───────────────────┘
                     │ git pull（默认 12 小时）    │ git push（保存并提交时）
                     ▼                           ▲
┌────────────────────────────────────────────────────────────┐
│ MagicPanel 容器                                             │
│                                                            │
│  /app/data/deps/rule-repo          ← Git 工作树副本（持久卷）│
│        │                                                   │
│        │ 同步：rule/*.yaml → 规则来源 content                  │
│        ▼                                                   │
│  rule_providers（kind=repo）                                  │
│        │                                                   │
│        │ 构建                                               │
│        ▼                                                   │
│  产物 rule-providers 段：url = {FEED}/res/rule/<name>        │
└────────┼───────────────────────────────────────────────────┘
         │ 客户端从面板拉（协议不变）
         ▼
    Stash / Mihomo
```

**关键事实（已实测）**：`/res/rule/<name>` 端点只读 `rule_providers.content`，**完全不看 URL**（`server/app/routers/feed.py:198`）。内容从哪来是面板内部的事，客户端零感知——这是「依赖内容可替换」成立的根本依据。

## 四、数据模型

### 4.1 `settings` 新增键

单仓库不需要单独建表，全部走 `settings`。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `deps_enabled` | `0` | 总开关，未配置时「自主维护」页显示引导 |
| `deps_url` | `git@github.com:astralwaveorg/magic-sets.git` | 仓库地址 |
| `deps_branch` | `main` | 分支 |
| `deps_auth` | `ssh` | `ssh` / `https` / `none` |
| `deps_private_key_enc` | '' | Fernet 密文；只写不读，接口永不回显 |
| `deps_token_enc` | '' | HTTPS 方式用；同样加密 |
| `deps_commit_name` | `MagicPanel` | 提交身份 name |
| `deps_commit_email` | `magicpanel@localhost` | 提交身份 email |
| `deps_sync_hours` | `12` | 拉取间隔（小时） |
| `deps_auto_push` | `1` | 保存并提交后是否自动 push |
| `deps_auto_create_rule_sources` | `1` | 仓库新增 `rule/*.yaml` 时是否自动建规则来源（见 §六） |
| `deps_exclude_paths` | `.git,.github,.env,*.bak,.*` | 排除的路径 glob，逗号分隔，可配（见 §五） |
| `deps_max_file_bytes` | `2097152` | 单文件编辑上限（2 MB） |
| `deps_last_sync_at` | '' | 上次成功同步时间（内部） |
| `deps_last_commit` | '' | 上次同步到的 commit（内部） |
| `deps_last_error` | '' | 上次失败原因（内部） |

工作树路径固定为 `/app/data/deps/rule-repo`，不作为配置项（只有一个仓库，改了也没意义）。

### 4.2 `rule_providers` 增列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `repo_path` | TEXT NOT NULL DEFAULT '' | 仓库内相对路径，如 `rule/chat-extra.yaml`。`kind='repo'` 时必填 |

`kind` 取值：`remote`（抓 URL）/ `inline`（面板内建）/ `repo`（仓库托管，内容由同步写入）。

**产物渲染层不需要改**：`compiler/render.py` 的 `_rule_provider_entry` 只看 `name` / `format` / `behavior` / `client_interval` / `interval`，`kind` 完全不参与；分发端点 `/res/rule/<name>` 也只读 `content`（`server/app/routers/feed.py:198`）。所以 `kind` 从 `remote` 换成 `repo` 后，**产物逐字节不变**——这也是 §9.3 核对清单里「产物一致」一项能成立的前提。

**定时抓取天然不受影响**：`services/scheduler.py` 的 `_run_rule_fetch` 只挑 `kind='remote'` 的来源，`kind='repo'` 的内容由仓库同步写入，不会被定时抓取覆盖。

### 4.3 `snippets` 不动

拓展模块的数据模型改动（新增 `source`/`url`/`format`/`interval`/`client_interval`/`proxy_url_enc`）属于**重构迭代方案 §3.2**，与仓库无关。自主维护功能**不触碰** `snippets` 表。

### 4.4 新表 `repo_migrations`

存档迁移前的原始配置，供回退与核对（详见 §九）。

## 五、仓库契约

### 5.1 目录约定

仓库里**任何文件**都能在自主维护页浏览与管理。面板只消费一类路径：

```
<仓库根>/
  rule/<name>.yaml       → 规则集合（rule-providers），会被自动引入（现 28 个）
  script/<name>.yaml     → 素材区：面板只管理文件，不消费（现 3 个）
  rewrite/<name>.yaml    → 素材区：面板只管理文件，不消费（现 3 个）
  README.md              → 素材区：仅文件管理
  其它任意路径/文件       → 素材区：仅文件管理
```

分类目录由仓库自己定，面板不管——它只认「是不是 `rule/` 下的 yaml」。

**素材区不与面板的任何实体挂钩**。用户想用仓库里的某个片段，去「拓展模块」页新建一个「远程 URL」条目，把地址填进去即可——面板不列文件、不自动建、不自动引用（D15）。

### 5.2 排除清单

排除清单存 `deps_exclude_paths`，逗号分隔的 **glob 模式**，逐项与仓库内路径做 `fnmatch` 匹配（`.*` 匹配任意点开头路径）。

默认值：

```
.git,.github,.env,*.bak,.*
```

| 模式 | 含义 |
| --- | --- |
| `.git` | Git 元数据目录，永远不可碰、不可管理、不可编辑 |
| `.github` | CI 配置 |
| `.env` | 环境文件（可能含凭据） |
| `*.bak` | 备份文件 |
| `.*` | **所有点开头的路径**（`.editorconfig`、`.gitignore`、`.gitattributes` 等） |

用户在设置里可增删条目；删掉 `.*` 即放开所有点开头文件（`.git` 仍不可放开）。

被排除的路径在自主维护页完全不显示（不树、不计数）。

> 排除只影响**面板的管理范围**，不影响 Git 自身：仓库里的 `.gitattributes`、`.gitignore` 照常对 Git 生效，只是不在面板里出现。

### 5.3 文件头注释

沿用仓库既有格式（28 个集合文件已经是这个格式，不新造元数据）：

```yaml
# 名称: chat-extra
# behavior: domain
# 条目: 43
# 说明: 即时通讯补充域名——blackmatrix7 与 geosite 都没有收录的小众聊天应用。
payload:
  - +.discord.com
```

| 头字段 | 必需 | 作用 |
| --- | --- | --- |
| `# 名称:` | 是 | 展示名。**规则集合以文件名为准**（文件名是引用键） |
| `# behavior:` | rule 必需 | `domain` / `ipcidr` / `classical` |
| `# 条目:` | 否 | 仅展示；同步时重算并提示不一致 |
| `# 说明:` | 否 | 展示用 |

**现状已核实（2026-10-25）**：`rule/` 下 28 个文件全部以 `# 名称:` 开头，且全部带 `# 说明:`（无缺省）；`script/` 与 `rewrite/` 下 6 个文件用 `# 名称:` + `# 说明:` + `# 注意:` 三行头。

`# 说明:` 这行现在有第二个用处：门户首页规则来源区块的每一行会把它显示成集合说明（重构方案 §1.5），门户端点 `POST /api/v1/portal/provider-detail` 从文件头解析这行。

### 5.4 面板实体映射

| 仓库路径 | 面板实体 | 引入方式 | 映射键 |
| --- | --- | --- | --- |
| `rule/chat-extra.yaml` | 规则来源 `chat-extra` | **自动**（可关） | 文件名去扩展名 |
| 其它路径 | 无 | — | 仅文件管理 |

### 5.5 校验规则

同步与保存时都跑：

- `behavior` 在 `domain|ipcidr|classical` 内
- `format` 固定 `yaml`（`mrs` 是二进制，不适合仓库托管）
- `payload` 是列表，条目非空、每条以 `+.` 或纯域名开头
- 文件 UTF-8 可解码；单文件 ≤ `deps_max_file_bytes`
- 路径必须在仓库根下、不得含 `..`、不得是绝对路径、不得穿越符号链接
- **二进制文件**（含 NUL 字节或解码失败）→ 只读展示 + 下载，不提供编辑

## 六、与拓展模块的关系：无关联

**两边都不做「关联」**：

| | 自主维护（仓库） | 拓展模块（功能片段） |
| --- | --- | --- |
| 管什么 | 仓库里的**文件** | 产物里的**功能片段** |
| 来源类型 | Git 仓库 | 内联内容 / 远程 URL |
| 谁提供内容 | 仓库的文件 | 用户写的，或从任意 URL 抓的 |
| 自动关联 | — | **无** |

用户想把仓库里的 `script/ua-apple.yaml` 用起来，路径是：

1. 自主维护页里改好这个文件 → 提交推送
2. 拓展模块页新建条目 → 来源类型选「远程 URL」→ 填该文件的可访问地址 → 设抓取间隔

面板不列仓库文件、不自动建条目、不自动改写已有的内联条目。

> 现存 6 个内联条目与仓库同名文件内容完全一致（已逐字核对）。是否改为「远程 URL」指向仓库，是**用户的选择**，不在面板的自动流程里。

## 七、Git 操作层

新文件 `server/app/services/repo_manager.py`，只负责 Git，不含业务判断。

### 7.1 命令封装

统一用 `subprocess` 调 git，**禁止 `shell=True`**。每次调用注入：

```
git -c user.name=<name> -c user.email=<email>
    -c core.hooksPath=/dev/null
    -c commit.gpgsign=false
    -c pull.rebase=false
    -c safe.directory=/app/data/deps/rule-repo
    -C /app/data/deps/rule-repo ...
```

SSH 方式额外注入 `GIT_SSH_COMMAND="ssh -i <临时私钥> -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new"`。
临时私钥写在 `<workdir>/.git/.mp_key`，权限 600，用完立即删除（`try/finally` 保证异常路径也删）。

> 这套命令序列已人工验证可用（2026-10-25 用真实密钥跑通 clone → commit → push）。

### 7.2 状态机

```

   clone ───────▶│  未初始化    │
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐   git fetch
                 │   已克隆    │◀──────────────┐
                 └──────┬──────┘               │
        ┌───────────────┼───────────────┐       │
        ▼               ▼               ▼       │
   ┌─────────┐   ┌──────────┐   ┌──────────┐  │
   │ 工作区干净│   │ 有本地改动│   │ 有冲突    │◀─┘
   └────┬────┘   └────┬─────┘   └────┬─────┘
        │             │  commit      │ 手工解决
        │             ▼              ▼
        │        ┌──────────┐   ┌──────────┐
        │        │ 待推送    │   │  待推送   │

        │             │  pull --rebase（先拉最新）
        │             └──────┬──────┘
        │                    │ 冲突则回到「有冲突」
        ▼                    ▼
   ┌──────────────────────────────────┐
   │  pull --rebase → 同步内容到面板  │
   │  → push（若 auto_push）          │
```

### 7.3 关键命令序列

**首次克隆**

```
git clone --branch <branch> --single-branch <url> /app/data/deps/rule-repo
```

失败分类（要给用户看得懂的提示，不能只回传 stderr）：

| 现象 | 提示 |
| --- | --- |
| `Permission denied (publickey)` | 私钥与 GitHub 上的公钥不匹配 |
| `Permission to <repo>.git denied to deploy key` | 部署密钥是只读的，需在 GitHub 上勾 "Allow write access"（**已实测遇到过**） |
| `Repository not found` | 地址错，或部署密钥没加到这个仓库 |
| `Could not resolve hostname` | 容器出网问题 |

**拉取**（定时同步 / 推送前）

```
git fetch origin <branch>
git status --porcelain
# 有本地改动 → 先 commit（信息前缀「面板自动提交：」）
git pull --rebase origin <branch>
```

`pull --rebase` 失败且 `git diff --name-only --diff-filter=U` 非空 → 冲突态。

**提交与推送**

```
git add -A <白名单目录>
git commit -m "<message>"
git push origin <branch>
```

push 被拒（`non-fast-forward`）→ 自动 `pull --rebase` 后重试一次，仍失败按冲突处理。

**冲突三方内容**

```
git show :1:<path>    # 共同祖先 base
git show :2:<path>    # 本地 ours
git show :3:<path>    # 远端 theirs
```

**解决冲突**（手工编辑为主）

```
# 页面把三方内容 + 冲突标记写入工作树文件 → 用户编辑 → 校验无残留标记
git add <path>
git commit -m "解决冲突：<path>"
```

「整体用远端」「整体保留本地」是快捷按钮，等价于 `git checkout --theirs/--ours -- <path>` + `git add`，供"不打算手工合并"时快速收场。

### 7.4 并发

模块级 `threading.Lock` 串行化所有 Git 操作。定时同步与用户操作抢锁时：用户优先，定时同步跳过并记「已延后」；定时同步持锁时用户请求排队（前端显示等待）。

## 八、现状冲突与解法

| # | 冲突 | 解法 |
| --- | --- | --- |
| 1 | 主仓库有 submodule 引用 | 目标态删除 `.gitmodules` 与 `magic-sets/` 目录。主仓库**没有任何代码引用 magic-sets**（已实测：除 `.gitmodules` 外零引用），移除成本极低 |
| 2 | 线上 102 个启用来源中，**28 个**指向 magic-sets（自维护仓库），其余 74 个是第三方仓库 | 只把指向 magic-sets 的 28 个改成 `kind='repo'`；第三方 74 个（MetaCubeX 32 / blackmatrix7 41 / TG-Twilight 1）保持 `kind='remote'` 不动。**客户端零影响**（`/res/rule/<name>` 只读 content）。切换后自维护层不再经过 jsDelivr |
| 3 | 改 jsDelivr 缓存那一大段文档与约定 | 目标态删除「改完必须换 commit 号 URL」的约定；`AGENTS.md` 约束 19 改写为"自维护层由依赖文件库托管" |
| 4 | 仓库托管来源的 `enabled` 被谁控制 | **归面板**（D6）。仓库不覆盖，文件库只管内容 |
| 5 | 文件头 `behavior` 与面板 `behavior` 不一致 | **文件头是事实来源**：同步时以文件头为准纠正面板值，记审计 + 界面提示 |
| 6 | 规则内容变更不触发自动构建 | 现状 `collect_snapshot` 的 rule_providers 不含 content，policy_sha 不变。**本期修**：把 content 的 sha256 纳入快照，仓库同步后自然触发自动构建 |
| 7 | 可追溯性 | 原来 submodule pin 天然知道用的哪版规则。目标态在构建记录里写明**依赖库 commit**，产物与构建详情都可追溯 |
| 8 | 仓库新增 `rule/*.yaml` | **自动建**规则来源（`kind='repo'`、behavior 取自文件头、默认启用），可用 `deps_auto_create_rule_sources` 关掉。**不自动建规则**——规则仍在「分流规则」页手工挂，避免规则表被自动污染 |
| 9 | 仓库删除文件 | 若对应来源被引用（`refs.rules_targeting`）→ 拒绝删除并列出引用；无引用 → 删除来源与文件 |
| 10 | 换仓库地址 | 原仓库的来源按 `repo_path` 找不到对应文件 → 标记「源文件缺失」并停用（不自动删） |
| 11 | 仓库里 CRLF/LF 混用 | 仓库加 `.gitattributes`（`*.yaml text eol=lf`），否则每次 diff 都是全文件 |
| 12 | 仓库为空（无 commit） | 本地建分支首次提交，`git push -u origin <branch>` |
| 13 | 提交身份与钩子 | `user.name`/`user.email` 走设置项；`core.hooksPath=/dev/null` 防止仓库自带钩子干扰 |
| 14 | 二进制文件 | 只读展示 + 下载，不提供编辑；同步时跳过 |
| 15 | 仓库里 script/rewrite 与面板拓展模块重复 | **不做自动关联**（D15）。用户自行决定是否在拓展模块里填远程 URL 指向它们 |
| 16 | 门户与后台只认 `remote` / `inline` 两态来源 | `kind='repo'` 落地后补第三态（远程 / 内联 / 仓库，见 D16），并把「复制地址」「预览」改成对仓库托管来源复制**仓库内路径**而非上游 URL（详见 §10.4） |

## 九、数据安全与回滚

> 迁移阶段的第一优先级。原则：**任何时候都不丢数据，任何一步都能退回去。**

### 9.1 五条原则

1. **迁移全程不删除任何 `content`**：切换只是改 `kind`/`repo_path`，内容原地保留
2. **原始配置留档**：切换前把每个来源的 `kind`/`url`/`repo_path`/`behavior`/`content_sha256`/`rule_count` 存档
3. **逐批核对**：一批核对通过才做下一批，不通过就停
4. **回退是一键操作**：不需要重建，只需还原存档字段
5. **Git 历史不丢**：冲突解决产生新 commit，不改写历史；不用 force push

### 9.2 存档表

```sql
CREATE TABLE IF NOT EXISTS repo_migrations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  batch INTEGER NOT NULL DEFAULT 1,
  object_type TEXT NOT NULL,     -- rule_provider
  object_id INTEGER NOT NULL,
  origin_kind TEXT NOT NULL,     -- remote / inline
  origin_url TEXT NOT NULL DEFAULT '',
  origin_repo_path TEXT NOT NULL DEFAULT '',
  origin_behavior TEXT NOT NULL DEFAULT '',
  origin_enabled INTEGER NOT NULL DEFAULT 1,
  origin_content_sha TEXT NOT NULL DEFAULT '',
  origin_rule_count INTEGER,
  switched_at TEXT NOT NULL,
  reverted_at TEXT
);
```

### 9.3 分批切换（magic-sets 的 28 个：4 批 × 7）

每批流程：

1. **批前快照**：把该批的原始字段写入 `repo_migrations`
2. **切换**：`kind='repo'`、`repo_path='rule/<name>.yaml'`
3. **同步**：从仓库读文件覆盖 content
4. **核对清单**（逐项比对，任何一项不过就不进入下一批）：

| 核对项 | 判据 |
| --- | --- |
| 来源名一致 | 仓库文件名去扩展名 == 规则来源名 |
| behavior 一致 | 面板 behavior == 文件头 `# behavior:` |
| 内容一致 | 面板 content 的 sha256 == 仓库文件 sha256 |
| 条目数一致 | 面板 rule_count == 文件头 `# 条目:` == 实际 payload 条数 |
| 分发路径不变 | 产物里该 rule-provider 的 url 仍为 `{FEED}/res/rule/<name>` |
| 产物一致 | 切换前后对同一策略快照构建，产物 rule-providers 段字节一致 |

5. **回退**：核对不过 → 用 `repo_migrations` 还原该批，不进入下一批

**拓展模块不参与这次迁移**（D15：两边无关联）。现存 6 个与仓库同名的内联条目是否改成「远程 URL」，由用户自行决定。

### 9.4 移除 submodule

随第 2 步合并为一个提交。要点：

- 删 `.gitmodules` 与 `magic-sets/` 目录
- **依赖库仓库必须保持可访问**（公开或至少部署密钥有读权限），否则规则无从获取
- 迁移前在面板侧做一次内容快照留档：`repo_migrations` 存 sha256，**内容本体**建议另存一份到 `data/backup/`（面板已有备份机制）

### 9.5 仓库历史

Git 自身保证。面板不做 `reset --hard` / `push --force` / `filter-branch`；只做 `fetch`/`pull --rebase`/`commit`/`push`。误操作回退用「回滚到指定提交」（生成一个 revert 提交，不改写历史）。

## 十、同步与构建联动

### 10.1 同步流程（定时 12 小时 / 手动立即同步）

```
取锁 → git fetch → 判断工作区状态
  ├─ 干净 → pull --rebase
  ├─ 有本地改动 → 提交（信息前缀「面板自动提交：」）→ pull --rebase
  └─ 冲突 → 记录冲突列表，停在冲突态，同步结束（不推）
  ↓
遍历仓库文件（排除清单内的路径跳过）：
  rule/*.yaml → 校验 → 找/建规则来源 → 覆盖 content
  其它文件    → 不消费，只更新文件树状态
  ↓
写 last_sync_at / last_commit
```

同步**只 pull 不 push**（D7）。冲突解决后需要用户显式触发一次推送。

### 10.2 内容 → 构建

`collect_snapshot` 的 rule_providers 项增加 `"content_sha": sha256(content)`。内容变了 → policy_sha 变 → 定时自动构建照常触发（现状 content 不进快照，规则改了不会自动重建，是现存缺陷）。

同步完成后把 `last_commit` 写进构建 note，让构建详情能回答"这次构建用的是哪版依赖"。

### 10.3 与「规则来源」页的关系

| 项 | 仓库托管来源的表现 |
| --- | --- |
| URL 列 | 显示仓库路径而不是 URL |
| 「抓取」按钮 | 改为「从仓库同步」（只更新该文件内容，不做 Git 操作） |
| 启用/停用 | 仍在这里做 |
| 内容编辑 | 只读，改动去自主维护页 |

### 10.4 与首页规则来源区块的关系

首页的规则来源区块（见重构方案 §1.5）是**只读视图**，但仓库托管来源在那里也必须显示得对，否则会出现「后台明明是仓库托管，首页看着像普通远程」的错位。

| 位置 | 仓库托管来源的表现 | 远程来源 | 内联来源 |
| --- | --- | --- | --- |
| 来源标签 | **仓库** | 远程 | 内联 |
| 「复制地址」复制的内容 | **仓库内路径**（`rule/chat-extra.yaml`） | 上游 URL | 按钮禁用（没有地址） |
| 详情弹层的「上游地址」 | 显示**仓库路径 + 所在仓库与分支** | 上游 URL | 显示「面板内联内容，没有上游地址」 |
| 详情弹层的其它字段 | 与远程来源同款（行为、格式、条目数、大小、抓取状态与时间、两侧间隔、内容预览） | 同左 | 同左 |

实现要点：

- 门户数据里补 `repo_path` 字段（`server/app/routers/portal.py` 的 `_provider_meta` 已经在算 `origin`，再加一个 `repo_path` 即可）
- 详情端点 `POST /api/v1/portal/provider-detail` 的返回体同样带 `repo_path`，弹层按 `kind` 决定「复制地址」复制什么
- `kind` 标签三态化：`remote → 远程`、`inline → 内联`、`repo → 仓库`（D16），后台「规则来源」页的来源列同步改三态
- 仓库托管来源**不参与**定时抓取（§4.2 已说明），门户显示的「抓取状态 / 最近抓取」对这类来源改称「同步状态 / 最近同步」，取 `deps_last_sync_at`

> 这部分只在第 2 步切换数据时才生效。第 1 步（能力就位）阶段线上全是 `remote` / `inline`，门户展示不变。

## 十四、特殊场景清单

| 场景 | 处理 |
| --- | --- |
| 首次配置，目录为空 | 引导流程：填地址 → 配密钥 → clone |
| 公钥没贴到 GitHub | clone 报 `Permission denied (publickey)`，页面给可执行提示 |
| **部署密钥是只读的** | push 报 `denied to deploy key`，页面提示"需在 GitHub 勾 Allow write access"（**已实测遇到过**） |
| 仓库地址错 | `Repository not found`，提示检查地址与密钥所属仓库 |
| 容器出网不通 | `Could not resolve host`，提示检查网络 |
| 远端更新 + 本地干净 | fast-forward，无冲突 |
| 远端更新 + 本地有改动 | 先自动 commit 再 pull --rebase，成功则 push |
| 同一文件两边都改 | 冲突 → 手工编辑为主，三方对照 + 两个快捷按钮 |
| push 被拒（非 fast-forward） | 自动 pull --rebase 重试一次，仍失败转冲突 |
| 本地有未提交改动时点同步 | 自动 commit（带「面板自动提交：」前缀）后继续 |
| 定时同步撞上用户编辑 | 锁串行；编辑期间定时同步延后并在状态条提示 |
| 二进制文件 | 只读展示 + 下载，不提供编辑 |
| 文件名含空格/中文 | 允许，URL 编码要正确 |
| 路径穿越 / 符号链接 / 绝对路径 | 白名单校验拒绝 |
| 非 UTF-8 文件 | 拒绝并提示编码问题 |
| 单文件超 2 MB | 拒绝 |
| CRLF/LF 混用 | 仓库 `.gitattributes` 统一 |
| 面板重启 / 崩溃 | 工作树与冲突中间态在持久卷，可恢复 |
| 换仓库地址 | 原来源标记「源文件缺失」并停用，不自动删 |
| 仓库被删除/改名 | 同上，页面明确提示 |
| 定时同步失败 | 记 `automation_runs` + 审计，状态条显示失败原因，不刷屏 |
| 误操作要回滚 | 提交历史页可看 diff，支持生成 revert 提交（不改写历史） |
| 私钥写错 | 设置页重新填；旧私钥从 DB 覆盖 |
| 排除清单把某目录排掉 | 该目录文件完全不显示；已引用它的来源标「源文件缺失」 |

## 十五、迁移路径

分三步，每步都可独立验证、可回滚。**目标：依赖库仓库保持可访问，数据零丢失。**

### 第 1 步：面板侧能力就位（不切数据）

- `settings` 加键；`rule_providers` 加 `repo_path` 列与迁移；建 `repo_migrations` 表
- 实现 `services/repo_manager.py` + 路由 + 前端页
- 镜像装 git

## 十六、风险与取舍

| 风险 | 应对 |
| --- | --- |
| 镜像 +60 MB（装 git） | 可接受；若不接受，退到 dulwich，冲突处理降级为"提示后人工下载 diff 合并" |
| 自动 push 是对外可见变更 | 提交前预览 diff + 明确显示目标仓库地址 + 二次确认；定时任务不 push |
| 部署密钥只读导致 push 失败 | 已在实测中发现并在引导页写明要勾 Allow write access |
| 私钥落 DB | Fernet 加密 + 只写不读 + 临时文件用完删；与设备令牌同等级保护 |
| 依赖库成为单点 | 库不可用时，来源表里已有 content 仍可继续构建分发（**不阻断**）；迁移存档里还留有 content sha256 |
| 自动提交产生噪音提交 | 只在冲突态或同步前有本地改动时提交，提交信息统一前缀可识别 |
| 仓库托管来源的内容在规则来源页不能改 | 只读 + 跳转自主维护页编辑（与 D14 一致） |
| 仓库托管来源在门户上被误标成「远程 / 内联」 | 来源标签改三态（远程 / 内联 / 仓库），门户与后台同一套标签（D16、§10.4） |
| 行级自动合并未实现 | 手工编辑为主路径 + 两个整文件快捷按钮，覆盖绝大多数场景 |

## 十七、已确认事项（2026-10-25）

| 事项 | 结论 |
| --- | --- |
| 依赖库数量 | 单仓库，不做多仓库 |
| 排除清单默认值 | 默认排除所有点开头路径（`.*`），加 `.git` / `.github` / `.env` / `*.bak`；可在设置里放开 |
| 规则集合自动建来源 | 默认开（`deps_auto_create_rule_sources=1`），可关 |
| 冲突解决粒度 | 手工编辑为主，附两个整文件快捷按钮 |
| 定时任务 | 只 pull，不自动 push |
| 鉴权 | SSH 部署密钥（已配置并验证写权限） |
| 规则来源切换 | 分 4 批 × 7，逐批核对 |
| submodule 移除 | 与第 2 步合并为一个提交 |
| 仓库托管实体能否在规则来源页直接编辑 | 不能，内容改动只在自主维护页 |
| **与拓展模块的关系** | **无关联**。拓展模块自己支持「内联内容 / 远程 URL」，用户自己填地址 |
| **来源标签的第三态** | 远程 / 内联 / **仓库**，门户与后台同一套中文标签（D16） |
| **仓库托管来源的「复制地址」** | 复制**仓库内路径**（`rule/<name>.yaml`），不是上游 URL（§10.4） |
| **切换范围** | 只切 magic-sets 的 28 个来源；第三方 74 个保持 `kind='remote'` |
| **产物是否变化** | 不变。渲染层不读 `kind`，分发端点只读 `content`（§4.2） |
