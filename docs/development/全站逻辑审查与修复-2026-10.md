# 全站逻辑审查与修复（2026-10）

> 目标：把「产物配置重构」这一轮做完之后，对整个系统做一次**以逻辑正确性为主**的全面检查——
> 功能是否缺失、有没有逻辑 bug、有没有漏洞、会不会不稳定、自动化还能不能更强——
> 并把问题逐条定位、修复、测试、重新发布。
>
> 审查时间：2026-10-20 晚间。范围：后端全部 routers / services / compiler / db、前端全部页面、
> 部署与运维链路（Dockerfile / compose / deploy.sh / 备份）。
>
> ⚠️ 术语说明：本文是**历史审查记录**，事实与时间点保持原样。发布模型此后已从「稳定 / 候选通道」双轨改为**单一版本生命周期状态机**（`builds.status` = `BUILT` / `TESTING` / `PRODUCTION` / `OFFLINE`，设备订阅环境为 `production` / `testing`），文中涉及发布位置的表述已按当前术语改写；重构的影响面见[构建发布状态机重构 · 影响面分析报告](构建发布状态机重构-影响面分析报告.md)。

## 一、审查方法

- 四路并行只读审查：① 后端 API 与数据层 ② 构建→校验→发布→分发链路 ③ 前端交互与状态 ④ 部署/运维/安全/数据可靠性。
- 每条结论都要求**给出文件:行号与代码依据**，能在临时数据目录复现的必须复现。
- 修复原则：能改行为的改行为；改不动语义的地方（例如"谁可以删审计"是产品决定）写进文档而不是偷偷放过。
- 回归保障：每类修复补一条端到端用例，`cd server && ../.venv/bin/python -m pytest tests -q` 保持全绿。

## 三、中等问题（已修复）

- **ETag 未覆盖正文**：改 base_url 后客户端拿 304 却仍是旧域名 → ETag 改为正文哈希。
- **feed 用写事务包住整个响应**：设备拉取抢写锁 → 读走只读连接，计数走独立短事务；设备下载不再写审计（避免审计被客户端流量淹没）。
- **`mihomo -t` 共用固定 `config.yaml`**：并发构建互相污染 → 每次校验用独立临时目录，Geo 数据只读共享。
- **来源名未限制 URL 安全字符**：含空格/斜杠会让 provider URL 失效 → 名称白名单（允许中文与 emoji）+ 路径段百分号转义。
- **功能模块绕过结构键保护**：列表追加语义能造出重名节点/永不生效的规则 → 与基础配置同款保护。
- **删设备残留 `base_configs` 孤儿行**：孤儿行进构建快照、改变 `policy_sha` → 同事务清理。
- **唯一键冲突返回 500**：并发下应返回 409 → 保持现状但补说明（见"遗留"）。
- **审计明文记录 `core_proxy` 凭据** → 按键名与 URL userinfo 统一打码。
- **备份导出含口令散列/盐/PIN 散列** → 文档标注导出文件等同凭据（保留导出能力，恢复依赖它）。
- **无自动备份**：NAS 一次磁盘故障即全量不可恢复 → 新增 `scripts/backup.sh`（`VACUUM INTO` 一致性快照 + 主密钥归档 + 完整性校验 + 轮转），compose 里加每日备份容器。
- **迁移在 import 期执行、失败即崩溃循环** → 迁移失败改为降级启动并打印明确原因；部署脚本加健康检查失败回滚与 data 目录预检。
- **`rsync --delete` 会删掉 NAS 侧 `.env`/override** → 加入排除项。
- **INFO 日志全丢 + 容器日志无轮转** → 加 `logging.basicConfig`；compose 加 `json-file` 轮转（10MB × 3）。
- **数据目录权限 0644**（产物含明文节点凭据）→ 目录 700、数据库与产物 600。
- **健康检查只探一个接口** → 改为接口 + 数据目录可写 + 磁盘余量；部署域名验证改打 `/api/v1/setup/status`（SPA 兜底对任何路径都 200）。
- **依赖未锁版本** → `requirements.txt` 锁版本，测试依赖拆到 `requirements-dev.txt`。
- **HSTS `includeSubDomains`** 施加在整个家族域名 → 去掉。
- **留存策略**：构建产物、构建记录、审计日志、过期会话现在每天清理一次，且**不依赖调度总开关**（独立 lifespan 任务）；旧的 `builds` 记录与快照一并回收（曾发布过的保留最近 20 个，更早的彻底清理）；卡在 `building` 的僵尸构建标记为失败。
- **门户与页面文案**：`MagicHub` → `MagicPanel`；`Mihomo / Clash` → `Mihomo`；补 `Linux` 平台标签。

## 四、前端修复

严重：

1. **策略组保存必然 400**：`strategy` 恒带 `consistent-hashing` 发出，后端对非 `load-balance` 直接拒绝 → 只有 load-balance 才发 strategy。
2. **「系统默认」作用域点开必 400 且显示上一层的旧内容**：`select()` 先切标题再请求、无错误处理 → 加 try/catch 与回滚；后端允许查看系统默认。
3. **审计「加载更早记录」永久置灰**：条件写反 → 改为真正的分页（后端加 offset/total/keyword）。

中等：

- 八个列表页补"加载失败 + 重试"状态（原先加载中/空/失败三态不分，失败时显示"还没有 XX"）。
- 设备"平台"改为由"引擎平台"推导，后端同步校验，避免设备平台与产物平台不一致。
- 规则类型补齐 4 种（原缺 `DOMAIN-REGEX`/`GEOSITE`/`PROCESS-NAME`/`SRC-IP-CIDR`），与后端白名单一致。
- 表单约束与后端一致（间隔上限、URL/匹配值长度、名称字符集）。
- 新建设备 / 轮换令牌后，订阅地址直接显示在弹窗里（原来只能去门户找）。
- 「恢复本层」返回真实覆盖信息（保留个人直连域名与 Fake-IP 过滤时不再显示"尚未做任何覆盖"）。
- 产物配置页提交时带上 `updated_at`，启用乐观锁（并发编辑会 409 而不是静默覆盖）。
- 概览页的可用率口径与「节点来源」页统一（以当前节点列表为准）。

## 五、术语与模型统一（与本轮重构同步）

- 「发布目标」统一更名为「**引擎平台**」（= 引擎 + 平台，对应一类客户端），UI、接口提示、文档同步。
- 基础配置作用域从"四级联动"收敛为"**三层联动**"：系统默认 → 通用配置（引擎 + 平台）→ 设备配置。
- 引擎平台改名/删除时自动维护策略组与规则的"适用平台"引用（此前会静默剔除一大片产物）。
- 合并语义用开源库 `deepmerge` 显式声明：字典递归合并、列表整体替换、同键后者覆盖。

## 八、2026-10-20 晚追加二：机房优先、日韩自动组、兜底规则顺序

| 需求/问题 | 落地 |
|---|---|
| Gemini 不可用 | 逐节点实测出口 IP 与 Google 判定：**所有可用的美国出口 Gemini 都返回 200** → 服务端规则链与出口都没问题（规则链：gemini.google.com → 人工智能 → 美国优先 → 美国自动 ✓）。问题在客户端/账号侧：当时节点大面积不可用（21:15 巡检 260 个节点失败 134 个），且"账号地区 / 出口地区 / 浏览器环境"三者不一致时 Google 才会给这句提示。处置：把「美国优先」固定到自有美国机房节点（固定出口 IP），消除"出口漂移"这个变量 |
| 优先美国要优先用自己的「美国机房」 | 策略组新增「本地节点排在最前」开关（`local_first`）；「美国优先」（fallback）改为：`[单] 🇺🇸 美国机房 01 → [单] 🇺🇸 美国机房 02 → 美国自动 → 日本自动 → …`；「人工智能」是 select 且首选「美国优先」，因此自动继承 |
| 新增日韩自动组 | 「日韩自动」= url-test，过滤日本+韩国节点（`(?i)🇯🇵\|🇰🇷\|日本\|韩国\|…`），来源为 4 个机场；同时加入「节点选择」便于手工切换 |
| 指定域名/IP 走日韩 | 用**内联规则来源**实现（面板原生支持）：`日韩服务`（behavior=domain，10 条 DOMAIN-SUFFIX）+ `日韩服务-IP`（behavior=ipcidr，`158.179.167.131/32,no-resolve`），各配一条 RULE-SET 指向「日韩自动」。规则集 URL 做百分号编码，客户端可直接拉取 |
| **兜底规则被排到中间**（自查发现） | 管理界面允许任意顺序，界面里若把 MATCH 放在中间，其后的规则永远不生效。现在：① 渲染时自动把兜底规则提到产物末尾（并给出提示）；② 产物校验拦截"兜底之后还有普通规则"；③ 生产数据已重排 |

另发现：本地单节点（trojan 的三个「机房 02」）实测全部连不通，且**本地单节点不在面板测速范围内**，用户看不到可用性——已记入遗留项。

**「空组保护」占位节点**：产物里恒定注入一个 `http://127.0.0.1:1` 的死节点，作用是让 url-test / fallback / load-balance 组永远非空——部分客户端会把**空策略组隐式改写成 DIRECT**，那会让指向它的规则变成直连（国内出口）。它永远连不通，因此只能起"存在性"作用，不能当出口。原先插在成员**首位**（客户端若不做健康检查直接取第一个成员，就会选到这个死节点 ✗），现已改到**末位**——真实节点优先，占位只兜底。

## 九、2026-10-21 追加：策略组 / 分流规则批量操作与清空按钮

| 需求 | 落地 |
|---|---|
| 策略组编辑项"成员"改名 | 编辑对话框与列表列统一改为 **包含策略**（relay 变体："包含策略（按顺序组成转发链，至少两个…）"） |
| 策略组批量操作 | 表格加多选列；工具栏出现「批量修改 / 批量删除 / 取消选择」。批量修改可统一改：包含策略、适用引擎平台、本地节点、节点来源、过滤正则、客户端可见性。**relay 组不支持节点来源**，这类组自动跳过该字段并在结果里说明 |
| 分流规则批量操作 | 同上；可批量改：目标、适用引擎平台、启用状态、备注、no-resolve；工具栏另有「批量启用 / 批量停用」。规则类型与匹配值天然逐条不同，不做批量 |
| 批量删除的引用保护 | 策略组被其它组或规则引用 → 保留并说明原因；规则是 MATCH/FINAL 兜底 → 不删（删了设备就没兜底了） |
| 多选控件旁加清空 | 新增 `MultiSelectClear` 组件；策略组编辑的 4 个多选（包含策略、适用引擎平台、本地节点、节点来源）与分流规则的适用引擎平台都带「清空」按钮（无选中内容时禁用） |
| 批量修改的字段语义 | 未勾选的字段 = 保持原样；勾上但内容为空 = 清空该项；`null` = 不修改（后端语义与前端勾选一致） |

顺带补了一个防护：批量改"包含策略"时会剔除**指向自己的引用**（自引用客户端加载会失败）。

## 十一、2026-10-21 追加三：移动端分页组件适配

| 问题 | 修复 |
|---|---|
| 手机上分页组件布局错乱（**所有**列表页都有） | 根因：`Pager` 组件把「总数 + 每页条数 + 页码 + 跳页」硬编码在一行，窄屏（≤768px）放不下，被挤变形。改为**响应式**：宽屏保持完整布局；窄屏切换为「共 N 条 + 每页条数」一行 + 「上一页 / 页码 / 下一页」一行居中，页码按钮缩到 5 个并用小号样式 |
| 分页样式各页不统一 | `审计日志`、`规则来源` 两页各自直接写 `el-pagination`（同样有窄屏问题），现统一改用 `Pager` 组件，全站仅此一处分页实现 |
| 极端窄屏仍可能溢出 | 分页容器加 `overflow-x: auto` 与换行保护 |

移动端与 APK 效果一致：APK 是 WebView 壳，加载的是线上站点，**网页端 UI 改动在已安装的 App 里刷新即生效，无需重打包**（只有原生壳改动——悬浮按钮、刷新手势、主题、面板地址——才需要重新出包）。

## 十四、遗留与后续建议

1. **角色模型尚未启用**：所有维护者共享同一份数据、权限相同（这是既有产品约定）。若将来需要只读账号，
   在 `users.role` 上加 viewer 并对写接口加校验即可，数据结构已预留。
2. **列表接口未分页**：来源/策略组/规则在几百条规模仍可接受，再大应加分页（审计已分页）。
3. **设备令牌轮换后旧订阅地址立即失效**：客户端需重新导入，这是令牌制订阅的固有代价，界面已提示。
4. **测速间隔与构建间隔**：默认 1 小时是当前折中；上游机场限流严格时可调大。
5. **备份需要额外同步到 NAS 之外**：容器内备份与数据同盘，磁盘故障时一起没了——建议再加一条异地同步。
