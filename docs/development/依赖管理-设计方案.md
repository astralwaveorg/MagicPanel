# 依赖管理：设计方案

> 状态：**设计讨论稿**，尚未开发。确认后作为开发依据。
> 起草：2026-10-25（v2：按「依赖管理」定位重写）
> 关联：`AGENTS.md` 约束 19/20/22、`docs/reference/规则集与分流设计.md`

## 一、定位与目标

把「当前系统依赖的仓库与文件库」的管理能力做进 MagicPanel 后台，菜单叫 **依赖管理**。

达成后应当成立：

1. **MagicPanel 独立**：仓库里不再含任何规则内容，不再有 submodule 引用，克隆 MagicPanel 即可运行。
2. **依赖内容外置且可替换**：依赖仓库的地址、分支、鉴权凭据都在后台配置，用户可以指向自己的任何仓库，MagicPanel 不绑定 `astralwaveorg/magic-sets`。
3. **仓库即文件库**：依赖管理页是一个**文件管理系统**，能浏览仓库里**全部文件**（除 `.git` 等必要隐藏文件外），不只是 `rule/` 里的规则集合。
4. **编辑即入库**：在页面上改文件、保存、提交、推送，走的是标准 Git 流程；远端有更新时自动拉取并提示处理合并冲突。
5. **内容即时生效**：自维护集合不再经 jsDelivr 中转，改完推上去面板就能拿到，没有 12 小时缓存。

### 非目标

- 不做 Git 托管服务，不代替 GitHub，只做**客户端**。
- 不做行级三方自动合并；冲突以**手工编辑**为主路径。
- 不改变客户端拉配置的协议（`/res/rule/<name>` 与 `/res/provider/<name>` 保持不变）。

## 二、关键决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 容器内装**系统 git**（`git` + `openssh-client`） | 需要真 merge/rebase、冲突标记、三方 blob 读取。dulwich 冲突能力残缺；GitHub API 做不了真合并 |
| D2 | 运行时把仓库 clone 到 `/app/data/deps/<仓库>` | `/app/data` 是持久卷，重启不丢；镜像里没有 submodule |
| D3 | 仓库地址/分支/私钥存 `repos` 表，私钥 Fernet 加密 | 沿用 `security.encrypt_text`，与设备令牌、节点凭据同等级 |
| D4 | **支持多仓库** | 「依赖管理」定位就是"管理当前系统依赖的仓库"；数据模型一次做对，以后加仓库只加一行配置 |
| D5 | 规则来源与功能模块各新增一个 `repo` 托管标记 | 复用现有 `rule_providers` / `snippets` 两张表，不另起炉灶 |
| D6 | **仓库是内容的事实来源** | 面板侧只额外持有"启用状态"这类运行态字段 |
| D7 | 定时任务**只 pull 不 push**；push 只在用户点「保存并提交」时发生 | 避免定时自动提交产生意料之外的提交 |
| D8 | 构建快照纳入规则内容的 sha256 | 现状 `collect_snapshot` 不含 content，规则内容变了不触发自动构建——这是现存缺陷，顺手修 |
| D9 | 冲突解决以**手工编辑**为主 | 规则文件通常整体重写而非逐行改，整文件覆盖反而容易丢改动 |
| D10 | 迁移**分批**执行，每批有核对清单 | 数据不能丢 |
| D11 | 移除 submodule 与第 2 步合并为一个提交 | 提交粒度无意义，数据安全有意义 |

## 三、架构总览

```
   ┌──────────── 依赖仓库 A（magic-sets）────────────┐
   │  rule/   script/   rewrite/   README.md  ...   │
   └───────┬───────────────────────────┬───────────┘
           │ git pull（默认 12 小时）    │ git push（保存并提交时）
           ▼                           ▲
   ┌──────────── 依赖仓库 B（可选）────────────┐
   │  （同上结构）                              │
   └───────┬───────────────────────────┬───────────┘
           │                           │
           ▼                           ▲
┌────────────────────────────────────────────────────────────┐
│ MagicPanel 容器                                              │
│                                                              │
│  /app/data/deps/<repo>/          ← Git 工作树副本（持久卷） │
│        │                                                 │
│        │ 同步：文件 → 面板实体                              │
│        ▼                                                 │
│  rule_providers（kind=repo）  snippets（repo=1）            │
│        │                                                 │
│        │ 构建                                             │
│        ▼                                                 │
│  产物 rule-providers / script-providers 段                  │
│        │  url = {FEED}/res/rule/<name>                     │
└────────┼─────────────────────────────────────────────────┘
         │ 客户端从面板拉（协议不变）
         ▼
    Stash / Mihomo
```

**关键事实（已实测）**：`/res/rule/<name>` 端点只读 `rule_providers.content`，**完全不看 URL**（`server/app/routers/feed.py:198`）。内容从哪来是面板内部的事，客户端零感知——这是「依赖内容可替换」成立的根本依据。

## 四、数据模型

### 4.1 新表 `repos`

```sql
CREATE TABLE IF NOT EXISTS repos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT UNIQUE NOT NULL,              -- 展示名，如「自维护规则」
  kind TEXT NOT NULL DEFAULT 'git',       -- git（local 预留）
  url TEXT NOT NULL DEFAULT '',           -- 仓库地址
  branch TEXT NOT NULL DEFAULT 'main',
  auth TEXT NOT NULL DEFAULT 'ssh',       -- ssh / https / none
  private_key_enc TEXT NOT NULL DEFAULT '',
  token_enc TEXT NOT NULL DEFAULT '',
  commit_name TEXT NOT NULL DEFAULT 'MagicPanel',
  commit_email TEXT NOT NULL DEFAULT 'magicpanel@localhost',
  sync_hours INTEGER NOT NULL DEFAULT 12,
  auto_push INTEGER NOT NULL DEFAULT 1,
  workdir TEXT NOT NULL DEFAULT '',        -- 容器内工作树路径
  enabled INTEGER NOT NULL DEFAULT 1,
  last_sync_at TEXT,
  last_commit TEXT NOT NULL DEFAULT '',
  last_error TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

### 4.2 `rule_providers` 增列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `repo_id` | INTEGER NOT NULL DEFAULT 0 | 0 = 不由仓库托管；非 0 = 由该仓库托管 |
| `repo_path` | TEXT NOT NULL DEFAULT '' | 仓库内相对路径，如 `rule/chat-extra.yaml` |

`kind` 取值扩展：新增 `repo`；`remote`（抓 URL）/ `inline`（手工粘贴）语义不变。

### 4.3 `snippets` 增列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `repo_id` | INTEGER NOT NULL DEFAULT 0 | 0 = 面板内建；非 0 = 由仓库托管 |
| `repo_path` | TEXT NOT NULL DEFAULT '' | 如 `script/ua-apple.yaml` |

### 4.4 `settings` 增键

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `deps_enabled` | `0` | 总开关 |
| `deps_exclude_paths` | `.git,.github` | 排除的路径前缀，逗号分隔，可配置 |
| `deps_max_file_bytes` | `2097152` | 单文件编辑上限（2 MB） |

## 五、仓库契约

### 5.1 目录约定

仓库里**任何文件**都可以在依赖管理页浏览与管理，但只有三类路径会被面板**消费**：

```
<仓库根>/
  rule/<name>.yaml       → 规则来源（rule-providers）
  script/<name>.yaml     → 功能模块·脚本（snippets，category=script）
  rewrite/<name>.yaml    → 功能模块·重写（snippets，category=rewrite）
  其它任意路径/文件       → 仅文件管理，不被消费
```

### 5.2 排除清单

默认排除 `.git`、`.github`（点开头的隐藏目录一律默认排除）。排除清单在设置里可改。

`.git` **永远不可排除、不可管理、不可编辑**——它是 Git 自身的元数据，碰了仓库就坏。其余隐藏路径按清单排除，用户可自行放开。

### 5.3 文件头注释

沿用仓库既有格式（28 个集合文件已经是这个格式，不新造元数据）：

```yaml
# 名称: chat-extra
# behavior: domain
# 条目: 43
# 说明: 即时通讯补充域名——blackmatrix7 与 geosite 都没有收录的小众聊天应用。
payload:
  - +.discord.com
  - +.viber.com
```

| 头字段 | 必需 | 作用 |
| --- | --- | --- |
| `# 名称:` | 是 | 展示名。**规则集合以文件名为准**（文件名是引用键），脚本/重写片段以名称为准 |
| `# behavior:` | rule 必需 | `domain` / `ipcidr` / `classical` |
| `# 适用引擎:` | script/rewrite 可选 | `stash` / `mihomo` / `all`，用于填 snippet 的 engine |
| `# 条目:` | 否 | 仅展示；同步时重算并提示不一致 |
| `# 说明:` | 否 | 展示用；同步时写入 snippet 的 note |

### 5.4 面板实体映射

| 仓库路径 | 面板实体 | 映射键 |
| --- | --- | --- |
| `rule/chat-extra.yaml` | 规则来源 `chat-extra` | 文件名去扩展名 |
| `script/ua-apple.yaml` | 功能模块 key `script-ua-apple` | 目录名 + 文件名 |
| `rewrite/ad-block.yaml` | 功能模块 key `rewrite-ad-block` | 目录名 + 文件名 |

**同步方向与字段归属**：

| 字段 | 归属 | 同步时的处理 |
| --- | --- | --- |
| content | 仓库 | 仓库 → 面板覆盖；面板改 content → 写回仓库文件 |
| behavior / format | 仓库（rule） | 以文件头为准，冲突时纠正面板值并记审计 |
| engine | 仓库（script/rewrite） | 以文件头「适用引擎」为准，缺省沿用现值 |
| enabled | 面板 | 仓库**不覆盖**（"默认停用"写在文件头注释里，由用户手工启用） |
| note / category | 仓库（script/rewrite） | 以文件头「说明」为准 |
| 规则引用关系 | 面板 | 仓库不感知 |

### 5.5 校验规则

同步与保存时都跑：

- `behavior` 在 `domain|ipcidr|classical` 内
- `format` 固定 `yaml`（`mrs` 是二进制，不适合仓库托管）
- `payload` 是列表，条目非空、每条以 `+.` 或纯域名开头
- 文件 UTF-8 可解码；单文件 ≤ `deps_max_file_bytes`
- 路径必须在仓库根下、不得含 `..`、不得是绝对路径、不得穿越符号链接
- **二进制文件**（含 NUL 字节或解码失败）→ 只读展示 + 下载，不提供编辑

## 六、Git 操作层

新文件 `server/app/services/repo_manager.py`，只负责 Git，不含业务判断。

### 6.1 命令封装

统一用 `subprocess` 调 git，**禁止 `shell=True`**。每次调用注入：

```
git -c user.name=<name> -c user.email=<email>
    -c core.hooksPath=/dev/null
    -c commit.gpgsign=false
    -c pull.rebase=false
    -c safe.directory=<workdir>
    -C <workdir> ...
```

SSH 方式额外注入 `GIT_SSH_COMMAND="ssh -i <临时私钥> -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new"`。
临时私钥写在 `<workdir>/.git/.mp_key`，权限 600，用完立即删除（`try/finally` 保证异常路径也删）。

### 6.2 状态机

```
                 ┌─────────────┐
   clone ───────▶│  未初始化    │
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐   git fetch
                 │   已克隆    │◀──────────────┐
                 └──────┬──────┘               │
        ┌───────────────┼───────────────┐       │
        ▼               ▼               ▼       │
   ┌─────────┐   ┌──────────┐   ┌──────────┐  │
   │ 工作区干净│   │ 有本地改动│   │ 有冲突    │◀─┘
   └────┬────┘   └────┬─────┘   └────┬─────┘
        │             │  commit      │ 手工解决
        │             ▼              ▼
        │        ┌──────────┐   ┌──────────┐
        │        │ 待推送    │   │  待推送   │
        │        └────┬─────┘   └────┬─────┘
        │             │  pull --rebase（先拉最新）
        │             └──────┬──────┘
        │                    │ 冲突则回到「有冲突」
        ▼                    ▼
   ┌──────────────────────────────────┐
   │  pull --rebase → 同步内容到面板  │
   │  → push（若 auto_push）          │
   └──────────────────────────────────┘
```

### 6.3 关键命令序列

**首次克隆**

```
git clone --branch <branch> --single-branch <url> <workdir>
```

失败分类（要给用户看得懂的提示，不能只回传 stderr）：

| 现象 | 提示 |
| --- | --- |
| `Permission denied (publickey)` | 私钥与 GitHub 上的公钥不匹配 |
| `Permission to <repo>.git denied to deploy key` | 部署密钥是只读的，需在 GitHub 上勾 "Allow write access"（**已实测会遇到**） |
| `Repository not found` | 地址错，或部署密钥没加到这个仓库 |
| `Could not resolve hostname` | 容器出网问题 |

**拉取**（定时同步 / 推送前）

```
git fetch origin <branch>
git status --porcelain
# 有本地改动 → 先 commit（信息前缀「面板自动提交：」）
git pull --rebase origin <branch>
```

`pull --rebase` 失败且 `git diff --name-only --diff-filter=U` 非空 → 冲突态。

**提交与推送**

```
git add -A <白名单目录>
git commit -m "<message>"
git push origin <branch>
```

push 被拒（`non-fast-forward`）→ 自动 `pull --rebase` 后重试一次，仍失败按冲突处理。

**冲突三方内容**

```
git show :1:<path>    # 共同祖先 base
git show :2:<path>    # 本地 ours
git show :3:<path>    # 远端 theirs
```

**解决冲突**（手工编辑为主）

```
# 页面把三方内容 + 冲突标记写入工作树文件 → 用户编辑 → 校验无残留标记
git add <path>
git commit -m "解决冲突：<path>"
```

「整体用远端」「整体保留本地」是快捷按钮，等价于 `git checkout --theirs/--ours -- <path>` + `git add`，供"不打算手工合并"时快速收场。

### 6.4 并发

模块级 `threading.Lock` 串行化所有 Git 操作。定时同步与用户操作抢锁时：用户优先，定时同步跳过并记「已延后」；定时同步持锁时用户请求排队（前端显示等待）。

## 七、现状冲突与解法

| # | 冲突 | 解法 |
| --- | --- | --- |
| 1 | 主仓库有 submodule 引用 | 目标态删除 `.gitmodules` 与 `magic-sets/` 目录。主仓库**没有任何代码引用 magic-sets**（已实测：除 `.gitmodules` 外零引用），移除成本极低 |
| 2 | 规则来源 28 个指向 jsDelivr | 改成 `kind='repo'` + `repo_id` + `repo_path`。**客户端零影响**（`/res/rule/<name>` 只读 content）。切换后 jsDelivr 环节消失 |
| 3 | 改 jsDelivr 缓存那一大段文档与约定 | 目标态删除「改完必须换 commit 号 URL」的约定；`AGENTS.md` 约束 19 改写为"自维护层由依赖仓库托管" |
| 4 | 面板「功能模块」的内置预设与仓库 `script/rewrite/` 重复 | `src/snippetPresets.js` 的 `script-ua-apple` / `rewrite-ad-block` 等与仓库同名文件内容一致——又是「同一件事两份清单」。**仓库为准**：这批预设从 `snippetPresets.js` 移除，改为仓库托管，功能模块页只显示仓库来的那批 |
| 5 | 仓库托管来源的 `enabled` 被谁控制 | 仓库只管内容。`enabled` 仍归「规则来源」/「功能模块」页。同步**不覆盖** |
| 6 | 文件头 `behavior` 与面板 `behavior` 不一致 | **文件头是事实来源**：同步时以文件头为准纠正面板值，记审计 + 界面提示 |
| 7 | 规则内容变更不触发自动构建 | 现状 `collect_snapshot` 的 rule_providers 不含 content，policy_sha 不变。**本期修**：把 content 的 sha256 纳入快照，仓库同步后自然触发自动构建 |
| 8 | 可追溯性 | 原来 submodule pin 天然知道用的哪版规则。目标态在构建记录里写明**依赖仓库 commit**，产物与构建详情都可追溯 |
| 9 | 仓库新增文件是否自动建来源 | `rule/*.yaml` → **自动建**规则来源（`kind='repo'`、behavior 取自文件头、默认启用）；`script|rewrite/*.yaml` → **自动建**功能模块（默认停用，与文件头「默认停用」一致）。**不自动建规则**——规则仍在「分流规则」页手工挂，避免规则表被自动污染 |
| 10 | 仓库删除文件 | 若对应实体被引用（`refs.rules_targeting`）→ 拒绝删除并列出引用；无引用 → 删除实体与文件 |
| 11 | 换仓库地址 | 原仓库的实体按 `repo_path` 找不到对应文件 → 标记「源文件缺失」并停用（不自动删） |
| 12 | 仓库里 CRLF/LF 混用 | 仓库加 `.gitattributes`（`*.yaml text eol=lf`），否则每次 diff 都是全文件 |
| 13 | 仓库为空（无 commit） | 本地建分支首次提交，`git push -u origin <branch>` |
| 14 | 提交身份与钩子 | `user.name`/`user.email` 走 `repos` 表；`core.hooksPath=/dev/null` 防止仓库自带钩子干扰 |
| 15 | 二进制文件 | 只读展示 + 下载，不提供编辑；同步时跳过 |

## 八、数据安全与回滚

> 这是迁移阶段的第一优先级。原则：**任何时候都不丢数据，任何一步都能退回去。**

### 8.1 五条原则

1. **迁移全程不删除任何 `content`**：切换只是改 `kind`/`repo_id`/`repo_path`，内容原地保留
2. **原始配置留档**：切换前把每个实体的 `kind`/`url`/`repo_path`/`behavior`/`content_sha256`/`rule_count` 存档
3. **逐批核对**：一批核对通过才做下一批，不通过就停
4. **回退是一键操作**：不需要重建，只需还原存档字段
5. **Git 历史不丢**：冲突解决产生新 commit，不改写历史；不用 force push

### 8.2 切换前的准备

- 面板 DB 备份（已有 `magicpanel-backup` 容器，每日快照）
- 存档表：

```sql
CREATE TABLE IF NOT EXISTS repo_migrations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  repo_id INTEGER NOT NULL,
  batch INTEGER NOT NULL DEFAULT 1,
  object_type TEXT NOT NULL,     -- rule_provider / snippet
  object_id INTEGER NOT NULL,
  origin_kind TEXT NOT NULL,
  origin_url TEXT NOT NULL DEFAULT '',
  origin_repo_path TEXT NOT NULL DEFAULT '',
  origin_behavior TEXT NOT NULL DEFAULT '',
  origin_content_sha TEXT NOT NULL DEFAULT '',
  origin_rule_count INTEGER,
  switched_at TEXT NOT NULL,
  reverted_at TEXT
);
```

### 8.3 分批切换（28 个规则来源，4 批 × 7）

每批流程：

1. **批前快照**：把该批 7 个来源的原始字段写入 `repo_migrations`
2. **切换**：`kind='repo'`、`repo_id=<id>`、`repo_path='rule/<name>.yaml'`
3. **同步**：从仓库读文件覆盖 content（若内容有差异，保留原值直到核对通过）
4. **核对清单**（逐项比对，任何一项不过就不进入下一批）：

| 核对项 | 判据 |
| --- | --- |
| 来源名一致 | 仓库文件名去扩展名 == 规则来源名 |
| behavior 一致 | 面板 behavior == 文件头 `# behavior:` |
| 内容一致 | 面板 content 的 sha256 == 仓库文件 sha256 |
| 条目数一致 | 面板 rule_count == 文件头 `# 条目:` == 实际 payload 条数 |
| 分发路径不变 | 产物里该 rule-provider 的 url 仍为 `{FEED}/res/rule/<name>` |
| 产物一致 | 切换前后对同一策略快照构建，产物 rule-providers 段字节一致 |

5. **回退**：核对不过 → 用 `repo_migrations` 还原该批（恢复 `kind`/`url`，`repo_id`/`repo_path` 清空），不进入下一批

### 8.4 功能模块的切换

`script/` 3 个 + `rewrite/` 3 个文件对应的 snippet，同法处理；`src/snippetPresets.js` 里那批重复的内置预设在切完后移除（属于代码改动，随第 2 步一起提交）。

### 8.5 移除 submodule

随第 2 步合并为一个提交。要点：

- 删 `.gitmodules` 与 `magic-sets/` 目录
- **magic-sets 仓库必须保持可访问**（公开或至少部署密钥有读权限），否则规则无从获取
- 若担心仓库被误删，迁移前在面板侧做一次「内容快照」留档：`repo_migrations` 已存 sha256，但**内容本体**建议另存一份到 `data/backup/`（面板已有备份机制）

### 8.6 仓库历史

Git 自身保证。面板不做 `reset --hard` / `push --force` / `filter-branch`；只做 `fetch`/`pull --rebase`/`commit`/`push`。误操作要回退时用「回滚到指定提交」（生成一个 revert 提交，不改写历史）。

## 九、同步与构建联动

### 9.1 同步流程（定时 12 小时 / 手动立即同步）

```
取锁 → git fetch → 判断工作区状态
  ├─ 干净 → pull --rebase
  ├─ 有本地改动 → 提交（信息前缀「面板自动提交：」）→ pull --rebase
  └─ 冲突 → 记录冲突列表，停在冲突态，同步结束（不推）
  ↓
遍历仓库文件（排除清单内的路径跳过）：
  rule/*.yaml    → 校验 → 找/建规则来源 → 覆盖 content
  script|rewrite/*.yaml → 校验 → 找/建 snippet → 覆盖 content
  其它文件 → 不消费，只更新文件树状态
  ↓
写 last_sync_at / last_commit
```

同步**只 pull 不 push**（D7）。冲突解决后需要用户显式触发一次推送。

### 9.2 内容 → 构建

`collect_snapshot` 的 rule_providers 项增加 `"content_sha": sha256(content)`。内容变了 → policy_sha 变 → 定时自动构建照常触发。

同步完成后把 `last_commit` 写进构建 note，让构建详情能回答"这次构建用的是哪版依赖"。

### 9.3 与「规则来源」「功能模块」页的关系

- 两个页仍列出全部实体（含仓库托管的），URL 列显示仓库路径而不是 URL
- 仓库托管的实体，「抓取」按钮改为「从仓库同步」（只更新该一个文件内容，不做 Git 操作）
- 启用/停用仍在这两页做
- 功能模块页改 content → 写回仓库文件（走依赖管理页的保存逻辑），但**不自动提交**，由用户在依赖管理页统一提交

### 11.3 冲突解决视图

顶部插入醒目冲突条，点开进入三方对照：

```
┌────────────────┬────────────────┬────────────────┐
│ 共同祖先 base  │ 本地 ours      │ 远端 theirs    │
├────────────────┼────────────────┼────────────────┤
│ ...            │ ...            │ ...            │
└────────────────┴────────────────┴────────────────┘
   [手工合并（主）]  [整体用远端]  [整体保留本地]
```

「手工合并」进编辑器，初始内容带 Git 冲突标记，保存时校验无 `<<<<<<<`/`=======`/`>>>>>>>` 残留，否则拒绝提交并高亮残留行。

### 11.4 仓库设置抽屉

### 11.5 首次配置引导

未配置时显示引导卡片：填地址 → 生成密钥对 → 显示公钥（复制按钮 + 提示贴到**该依赖仓库**的 Settings → Deploy keys，并**勾上 Allow write access**）→ 填私钥 → 保存 → 克隆。

> 部署密钥必须加在**被管理的那个仓库**上（当前是 `astralwaveorg/magic-sets`），不是 MagicPanel 仓库。
> 多仓库场景下每个仓库各配各的密钥，页面按仓库分别引导。

## 十二、部署与凭据

### 12.1 镜像

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \
        git openssh-client ca-certificates \
    && rm -rf /var/lib/apt/lists/*
```

镜像增大约 60 MB。`openssh-client` 提供 `ssh-keygen`（生成密钥对）与 `ssh`（SSH 传输）。

### 12.2 凭据

| 凭据 | 存放 | 保护 |
| --- | --- | --- |
| SSH 私钥 | `repos.private_key_enc`（Fernet） | 用时写临时文件 600 权限，用完删；接口不回显 |
| HTTPS Token | `repos.token_enc` | 同上；`security.mask_url` 脱敏 |
| 提交身份 | `repos` 表明文 | 非敏感 |

面板的 `data/secret.key`（Fernet 主密钥）已有备份机制（`magicpanel-backup` 容器 + WebDAV），私钥随之可恢复。

### 12.3 部署时的自动拉取

- 容器启动后，若仓库已启用且工作树不存在 → 后台自动 clone（失败不阻塞服务启动，记 `last_error`）
- 工作树已存在 → 不动，等定时同步或用户手动操作
- 新增的同步任务挂在现有 scheduler 循环里（`server/app/services/scheduler.py`：30 秒 tick，读 repos 表决定到期）

### 12.4 本机初始密钥对（2026-10-25 生成）

| 项 | 路径 / 值 |
| --- | --- |
| 私钥 | `~/.ssh/magicpanel-rules-repo`（权限 600，不入库） |
| 公钥 | `~/.ssh/magicpanel-rules-repo.pub` |
| 指纹 | `SHA256:7VNazP5gLZ2gHGkaDJ66JSYs5eox+2gFX/Tt4/iD5zQ` |
| 已加在 | `astralwaveorg/magic-sets` 仓库的 Deploy keys（**只读**，待勾 Allow write access） |
| 已验证 | clone 成功；`git push --dry-run` 报 `denied to deploy key`（只读密钥的典型表现） |

实施时把私钥内容写入 `repos.private_key_enc`（Fernet 加密），本机这份留作备份。

## 十三、特殊场景清单

| 场景 | 处理 |
| --- | --- |
| 首次配置，目录为空 | 引导流程：填地址 → 配密钥 → clone |
| 公钥没贴到 GitHub | clone 报 `Permission denied (publickey)`，页面给可执行提示 |
| **部署密钥是只读的** | push 报 `denied to deploy key`，页面提示"需在 GitHub 勾 Allow write access"（**已实测会遇到**） |
| 仓库地址错 | `Repository not found`，提示检查地址与密钥所属仓库 |
| 容器出网不通 | `Could not resolve host`，提示检查网络 |
| 远端更新 + 本地干净 | fast-forward，无冲突 |
| 远端更新 + 本地有改动 | 先自动 commit 再 pull --rebase，成功则 push |
| 同一文件两边都改 | 冲突 → 手工编辑为主，三方对照 + 两个快捷按钮 |
| push 被拒（非 fast-forward） | 自动 pull --rebase 重试一次，仍失败转冲突 |
| 本地有未提交改动时点同步 | 自动 commit（带「面板自动提交：」前缀）后继续 |
| 定时同步撞上用户编辑 | 锁串行；编辑期间定时同步延后并在状态条提示 |
| 二进制文件 | 只读展示 + 下载，不提供编辑 |
| 文件名含空格/中文 | 允许，URL 编码要正确 |
| 路径穿越 / 符号链接 / 绝对路径 | 白名单校验拒绝 |
| 非 UTF-8 文件 | 拒绝并提示编码问题 |
| 单文件超 2 MB | 拒绝 |
| CRLF/LF 混用 | 仓库 `.gitattributes` 统一 |
| 面板重启 / 崩溃 | 工作树与冲突中间态在持久卷，可恢复 |
| 换仓库地址 | 原实体标记「源文件缺失」并停用，不自动删 |
| 仓库被删除/改名 | 同上，页面明确提示 |
| 定时同步失败 | 记 `automation_runs` + 审计，状态条显示失败原因，不刷屏 |
| 误操作要回滚 | 提交历史页可看 diff，支持生成 revert 提交（不改写历史） |
| 私钥写错 | 设置页重新填；旧私钥从 DB 覆盖 |

## 十五、风险与取舍

| 风险 | 应对 |
| --- | --- |
| 镜像 +60 MB（装 git） | 可接受；若不接受，退到 dulwich，冲突处理降级为"提示后人工下载 diff 合并" |
| 自动 push 是对外可见变更 | 提交前预览 diff + 明确显示目标仓库地址 + 二次确认；定时任务不 push |
| 部署密钥只读导致 push 失败 | 已在实测中发现；引导页必须写明要勾 Allow write access |
| 私钥落 DB | Fernet 加密 + 只写不读 + 临时文件用完删；与设备令牌同等级保护 |
| 依赖仓库成为单点 | 仓库不可用时，实体表里已有 content 仍可继续构建分发（**不阻断**）；迁移存档里还留有 content sha256 |
| 自动提交产生噪音提交 | 只在冲突态或同步前有本地改动时提交，提交信息统一前缀可识别 |
| 面板「功能模块」与仓库内容双向写 | content 单一事实来源是仓库；功能模块页改 content 写回仓库文件但不自动提交，提交统一在依赖管理页做 |
| 行级自动合并未实现 | 手工编辑为主路径 + 两个整文件快捷按钮，覆盖绝大多数场景 |
