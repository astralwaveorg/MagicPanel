# Mac mini 按需局域网代理方案

更新／检查日期：2026-10-19。状态：**方案已优化，尚未执行迁移。Surge 当前正常提供服务，用户确认 NAS 已使用 Mac mini 的代理；必须保持现有服务连续性。**

## 必须满足的要求

1. R6S `10.0.1.1` 继续提供默认网关、DHCP 和基础 DNS，不启用代理，不为本方案修改路由／DNS 或增加 WAN 映射。
2. Mac mini `10.0.1.8` 提供显式 LAN 代理。设备或应用只有主动填写它的代理地址时才使用服务。
3. 不启用全网透明代理，不把任意设备的默认网关／基础 DNS 改为 Mac mini；共享服务首期也不需要 TUN。
4. Mac mini／NAS 停机或代理节点失效，不应影响未启用代理的设备。已启用手动代理的应用可能失败，关闭该代理即可恢复原有直连路径，不能承诺自动回退。
5. 在家共享规则由 Mac mini 执行；外出使用本机客户端，同一份策略来源生成配置。不在 NAS 上设置全局代理环境来替代按应用选择。

```text
普通上网：设备 ─────────────────→ R6S → 互联网
按需代理：设备／应用 → Mac mini → R6S → 机场或直连目标
基础 DNS：设备 ─────────────────→ R6S
```

设备的普通 DNS 设置不改；代理服务为其出站解析节点和目标域名，不等于给全家提供 DNS。哪些域名在客户端解析、哪些交给代理解析，取决于应用和协议，应分别验证。

## 已选服务方式：Stash Mac

用户已购买 Mac 授权，明确 Windows + 两台 Mac 使用 Stash。Mac mini 目标为 **Stash Mac 显式 LAN HTTP／SOCKS**；MacBook 已完成后续授权的清理并保留 Stash；mini 的 Surge 运行现状未变。旧的独立 Mihomo／LaunchDaemon 路线降为后备，不作为本次主方案执行。

官方明确 Stash Mac 支持 LAN HTTP／SOCKS，默认 7890，需允许局域网连接；这与网关模式是两种接入方式。这里只选显式代理，不接管家庭网关或 DNS。[LAN 官方说明](https://stash.wiki/features/provide-proxy-to-lan-device)

Stash Mac 文档注明开机启动，但未证明本机未登录就能恢复代理。上线前验证无屏重启、登录会话依赖、睡眠、授权／订阅失败和端口兼容。Helper 不代表完整核心已具备无人登录服务能力。不得自行开启自动登录解决，验收失败保留 Surge。[Mac 说明](https://stash.wiki/stash-mac) · [Helper 说明](https://stash.wiki/faq/stash-mac-helper)

Apple 区分系统 daemon 与登录用户 agent；图形应用的登录启动不能替代“未登录即可恢复服务”的验收。采用 LaunchDaemon 也不会天然保证网络就绪、配置有效或代理可用。[Apple launchd 文档](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)

## 设备手动接入与退出

现有 NAS 继续保留当前有效设置。以下接入卡片需在目标服务验收后使用：地址为 `10.0.1.8`，HTTP 端口优先兼容现有 `6152`，SOCKS 消费者优先兼容 `6153`，最终以实际协议核对为准。`7890` 不是必须迁移到的新端口；它是 MacBook 当前本机端口，也是 Stash 文档的默认值，目标入口须另行验证。不要把客户端的 `127.0.0.1` 当作 Mac mini 地址，也不要填订阅 URL。

| 平台 | 接入方式 | 恢复原有直连 |
| --- | --- | --- |
| iPhone | 设置 → Wi-Fi → 当前网络的信息按钮 → 配置代理 → 手动，填地址、端口；按服务策略填写认证 | 配置代理 → 关闭；不改配置 IP／DNS |
| 小米 Android | 当前 Wi-Fi 详情／修改网络中的代理 → 手动，填主机和端口；HyperOS 4 具体标签与鉴权支持需实机确认 | 代理 → 无／不使用；不改静态 IP／网关 |
| MacBook | 系统设置 → 网络 → Wi-Fi → 详细信息 → 代理，HTTP 与 HTTPS 均使用该地址和端口 | 恢复先前的代理设置；本机已运行 Stash，测试前先记录当前值 |
| Windows | 设置 → 网络和 Internet → 代理 → 手动设置代理；不承诺只作用于一个 Wi-Fi，需按实际 Windows 版本核对 | 关闭手动代理，或恢复先前本机客户端设置 |
| NAS／命令行应用 | 仅给需要的应用、进程或容器单独配置代理，保留 LAN／管理目标绕过 | 移除该应用代理；不全局改宿主机 DNS／网关 |
| Apple TV | 不预设 tvOS 提供同样的手动代理入口；优先使用独立 Stash tvOS | 关闭客户端，并验证网络恢复 |

Apple 官方确认 iPhone 可按所连 Wi-Fi 修改 HTTP Proxy，Mac 可分别配置 HTTP／HTTPS／SOCKS 和绕过目标。[iPhone 网络设置](https://support.apple.com/guide/iphone/manage-wi-fi-settings-iphw5gjwl8k2/27/ios/27) · [Mac 代理设置](https://support.apple.com/en-gb/guide/mac-help/mchlp2591/mac)

Android 提供 HTTP 代理描述，但不能保证每个应用遵从系统代理；Google 也说明网络设置因设备／Android 版本而异。HTTP 代理不是全流量 VPN，不能承诺任意 UDP 游戏、QUIC、ICMP 或所有后台应用覆盖。优先用浏览器验证；不遵从的应用需要自身代理支持或独立客户端。[Android ProxyInfo](https://developer.android.com/reference/android/net/ProxyInfo) · [Google 网络设置](https://support.google.com/pixelphone/answer/9655181)

HTTP 代理不意味着要解密 HTTPS；首期不安装 MITM 根证书，不做 HTTPS 解密。代理认证与 HTTP／SOCKS 接入本身的链路加密也不是同一概念，不能将账号密码认证当成 TLS。

## 深度优化：固定入口、独立故障边界

### 端口保持稳定，内核可以替换

NAS 已经依赖 Mac mini，因此长期入口应稳定，避免为了统一默认端口让每个容器／应用改配置。先核实 HTTP／SOCKS 的真实协议及鉴权，然后让目标 Mihomo 兼容现有入口；mixed 支持 HTTP 和 SOCKS，不代表必须新增一个端口。

Surge 与 Mihomo 不能同时占用同一地址端口。可以在未占用的临时端口准备候选服务，但 **Surge 的虚拟路由仍可能影响候选出站**，这种测试不能证明已经形成独立直连出口。候选端口验证、正式出口验证和生产端口切换要分开记录。不新增常驻转发层来掩盖端口冲突。

### 三种用户操作模式

| 模式 | 入口 | 用途／退出方式 |
| --- | --- | --- |
| 普通直连 | 无手动代理，原有网关与 DNS | 默认状态，完全不依赖共享代理进程 |
| 家庭共享 | 10.0.1.8 的稳定 HTTP／SOCKS 端口 | 手动开启；共享服务故障时关闭它，不自动转向 NAS |
| 独立客户端 | MacBook Stash 4.4.0 已运行；移动端各自客户端 | 外出或需要更完整覆盖；先关闭共享代理，避免双层路径 |

macOS Wi-Fi 网络服务代理、Windows 系统代理不能未经实测就当成只绑定一个 SSID；离开家后可能保留 10.0.1.8 设置。首期提供明确开关与恢复记录，不引入自动 WPAD／PAC 或依赖家庭在线的切换脚本。后续自动化必须可手动撤销，并验证 Wi-Fi／蜂窝、休眠和不同网络切换。

### DNS 与本地业务

终端基础 DNS 保持原设置；共享核心为自身出站做域名解析，不发布 LAN DNS。通过 HTTP CONNECT 提交域名与应用自行解析 IP 的行为不同，不保证全部 DNS 都经过代理。首期不用面向全家的 Fake-IP，也不启用 MITM／TLS 解密或为此安装根证书。

本地路由、NAS、管理地址和内部域名优先在支持的应用中绕过代理；服务端也保持本地目标直连规则。但后者仍依赖核心在线，不能代替客户端绕过与“关闭手动代理”。IPv4 LAN、IPv6 本地／直连行为分别验证，不为规避问题全局关闭 IPv6。

### 容量与运行方式

Mac mini 千兆有线足以作为当前带宽下的候选共享服务，但 NAS／多设备共享同一 NIC，不能由 M4 性能推导所有并发代理都能跑满千兆。保持 NAS BT、保种、局域网拷贝直连；镜像、元数据和确需代理的业务按应用选择。

主方案由 Stash Mac 自身及官方 Helper 管理；不额外用 Homebrew／独立 LaunchDaemon 再启动一份核心。验证登录前后可用性、日志／缓存、网络未就绪恢复；不通过定时重启掩盖故障。若不能满足无屏恢复要求，保留 Surge 并报告，独立 Mihomo 后备须重新决定后再执行。

## NAS 消费者必须按层登记

用户确认 NAS 使用 Mac mini，这是当前事实；尚未确认的是具体消费层和端口，不能从 SSH 登录环境为空否定它。

| 层面 | 检查对象 | 迁移边界 |
| --- | --- | --- |
| 宿主机应用 | 飞牛应用、下载器、元数据服务自身代理设置 | 仅调整已登记且需要的应用，不把所有 NAS 流量强制代理 |
| Docker daemon | 镜像拉取的 daemon 代理 | 不等于容器内业务代理；若修改需重启 daemon，单独评估容器影响，不顺手执行 |
| 容器／Compose | 单个服务的环境、应用设置、构建参数 | 只更新受影响服务；不因为换代理批量重建所有容器 |
| shell／任务 | 用户环境、计划任务、一次性命令 | 环境变量有作用域，SSH shell 的结果不代表其他上下文 |

登记表只保存服务名、HTTP／SOCKS 类型、脱敏端点、配置位置、是否需要重启、验证与恢复方法，不存密码。保留本地地址／内部域名的绕过；`NO_PROXY` 的通配符和 CIDR 支持因程序而异，不盲目复制一份就宣称全部生效。HTTPS 目标经 HTTP 代理时，代理端点仍可能是 `http://...`，不能只因变量名为 HTTPS_PROXY 就擅改协议。

Docker 官方分别描述 daemon 与容器／构建代理，必须区分作用域。[Daemon 代理](https://docs.docker.com/engine/daemon/proxy/) · [容器与构建代理](https://docs.docker.com/engine/cli/proxy/)

## 规则与发布：一份来源，少量目标

- 共享服务与独立客户端共用业务规则、节点来源和策略命名；仅 DNS、入站、TUN、平台权限等差异由小模板处理。不构建多层订阅转换服务来增加依赖。
- 先整理现有仓库规则与个人例外，保留匹配顺序；业务分组以通用代理、稳定地区、媒体／AI、直连和个人例外为主，确有需求再细分。
- 默认固定地区偏好并故障切换，避免频繁追逐最低延迟；健康探测成功不等于媒体解锁或 AI 服务可用，按实际业务验收。
- 生成配置与规则资源带版本标识，校验后先在单端试用，再提升稳定入口。更新失败保留最后有效配置／缓存，不能把空列表或缺失 provider 当作有效发布。
- 节点订阅和规则更新使用各自刷新机制；完整配置更新还需明确 reload 行为。手动选择状态保存在各端，不承诺自动跨端同步。
- 节点秘密与公共规则分离；外出配置从可独立访问的 HTTPS 端点更新。发布端离线时已缓存设备可继续用；不把发布任务或健康检查放到 R6S。
- 云端开发见[工作台规格](../development/Remote-Config-Console.md)。生产管理放独立云端，不依赖 Stash 跨设备同步；先验证各 Stash 目标与 Android Mihomo 输出，当前没有实现生成平台。

## 访问控制与故障策略

代理只绑定目标 LAN 地址并限制来源，不增加 WAN 映射，不默认监听全部 IPv6 地址；管理接口只在本机或 SSH 隧道访问。现有局域网与访客／IoT 是否隔离尚未证实，来源为 10.0.1.0/24 不能直接等同于身份认证。

鉴权应与 iOS、HyperOS 和 NAS 各应用兼容：没有通用认证能力的应用可用独立客户端，或在确认可信范围后设计受限入口，不擅自把全网段都列为免认证。HTTP／SOCKS 账号密码本身不提供接入链路加密；不通过扩大监听范围解决认证问题。

| 故障 | 应有结果 | 用户恢复方式 |
| --- | --- | --- |
| 某个机场节点失效 | 策略切换到已配置、验证过的备用节点 | 节点均失败时，对要求代理的请求明确报错，不悄悄 DIRECT |
| Mac mini 核心或主机停止 | 未选共享代理的设备与本地网络不受影响；共享代理请求可能失败 | 关闭手动代理恢复普通直连，或切到独立客户端 |
| NAS 维护 | 手机、笔记本和 Mac mini 代理继续运行 | NAS 自身任务按维护计划恢复 |
| 发布端或资源更新失败 | 已运行服务保留有效版本 | 等待恢复或人工回滚，不重启整网 |
| R6S／宽带／家庭电源故障 | 不属于代理服务可屏蔽的故障 | 另评估基础设施恢复；手机可用蜂窝独立客户端 |

节点回退、核心重启、配置回滚和终端恢复直连是四种不同机制，不能互相替代。

## 迁移与验收顺序

所有步骤仍为计划。当前 Surge 正常工作，NAS 已依赖它；仅获授权查看不表示可以开始切换。

1. **登记与备份**：核实 NAS 每层消费者、现有协议／端口／鉴权、Surge 接管范围与恢复方式；保留原配置和路由记录，不在仓库保存秘密。
2. **准备候选**：选定 Stash Mac 版本，按官方文档及 App 检查配置、规则与节点；在独立临时端口准备候选时明确原 Surge 路由仍可能参与，不能以连通性成功代替出口隔离验证。
3. **单端试用**：用一个可随时恢复的应用验证规则、HTTPS、LAN 绕过、鉴权和出口。候选失败不改生产入口，不重启 NAS／Docker。
4. **约定代理维护窗口**：在明确授权后停止 Surge 接管，确认 Mac mini 的基础路由／SSH／直连恢复；启动目标服务并复用已核实的稳定端口。断开现有 TCP 连接不可完全避免，不承诺无缝切换。
5. **生产消费者验收**：NAS 按登记逐项检查，优先不改端点；只在必须时调整单个服务。不进行无关固件、安全整改或全容器重启。
6. **失败回退**：目标服务未启动、端口冲突、出口／规则错误或 NAS 关键任务失败时，停止候选，恢复 Surge 原配置与接管状态，复核 NAS 和本机。不能让两个核心争用入口后继续尝试。
7. **故障隔离验收**：安排核心停止、节点全部失败、资源下载失败、Mac mini 重启／空闲等测试；逐项证明普通网络不受影响，以及测试端关闭手动代理可恢复直连。
8. **记录上线**：通过后更新运行上下文、端口卡片和版本记录；旧安装先保持可回退，不立即卸载。至少跨越一次完整重启与空闲运行验收后再考虑清理。

最小上线条件：稳定端口可用、NAS 关键消费者通过、直连设备未受影响、IPv4／IPv6 行为符合预期、无屏恢复可用、规则来源可追踪、故障能恢复原服务。任一项缺证据，就记录未通过，不以一次 TCP 握手宣布迁移完成。

mini／NAS／R6S 只做文档与先前有限检查，未迁移或停用 mini Surge；MacBook 的独立授权清理见卸载记录，不扩展为远端实施许可。
