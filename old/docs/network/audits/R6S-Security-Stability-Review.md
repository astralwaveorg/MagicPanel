## 总体判断

R6S 当前基础路由、DNS 和防火墙在工作，资源充足；本次短时观察未发现 OOM、内核崩溃或链路硬件错误。**不能据此认定整体配置已经安全、长期稳定或没有入侵。** 优先审阅项是 NAS 管理服务的 WAN 转发、HTTP 管理入口和固件维护状态，而不是路由性能不足。

## F02：路由管理入口

### 已有的保护

- Dropbear 绑定 LAN，TCP 22；`PasswordAuth=off`、`RootPasswordAuth=off`。本次通过已有密钥成功登录。
- root 密码字段非空，但未读取或评估密码强度。
- 6 条授权密钥均为 Ed25519；`authorized_keys`、`/etc/shadow`、network／dropbear 配置权限为 600。
- 已加载 nftables：input 默认 drop，WAN 未匹配流量走 reject；只见 LAN → WAN 的区域转发。IPv6 也经过 fw4，未见通用的 WAN → LAN 全放行。

### 需要改善的部分

uHTTPd 监听 `0.0.0.0:80` 与 `[::]:80`；无 `listen_https`，`redirect_https=0`。证书路径存在于配置中，**不代表 HTTPS 已启用**。HTTP 缺少传输加密，局域网不可信设备或被控制的终端也需要考虑。

ttyd 监听 LAN 地址 TCP 7681，配置命令为 `/bin/login`，未配置独立 credential 或 TLS。**没有 credential 不等于免密 root 终端**，因为仍有系统 login；但直接使用该 HTTP／WebSocket 入口缺少传输加密。SSH 的禁用密码设置不能推导 ttyd 的 login 也禁止密码。

DDNS-Go 监听所有地址 TCP 29876，WAN 默认拒绝且相应映射已禁用。目前未验证 DDNS-Go 自身密码与“禁止公网访问”选项，也未读取 DNS 服务商密钥。后续可核对绑定范围和应用访问控制，不把全地址监听直接当成公网可达。官方默认提供公网访问限制，并建议需要公网访问时使用 HTTPS 反向代理。[DDNS-Go 官方说明](https://github.com/jeessy2/ddns-go)

本地未登录访问 LuCI 路径返回 403，根路径返回 200；这不能单独判定故障或安全，未进行浏览器认证登录。HTTPS／隧道建议依据[OpenWrt 安全访问文档](https://openwrt.org/docs/guide-user/security/secure.access)与 [ttyd TLS 文档](https://github.com/tsl0922/ttyd/wiki/SSL-Usage)，本次没有应用变更。

## 代理与基础网络隔离的设计要求

用户的“代理不可用也不能影响整体家庭网络”应具体定义为：**基础直连、DHCP、普通 DNS、LAN 通信不依赖代理服务**。必须代理的目标仍可能不可达，这与全家基础断网不同。

推荐手机、电脑、Apple TV 使用各自客户端；Mac mini 提供可选的 LAN HTTP／SOCKS 代理。最新方案将配置管理／发布移至独立云端，客户端选择与已购买授权以[总体设计](../Home-Proxy-Architecture.md)为准。R6S 继续作为默认网关／基础 DNS，不接管代理，也不通过 DHCP 把全家引向 Mac mini。显式代理只覆盖实际支持并配置了它的应用，不保证任意 UDP／ICMP 或所有智能设备透明代理。

用户后续已进一步明确：设备仅手动选择 Mac mini 显式代理，不采用单设备或全家的 Mac mini 网关模式。需要更完整覆盖时使用设备独立客户端；填写两个 DNS 不等于可靠的主备切换。当前 NAS 已使用 mini 的正常 Surge 服务，迁移应先登记消费者，不能因为登录 shell 没有代理变量就认定不存在代理使用。
