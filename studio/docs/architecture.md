# 架构、数据与无人值守

## 选型

新前端采用浏览器 ES modules、语义化 HTML 与响应式 CSS，以同源 JSON API 交换数据。对这个单管理员工具，不需要把组件库、SSR 服务和前端包管理加入部署链。后端保留成熟的 FastAPI、SQLite WAL 和 PyYAML 依赖，重新设计领域与 API，不挂载旧后台、不复用旧数据库做运行存储。与 PostgreSQL/Redis + 多进程相比，单进程内网 NAS 部署的快照、原子事务与恢复更容易验证。密钥和压缩后加密的业务数据分开管理；对大资源按内容摘要去重。

## 数据合同

工作区是可编辑草稿，有整数版本。目标模板持有配置底稿、稳定规则 ID 的有序引用、资源引用；同一规则只有一份定义。设备绑定模板，旧设备若有实质差异则保留显式差异或独立模板，而不静默摊平。运行时不从旧服务器拉订阅。发布事务同时固定模板、规则、设备配置与依赖资源，设备只获取完整的某一版本。发布号进入资源路径；即使同时发布或回滚，已经被客户端下载的配置仍可以拉取当时的资源。认证/撤销单独生效。写入须检查草稿版本，服务端规定可操作字段，禁止把客户端提交的未知键直接更新数据库。

## 引擎与转换器

Mihomo 与 Stash 的节点（如 Hy2 密码）、集合鉴权头、测速、规则标志和 DNS 存在差异；以已发布目标配置为迁移基准，新增节点按目标适配。转换器独立运行在 Docker 网络，仅用于明确的输入转换，不接管最终模板；不能把 Stash 的完整响应当成只含节点的文件。禁止自动把真实订阅交给公共服务。引入公开模板时须能预览和固定版本；远程资源不可用时保留上一份成功数据。

## 迁移、密钥与模型

用 SQLite 在线备份读出一致副本，复制当前发布产物；在只读部署材料上提取目标、设备差异、管理员 verifier、可用节点与规则资源，签发 v2 新 token，不继承 v1 会话。验证数量、引用和主要顺序，再首次发布。既有凭据仅在本地解密并用 v2 主密钥重新封装；不入 Git。新系统不给旧系统挂载读写目录。

MiniMax 使用用户指定的 MiniMax-M3.1-Flash 与官方兼容端点。Key 仅进后端 secret；模型无 shell、SSH、网络抓取、改库工具。节点链接及其中的密码、认证头在本地解析；模型处理脱敏意图、可见的组名称与规则摘要。输出须通过类型约束、当前版本和业务校验，再由用户选择应用到草稿。模型未响应，页面仍能完成手动编辑与发布。自然语言助手不代替定时任务或配置门禁。

## 安全与可恢复性

HTTPS 域名限制、仅回环映射服务端口、独立 cookie（HttpOnly、SameSite、Secure）、同源写请求、登录限速；订阅只接受高熵设备令牌。代理日志不落完整 feed 路径。自动任务在单实例运行，版本不变时跳过，失败带退避和原因；服务重启继续检查持久状态。备份必须同时保留一致数据库和主密钥。更换镜像或回滚发布时保持二者匹配，回退 v2 不碰 v1。
