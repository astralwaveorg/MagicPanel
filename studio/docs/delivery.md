# 开发验证、安装与发布

Studio 的源码、容器与持久状态应独立于仓库中的旧应用。部署脚本是面向维护环境的工具，运行前必须检查 `studio/ops/deploy.sh` 与 Compose 配置中的宿主、账号、路径、端口和镜像来源，按目标机器适配。不要直接使用脚本中的维护环境默认值。

## 本地验证

从仓库根目录运行：

```sh
python -m pytest -q studio/tests
```

在 `studio/client/` 按 `package.json` 和 `.github/workflows/studio.yml` 执行类型检查、链接测试与构建。后端测试覆盖认证、草稿并发、跨平台输出、版本资源与回退；客户端链接测试应解析外层 Scheme 并实际下载内层订阅。移动端和桌面端的浏览器验证需要覆盖登录、复制、弹窗、键盘和空列表。

Mihomo 核心检查、转换字段检查与原生客户端真实导入分别记录，不能互相替代。认证验证可用无外网容器中的两端 Mihomo、临时证书与随机口令，检查正确口令能读取随机响应、错误口令不能读取。`studio.check_hy2_auth` 用于部署前的 Hy2 认证检查。

## 全新安装

全新安装不需要旧数据库、旧密钥或历史记录。先准备 Docker Compose、独立持久目录、HTTPS 入口，以及经过验证的 Mihomo 核心和地理数据。路径约定、初始化参数和挂载以 `ops/deploy.sh`、`compose.yaml`、`init.py` 为准。

首次初始化用 `python -m studio.init --admin admin` 从标准输入读取密码，创建管理员、五份平台模板、四个线路方案和初始配置。部署脚本在空数据库场景生成受权限保护的一次性初始密码；已有库不应覆盖或重建。初始模板仅 DIRECT，导入节点与规则并发布后再交付。忘记密码应在有主机权限的维护环境中离线处理，不开放公网注册。

仅在需要复用配置时使用一次性导入器：从一致副本读取模板、规则、节点和资源，签发新的订阅密钥，不继承登录会话与旧设备令牌。凭据在本地解密后用新主密钥封装；临时副本在验证后删除。新应用不给旧系统挂载读写目录。

## 发布

脚本要求当前分支为 `v2`、`studio/` 没有未提交变更、HEAD 与远端 `v2` 相同；只归档该提交中的 `studio/`。准备并核对目标环境后，更新应用服务使用：

```sh
STUDIO_DEPLOY_SCOPE=studio bash studio/ops/deploy.sh
```

`STUDIO_NAS` 可指定部署宿主。脚本的默认范围为整个栈；只更新 Studio 时显式使用上述范围。部署应先检查 Compose、构建镜像、通过认证测试，再切换服务。应用只映射回环地址，转换器留在 Compose 网络；HTTPS 入口由维护者配置。

部署后检查当前发布目录、镜像 revision、容器健康、认证、配置及其版本化资源，并确认旧应用不受影响。记录提交、检查结果和未验证边界；真实地址、主机信息与现场回执保存在本地维护材料中。

## 回滚与恢复

规则错误可切回已验证的发布版本；程序错误使用上一镜像与匹配的数据快照。首次安装失败时只撤回新应用入口和容器。备份同时保留一致数据库与主密钥，在隔离目录验证 SQLite、解密和资源摘要后再用于恢复。失败任务保留上一份成功数据；无效候选不能移动生效指针。

规则产物升级使用 `studio.promote_rules`，先核对生效版本与草稿，再传预期版本、修订号。工具在同一事务中检查基础配置不变、已有客户端未失效，并保留上一发布以供恢复。
