# 开发顺序与发布合同

1. **基线**：记录旧站镜像、容器启动时间、设备/模板/资源数量和当前发布；检测 v2 DNS、端口与证书覆盖。确认新目录、容器名、数据库、令牌、域名与旧版独立。
2. **数据与编译**：先实现一致性导入、加密工作区、引用管理、单设备生成与不可变资源。用代表设备覆盖 Mihomo、Stash 与设备例外，比较规则首尾、顺序、策略组成员和资源内容。无效候选永不移动生效指针。
3. **服务与 UI**：实现登录、模板/节点/规则/设备管理、构建预览、发布与回滚，并加入自然语言提案。先完成一条可操作的维护流程，再覆盖移动窄屏与键盘操作。
4. **自动流程**：按持久配置刷新、编译、校验、发布；幂等运行，失败保留旧产物。备份与保留策略在独立目录执行，不操作旧数据。验证恢复到隔离目录而不是回写旧库。
5. **最短验收**：集中跑一个测试集覆盖变更和权限、两种引擎、回滚与资源，必要时用部署版本的 Mihomo 做核心校验。移动/桌面各走一次真实界面，模型用无秘密样例实调一次。跳过项记录影响，不以语法通过冒充真实设备行为。
6. **发布**：仅从 v2 提交归档部署到独立 Compose 项目。先在回环地址初始化并验证；再创建 v2 独立 OpenResty 站点，验证证书域名、配置检查后平滑加载。公开入口核对认证、设备配置及版本化引用资源；重复核验旧站未重启且域名仍可用。旧的 deploy.sh 不用于 v2。
7. **回退**：业务规则错误移动 v2 生效指针到旧版本；程序错误以之前已验证镜像与配套快照恢复。首次上线失败只撤新版站点/容器。健康、构建与助手分别记录结果；无真实客户端回执时不宣称已在该设备验证。

上线记录须列出代码修订、数据基线、实际部署路径、域名回执、使用入口与未验证边界；状态依实际执行填写。

### 全新安装与可选配置导入

全新安装不需要旧数据库、旧密钥、旧应用镜像或历史记录。在 NAS 为 v2 独立目录准备已验证的核心包（core/mihomo、geoip.dat、geosite.dat、country.mmdb），然后从已推送的 v2 分支运行 studio/ops/deploy.sh。若独立数据目录没有库，脚本在 NAS 本地生成一次性初始密码，写入权限为 0600 的 /opt/magicpanel-v2/initial-admin-password，用 studio.init 创建 admin、五个平台模板、四个线路方案和第一版配置。已有数据库不覆盖、不重建。起始模板仅 DIRECT，用户导入节点和规则后发布即可。离线替换忘记的密码须在有主机权限的维护环境执行，不开放公网注册。

本次上线为便于直接使用，复用了当时生效的设备配置、规则资源、节点和管理员密码校验。旧版历史发布、测速、审计、登录会话和旧设备订阅 token 均不继承。只在可选导入时使用一致副本；完成后删除临时副本。新数据库的历史只记录 v2 自身的动作。
